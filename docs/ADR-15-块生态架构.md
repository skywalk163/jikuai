# ADR-15 · 块生态架构决策（v0.12.0 起草）

- 状态：Proposed
- 日期：2026-08-09
- 决策者：架构师（用户主导，AI 辅助推演）
- 落地环节：v0.12.0 · 块生态基础设施
- 相关：ADR-16（标准库契约）、包管理.md、元数解析规范.md

---

## 1. 背景

用户提出"积木分层构建模块"思路：预置大量稳定的 `.jk` 库（"积木"），通过组合替代 AI Agent 从零生成代码。文心与 DeepSeek 分别提出了两版参考方案：

- **文心方案**：4 批次、7~10 个工作日内交付 50 条测试 + 30 个原子块 + 15 个一级模块 + 8 个二级模块 + CLI 工具链 + 可视化拖拽编辑器。层级刚性：0/1/2/…/6 级目录固定，每级 3~7 块聚合。
- **DeepSeek 方案**：新增大量语法糖 `模块 X v1.0 { ... }`、`|>` 管道符、`::` 命名空间分隔符、`实现 接口A, 接口B`、`模板 X { 生成 { ... } }`。

**核心争议点**：

1. "零 token 替代 AI Agent" 的命题是否成立？
2. 是否需要为块生态引入新语法？
3. 层级结构是刚性目录还是弹性标签？
4. 交付节奏应该多快？

---

## 2. 命题客观评估

### 2.1 "零 token 替代 AI Agent" —— 部分成立，需要降级表述

**成立的部分**：对于**已知模式**（读文件→清洗→统计→输出报表这类流水线任务），预置块 + 极快原生管道语法确实能：

- 消除代码级幻觉（块是预测试过的稳定代码，不是 AI 现场生成）
- 大幅降低 token 消耗（AI 只需输出粘合层，几十行代码级 → 几行块组合级）
- 提升可复现性（同一自然语言需求→同一段极快代码）

**不成立的部分**：AI Agent 之所以有价值，是因为它能处理**新颖、模糊、跨越已知模式**的需求。块组合只能覆盖组合空间内的任务，边界外仍需 AI 生成新块或新粘合逻辑。因此：

- ❌ 命题："零 token 替代 AI Agent"
- ✅ 修正后命题："**AI 从代码生成器降级为块选择器**——AI 负责'挑哪些块 + 怎么连'，极快负责'把它们跑起来'；对已知模式实现 10~50 倍 token 压缩，对未知模式退化为传统 AI Agent 但仍受块生态兜底"

### 2.2 层级刚性 vs 弹性

**文心方案的 7 级刚性目录**（`0_原子层/`、`1_一级模块/`、…）在数学上诱人（3^7 ≈ 2187，7^7 ≈ 82 万种组合），但工程上有以下问题：

- 真实软件有横切关注点（错误处理、状态、异步 I/O、日志），无法严格分层
- 一个块可能同时属于多个语义分组（"农历转换"既是数据变换也是中文特色），单一目录归属会强迫误分类
- 层级晋升机制不明确：一个模块什么条件下从一级升为二级？谁审？

**采纳的替代**：**层级是元数据字段（`层级: 0..N`），不是物理目录**。目录按**领域**组织（`stdlib/blocks/数据/`、`stdlib/blocks/中文/`、`stdlib/blocks/网络/`），`层级` 字段声明"这个块聚合了几层子块"。这样：

- 一个块可以在领域目录里存在，同时被多个更高层块聚合
- CLI 检索既能按领域过滤，也能按层级过滤
- 无需被迫构造刚性 7 级目录树

### 2.3 新语法引入 —— 全部拒绝

DeepSeek 提出的语法均予以拒绝，理由：

| 语法 | 拒绝理由 |
|------|----------|
| `模块 X v1.0 { ... }` | 花括号与现有 `：换行缩进` 块语法冲突；`v1.0` 内联版本号引入新词法类别 |
| `|>` 管道符 | 极快已有 `，`（逗号）作为管道分隔符（见元数解析规范 §3），引入 `|>` 造成异形写法碎片化 |
| `::` 命名空间分隔 | 极快已用 `.`（成员访问）承担同样语义 `模块.函数`；`::` 引入新 token 类型 |
| `实现 接口A, 接口B` | v0.10.0 已通过命名约定（`协` 前缀 = 接口，`抽` 前缀 = 抽象类）承载，无需新关键字 |
| `模板 X { 生成 { ... } }` | 元编程/代码生成是重大特性，超出块生态范畴；若真需要应单独立 ADR |
| `搜索 模块 关键词 = ...` | 检索是**工具行为**（CLI 命令），不是**语言行为**（不该进语法） |

**指导原则**：块生态是**基于现有语言的组织学**，不是**新的语言层**。任何"用现有 `导入`/`函数`/`类` + 元数据文件能表达"的东西，都不引入新语法。

### 2.4 交付节奏 —— 从"日"改为"周"

文心方案的时间估算（"1~2 个工作日"落地基础框架、"2~3 个工作日"落地可视化编辑器）严重低估工程实际。3 个月（12 周）×4 条并行轨道的节奏更贴近现实。详见路线图-v0.12.0.md。

## 3. 采纳方案

### 3.1 块的定义

一个"块"就是一个**带元数据的 `.jk` 模块**（或 `.jk`+`.py` 混合模块）。物理上：

```
stdlib/blocks/<领域>/<块名>/
├── 块名.jk              # 主模块（导出块的公共 API）
├── 块名.py              # 可选：Python 实现（ADR-16 §3.3 混合模块）
├── 块.json              # 块元数据（本 ADR §3.2）
└── 测试.jk              # 单元测试
```

或简单块直接落成单文件 `stdlib/blocks/<领域>/<块名>.jk` + 同级 `<块名>.块.json`。

### 3.2 元数据字段（`块.json`）

复用 `包.json` 的 JSON 格式和字段命名族，追加块专属字段：

```json
{
  "名称": "读取文件",
  "版本": "0.1.0",
  "层级": 0,
  "领域": ["数据"],
  "描述": "读取文本文件为字符串，UTF-8 编码",
  "输入": [{"名": "路径", "类型": "字符串"}],
  "输出": {"类型": "字符串"},
  "依赖块": [],
  "极快版本": ">=0.12.0",
  "示例": "读取文件 \"data.txt\"，长度。",
  "稳定性": "stable"
}
```

字段解释：

- **层级**：0=原子（不聚合其他块），N=聚合了 N-1 级块。**不是目录**，是标签。
- **领域**：数组（一个块可同时属于多个领域）。允许值：`数据`/`中文`/`网络`/`工具`/`财务`/`历法`/等，扩展需走注册流程。
- **输入/输出**：文档化的类型注解，用于 CLI 检索与 AI 桥接协议（见 §3.4）。**运行时不强制**（极快是动态类型）。
- **依赖块**：列出这个块 `导入` 的其他块名。CI 校验字段与实际 `导入` 语句一致。
- **稳定性**：`experimental`/`stable`/`deprecated`。CLI 默认只推荐 `stable`。

### 3.3 组合仅用现有语法

块的组合完全用极快现有语法：

```jikuai
导入 blocks.数据.读取文件。
导入 blocks.数据.清洗。
导入 blocks.统计.求和。

函数 处理报表 接收 路径：
  返回 读取文件(路径)，清洗，求和。
。
```

无新语法。命名空间由目录路径承担（`blocks.数据.读取文件` 是 `stdlib/blocks/数据/读取文件/读取文件.jk`）。

> **实施依赖**：当前 `module_loader.py` 的 `resolve()` 只支持扁平模块名，不支持点分路径。需在 v0.12.0 · M1 扩展 `resolve()` 支持 `blocks.数据.读取文件` → `stdlib/blocks/数据/读取文件.jk` 或 `stdlib/blocks/数据/读取文件/读取文件.jk` 的映射。此扩展与 §2.3 "不引入新语法" 不冲突——它是**解析器行为**，不是**语法变化**。

### 3.4 AI 桥接协议（token 压缩关键机制）

块生态的核心价值不是"取代 AI"，而是"让 AI 只输出粘合代码"。为此需要一份 **块索引 JSON**（`stdlib/blocks/索引.json`，由 CI 自动生成）：

```json
{
  "版本": "0.12.0",
  "块": [
    {"名称": "读取文件", "领域": ["数据"], "输入": [...], "输出": {...}, "描述": "..."},
    ...
  ]
}
```

AI Agent 拿到用户需求后：

1. 只读一次索引（几 KB～几十 KB，一次性成本）
2. 选出候选块列表
3. 输出粘合代码（十几行极快，而非几百行 Python/JS）

预期 token 压缩比：**10~50 倍**（基于粘合代码行数 / 传统 AI 从零生成代码行数的比例）。

### 3.5 检索工具链（`jk 块 ...`）

复用现有 `jk` CLI 入口，新增 `块` 子命令族：

- `jk 块 列表 [--领域 X] [--层级 N] [--稳定性 stable]` —— 列出块
- `jk 块 查找 "关键词"` —— 关键词/描述模糊检索
- `jk 块 详情 <块名>` —— 显示某块的完整元数据 + 示例
- `jk 块 校验 <块目录>` —— 校验一个块的元数据/测试是否合规（供社区贡献者本地校验）
- `jk 块 索引` —— 重新生成 `索引.json`（供 CI 使用）

### 3.6 明确不做的事

以下条目**不在 v0.12.0 范围内**，即使未来做也需独立 ADR：

- ❌ 可视化拖拽搭建界面（文心方案批次 4）—— UI 工程量远超估算，且价值待验证
- ❌ 强类型检查/接口契约运行时校验 —— 极快是动态类型语言，运行时类型检查违背语言哲学
- ❌ 块模板生成器（DeepSeek 方案 §七）—— 元编程另立项
- ❌ 云端块仓库 / 私有仓库 SSO —— 当前 `包.json` 支持路径 + Git 依赖已够用；中心化仓库运维成本高
- ❌ 强制所有块用 `协/抽` 接口 —— 命名约定作为可选最佳实践，不强制

### 3.7 词法原子性约束（v0.12.0 W2 dogfooding 实测发现）

**硬约束：块的导出名必须是「词法原子」的——整体被 lexer 识别为单个 `IDENT` token。**

#### 问题根因

极快的 lexer 是免空格的最长匹配分词器，会把内建动词从标识符中切出来：

```
块求和  →  块(IDENT) + 求和(VERB)      ✗
累加    →  累(IDENT) + 加(VERB)        ✗
赵列表  →  赵(IDENT) + 列(VERB) + 表(IDENT)   ✗
汇总    →  汇总(IDENT)                  ✓
合计    →  合计(IDENT)                  ✓
```

ADR-09 的类作用域白名单机制解决的是「**同一次分词内**用户定义名覆盖内建动词」。但块的导出名定义在**被导入模块的文件里**，调用方分词时根本不知道这个名字存在——白名单里没有它，成员访问松弛（元数解析规范 §5 第 3 条）也只松弛到「本次分词的用户定义名」。因此：

- 模块**内部**可以正常定义和调用 `块求和`（本次分词有 `函数 块求和` 声明）
- 调用方**无论**用 `从 ... 导入 块求和` 还是 `别名.块求和`，都会被切成 `块` + `求和`，报 `JK-E5002 模块 X 未导出：块`

这不是 bug，是免空格分词的固有代价。修复方向（让 loader 反哺 lexer 白名单）需要打通「先解析导入 → 再拿到导出名 → 重新分词」的双向依赖，代价远大于约定命名。

#### 采纳的约定

1. **导出名必须词法原子**。CI 门禁（`jk 块 校验`）对每个块的 `.jk` 逐一 `tokenize(导出名)`，若结果不是单个 IDENT 则拒绝入库。
2. **形参名同理**（虽然只影响模块内部可读性，但一并约束以免踩坑）。
3. **块目录名（= `块.json` 的 `名称` 字段）同样必须词法原子。**

   > **勘误**（v0.12.0 W4，三条轨道独立复现）：本条初稿写的是「目录名不受此约束，由 `_read_module_name()` 松弛接受任意词形 token」——**该表述错误**。松弛只覆盖「整段恰好是**单个** VERB/KEYWORD/ADVERB token」（`求和`→VERB 单 token，作目录名合法），不覆盖「一段被切成多个 token」。因为 `_read_module_name()` 每个点分段只消费**一个** token：
   >
   > ```
   > 从 blocks.工具.配置加载 导入 载配。
   > → ... 配置(IDENT) 加(VERB) 载(IDENT) 导入 ...
   > ```
   >
   > 模块名只拼出 `blocks.工具.配置`，parser 随后期望 `导入` 却撞上 `加`(VERB) → ParseError。这类块能通过元数据校验但**必然是死块**（无法被任何代码引用）。
   >
   > 实测被迫改名的目录：`文件装载`→`载入`、`文件落盘`→`存文`、`排序导出`→`序出`、`生肖属相`→`属相表`、`金额大写`→`金额雅写`、`农历日程`→`阴历日程`、`配置加载`→`配置集`、`JSON解析`→`记法解析`、`JSON序列`→`记法织串`、`百分编码`→`转义编码`、`请求构造`→`请求组装`。
   >
   > 另注：`百分编码` 之所以失败是 `百` 被识别为中文数字（NUMBER token）；`请求构造` 是 `构造` 为类构造器关键字；`JSON解析` 是拉丁串与汉字必然分词。

#### 唯一支持的调用形式

```jikuai
从 blocks.数据.求和 导入 汇总。
打印 汇总(列 1 2 3 4 5)。      -- 15
```

`导入 blocks.数据.求和。` 形式会把模块绑定到**叶段名**（`求和`），但由于叶段名常与内建动词重名，这条路径**不推荐用于块**——文档只宣传 `从 ... 导入 ...` 一种写法，减少用户踩坑面。

#### 推荐命名词库（原子性已实测）

`汇总` `合计` `聚合` `总和` `清洗` `规整` `解析` `编码` `校对` `裁剪` `归并` `采集` `落盘` `装载`

**禁用**：任何含 `加/减/乘/除/列/求和/长度/排序/连接/包含/反转/替换/分割/拼接/打印/输入/读取/写入` 等内建动词字样的名字。



- **`src/jikuai/module_loader.py`**：`resolve()` 支持点分路径解析（`a.b.c` → `a/b/c.jk` 或 `a/b/c/c.jk`）
- **`src/jikuai/pkg/`**：新增 `blocks.py` 模块，负责 `块.json` 解析、块索引生成、CLI `jk 块` 子命令
- **`stdlib/blocks/`**：新目录，按领域组织
- **`stdlib/blocks/索引.json`**：由 CI 生成，进版本控制以便 diff
- **`scripts/check_stdlib_contract.py`**：扩展校验 `块.json` 中 `依赖块` 字段与 `.jk` 中 `导入` 语句一致
- **`docs/块生态.md`**：新增用户手册
- **CI 门禁 G11**：块元数据一致性校验（依赖块字段 = 实际 import 语句）

## 6. 已知限制与风险

- **层级晋升治理**：一个块从 `experimental` 升为 `stable`、从层级 1 升为层级 2 的判定标准未在本 ADR 定义，交由社区治理文档（另立）
- **命名冲突**：`stdlib/blocks/数据/读取文件` 与用户项目里的 `极快_包/读取文件` 存在潜在冲突，冲突时 `module_loader._search_paths()` 的既定优先级（脚本目录 > 极快_包 > stdlib）自动裁决——用户可用局部包覆盖标准块，这是**特性不是 bug**
- **`.py` 桥接的沙箱边界**：块允许含 `.py` 实现，受 ADR-21 pybridge 安全边界约束——不新增豁免
- **"取代 AI" 期望管理**：文档必须诚实标注块生态的适用边界（已知模式），避免用户误解为"极快 = 不再需要 AI"

## 7. 领域注册记录

`领域` 白名单的正本是 [`src/jikuai/pkg/blocks.py`](../src/jikuai/pkg/blocks.py) 的
`ALLOWED_DOMAINS`；本节是每次扩容的决策档案。**改白名单必须在这里留一条记录**，
否则下一个人无从判断某个域该收什么、不该收什么。

| 领域 | 注册环节 | 边界 |
|------|----------|------|
| `数据` / `中文` / `网络` / `工具` | v0.12.0 · M1（本 ADR §2.2 初版） | 通用算子 / 中文文本 / 网络协议 / 杂项 |
| `财务` | v0.13.0 · M2 | 金额**计算**层，区别于 `中文` 域的金额表现层 |
| `历法` | v0.13.0 · M2 | 日期**数学**，区别于 `中文` 域的农历/干支文化表现层 |
| `制造` | v0.26.0 · W131（ADR-40） | 带**业务口径**的制造业指标，见 §7.1 |

### 7.1 `制造`（v0.26.0 W131 · ADR-40）

**决议**：`制造` 单独成域，白名单从六域扩到七域。

**为什么不塞进 `数据`**——这是本条记录唯一要交代清楚的问题：

- `数据` 域是**通用统计算子**：求和、均值、排序、最大最小。它们**没有业务口径**，
  给定同一组数，答案只有一个，换个行业照样能用。
- `制造` 域是**带业务口径的指标**：缺陷率、达成率、单车电耗。这些块的分母是什么、
  含不含哪些行、是先汇总后相除还是先算比率再平均、用现成比率列还是关联另一张表重算，
  **每一项都是业务判断而不是数学事实**。ADR-40 §5 记了三处实测口径分歧，同一份数据
  按两种口径算出的**是两个不同的数，且都对**——分歧只能由块的 `描述` 显式声明，
  不能由算子本身隐含。

**混在一个域里的具体代价**：`jk 块 选` 的候选列表会把通用算子和口径块混排。
`数据/均值` 和一个「平均达成率」口径块会以相近的分数并列出现，而前者对
`achievement_rate` 列做行级算术平均、后者按产量加权——这正是 AGENTS.md 第四节所说的
**「兄弟能力缺位」**：同族、口径差一档、照着组出来的代码**会跑通，结果是错的**。
检索层没有拒答路径（四轮实测已证伪所有基于分数的自动拒答方案），唯一的防线是
选块者能一眼看出「这是通用算子」还是「这是带口径的指标」。**领域字段就是这条分界线
在协议里的载体**，把它抹平等于主动放弃这条防线。

反过来说，这也界定了 `制造` 域的收录标准：**块的正确性依赖某个业务口径判断的，
进 `制造`；换个行业照抄也成立的，留在 `数据`**。ADR-40 §3.1 的引擎层算子（选取、
投影、连接、分组聚合）虽然物理上落在 `制造/` 目录下，本质是通用关系代数，
它们的 `描述` 必须自报「这是关系算子，不含业务口径」以免反向误导。
