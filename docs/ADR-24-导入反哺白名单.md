## 1. 背景

极快是免空格分词器，采用**最长匹配**规则，会把内建动词从相邻汉字里切出来：

```
块求和  → 块(IDENT) + 求和(VERB)        ✗ 调用方拿不到 `块求和`
累加    → 累 + 加(VERB)                 ✗ 同理被切碎
汇总    → 汇总(IDENT)                   ✓ 词法原子
```

ADR-09 的**作用域限定白名单**只解决"同一次分词内"的冲突：预扫描该源文件里 `定义/函数/方法/类 X` 声明的名字，加进 `ScopeMap` 免被切碎。它对**跨模块**的名字无能为力——调用方分词时**不知道**被导入模块的导出名，`块求和` 必被切成两半。

v0.12.0 因此付出实测代价：
- ADR-15 §3.7 起草 "词法原子性约束"，把这条限制写成规范约束
- dogfooding 阶段四条并行轨道被迫改名共 11 个块目录（v0.12.0 复盘 §3.1）
- `check_export_atomicity` / `check_module_segment_atomicity` 作为 CI 门禁把关（G10/G11）

痛点原文（复盘 §六 遗留技术债 · 第 1 条）：

> 块导出名词法原子性限制块命名自由度（治本需 lexer 加"导入声明反哺白名单"通路，代价大）

v0.13.0 W1-W2 决定啃这块骨头。

## 2. 目标 / 非目标

**目标**：
- 让"非词法原子的导出名" 在调用方源码里**不被切碎**，前提是调用方已经写了 `导入 <模块>` 或 `从 <模块> 导入 <名字>`
- 覆盖点分路径块（`blocks.数据.求和`）与扁平模块名（`我的块`）
- 覆盖两级组合（L2 块聚合 L1 块 —— 被加载的模块自己也 `导入` 时也要反哺）
- 全量测试零回归；无导入的普通脚本零性能开销
- 提供环境变量回退开关

**非目标**：
- 不引入新语法（沿用现有 `导入` / `从 ... 导入 ...`；符合 ADR-15 §3.3）
- 不覆盖 `蟒:X` Python 桥模块（ADR-11 强制括号调用，天然无原子性问题）
- 不覆盖动态字符串模块名（编译期不可判定）
- 不去掉 CI 门禁（原子性依然是**推荐命名**，本 ADR 只是**兜底救** 非原子名，不鼓励刻意起非原子名）

## 3. 方案候选

### 方案 A · 反哺白名单（本 ADR 采纳）

复用 `frontend.compile_source` 的 2-pass 骨架：Pass1 分词 + parse → 扫描 AST 中的 `导入` → 静默解析目标 `.jk` → `pkg.blocks.extract_exports` 提取导出名 → 过滤后作为 `external_defs` 注入 lexer → **Pass2 重新分词并重新 parse**。

关键子选择：
- **不复用 v0.5.0 的收敛判定**：白名单命中的正常结果就是"两遍 token 序列不同"（原本被切碎的名字聚合成整体 IDENT），照收敛判定回退等于把功能整个抵消。
- **不复用 Pass1 AST**：token 变了 AST 结构不同，必须重新 parse。二次 parse 失败才回退首遍并发 `JK-W9001`。

### 方案 B · 文档化约束 + 命名词库扩容

不改代码，扩充"推荐原子名词库"（汇总/合计/聚合/清洗/解析/编码/校对/裁剪/采集/落盘/装载 等），继续走 CI 门禁把关。

### 方案 C · 语法级 `导出` 元数据

给 `块.json` 加 `导出` 字段（W3 计划），或者引入 `导入 X 显式导出 A B` 之类的显式语法。前者是元数据优化（并不解决问题本身），后者违反 ADR-15 §3.3 「不引入新语法」。

## 4. 对比矩阵

- **命名自由度释放**：A 大 · B 无 · C 中（依赖用户配合写元数据）
- **代码复杂度**：A 中（Pass2 独立路径 + 3 张缓存）· B 无 · C 大（新语法路径 + 兼容层）
- **编译期性能**：A 无导入场景 +0%，含导入 +21%（详见 §7）；B/C 都是 0%
- **对现有约束的破坏面**：A 零破坏（回退开关就绪）· B 零 · C 中等
- **对 AI 桥接的收益**：A 直接兑现（AI 可以推荐"块求和 / 块清洗"这类语义清晰的名字，不用死盯着推荐词库）· B/C 不改善

## 5. 决议

**采纳方案 A**。B 作为兜底保留（推荐词库仍在维护，是命名的第一选项）；C 里的 `块.json::导出` 字段可选，作为 W3 的性能优化留待评估。

## 6. 关键机制

### 6.1 触发条件

`compile_source` 主流程：

```
Pass1: tokenize + parse
判定顺序（有一即走 Pass2）：
  a) AST 有 Import 节点 & JIKUAI_IMPORT_WHITELIST != off & JIKUAI_LEGACY_ADR06 != 1
     → 收集白名单 → 若非空则走「白名单 Pass2」
  b) AST 有 ClassDef & JIKUAI_LEGACY_ADR06 != 1
     → 走「类区间 Pass2」（v0.5.0 ADR-06 X2 行为不变）
两条互斥（有 a 就不走 b；白名单 Pass2 会顺带把 class_regions 一起注入）
```

### 6.2 白名单收集（两道过滤）

```python
whitelist = { name
              for imp in program.body if isinstance(imp, Import) and imp.kind == 'jk'
              for name in _cached_exports(_cached_resolve(imp.module))
              if name in source                    # ① 在调用方源码里出现过
              and _needs_whitelist_help(name) }    # ② 单独喂 lexer 非单 IDENT
```

**为何两道过滤都必要**：
- ① 若名字根本没出现在源码里，注入了也不改变分词结果——纯白开销。
- ② 若名字本身就是原子（如 `汇总`），塞进白名单反而可能在别处切碎更长的标识符（`汇总额` 会被 `汇总` 抢先吃成 `汇总`+`额`）。**这是一个隐患修复，不是纯性能优化**。

### 6.3 白名单 Pass2 分支

```
tokens2 = tokenize(source, external_defs=whitelist, class_regions=可选)
if token_signature(tokens1) == token_signature(tokens2):
    final = (tokens2, ast1)             # 没有名字实际被切碎，AST 等价
else:
    try:
        final = (tokens2, parse(tokens2))
    except:
        final = (tokens1, ast1)
        emit JK-W9001
```

### 6.4 模块体反哺（L2 聚合 L1）

`module_loader.load()` 用 `parse_with_import_whitelist(source, file=path)` 替代裸 `parse(tokenize(source))`。被加载的模块自己 `导入 X` 时，X 的导出名也要反哺，避免多级组合链断裂。

### 6.5 三张进程级缓存

| 缓存 | 键 | 失效策略 |
|------|-----|--------|
| `_RESOLVE_CACHE` | `(模块名, 调用方目录)` | 无（模块路径在进程生命周期内视为稳定） |
| `_EXPORTS_CACHE` | `.jk 绝对路径` | 按 `(mtime_ns, size)` 指纹校验 |
| `_NEEDS_HELP_CACHE` | 名字 | 无（原子性判定纯函数） |

指纹校验保证 LSP/REPL 里改块源码下次编译立刻生效；代价是每次编译对每个 import 做一次 `os.stat`——含导入场景 +21% 开销的主因。

### 6.6 静默失败原则

任意单个 `导入` 的白名单收集环节失败（模块解析失败/文件不可读/`extract_exports` 抛错）→ 跳过该项，不抛错。运行时的 `evaluator._eval_Import` 会走真正的 `resolve()` 精确报错（JK-E5001 等），前端阶段的静默是**降级到不反哺**、绝不是**吞掉真错误**。

## 7. 性能

Benchmark 方法：`benches/bench_compile.py` 变体，把 `examples/` + `stdlib/**/*.jk` 共 150 个 `.jk` 文件分成"含导入 / 无导入"两组，各测 `compile_source` 中位数（40 采样 + 1 轮预热）。

| 子集 | 文件数 | 基线（off） | 反哺（on） | 净增量 |
|------|--------|-------------|-------------|--------|
| 无导入 | 55 | 104.00 ms | 104.03 ms | **+0.0%** |
| 含导入 | 95 | 123.92 ms | 149.58 ms | **+20.7%** |

**优化历史**（同一天内的三个版本）：
- v1（激进版）：含导入 +138%（超阈值）—— 每次编译都重新走 tokenize + parse
- v2（加原子性过滤）：+37% —— 白名单为空时跳过 Pass2
- v3（加三张缓存 + 顶层扫描替代全 AST 遍历）：**+20.7%** ← 本 ADR 定稿

**剩余开销归因**：`os.stat` 指纹校验 + 白名单集合构造 + `_needs_whitelist_help` 缓存查询。

**是否达标**：
- 路线图原目标 <5% —— **未达**
- 现实评估：编译时性能，非运行时；生产库 52 个块导出名全原子，实际 `.jk` 脚本白名单为空、命中 §6.2 过滤 → 走 Pass1 → **实际用户零感知**。基准数据的 +20.7% 是"每个含导入文件都不断被重复编译"这种极端场景（例如 CI 批量校验）才能观察到。**接受**。

**未来优化**（W4 或延后）：可选去掉 `os.stat` 校验、改为纯进程级缓存，把开销压到 <5%。代价是 LSP/REPL 里改块源码需要重启会话——**留待用户裁决**。

## 9. 已知限制

- **动态模块名不覆盖**：`导入 (拼接 "M" 数字)` 之类形态在编译期不可判定，反哺不生效——运行时依旧按 v0.12.0 语义。用户想让动态导入享受反哺，只能改写成静态 `导入 M1` / `导入 M2`。
- **单向反哺**：只从**被调用模块 → 调用方**注入白名单；不做双向传递（被调用模块自己的导出 `.jk` 里若引用了 **它** 导入的名字，那次分词依然靠 `parse_with_import_whitelist` 内部递归解决，但不会把这些名字继续暴露给外层调用方）。当前语义下够用；出现跨三级转发场景再评估。
- **含导入文件 +20.7%**：见 §7 讨论。
- **超集注入**：`从 M 导入 A B` 时白名单取 M 的**全部**导出，不严格按名字列表。理由：白名单只影响分词，运行时可见性仍由 `ModuleValue.get` 按 `_exports` 拦截；超集在语义上安全，但会让白名单略大一些。

## 10. 回退策略

三档：

1. `JIKUAI_IMPORT_WHITELIST=off` —— 只关本次反哺，类区间 Pass2 仍工作
2. `JIKUAI_LEGACY_ADR06=1` —— 关掉整个两遍分词（ADR-09 强制单遍），退回 v0.4.x 行为
3. Pass2 二次 parse 失败自动回退首遍并发 `JK-W9001` —— 无需环境变量介入
