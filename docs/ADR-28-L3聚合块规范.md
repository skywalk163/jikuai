# ADR-28 · L3 聚合块规范（v0.16.0 W29）

- 状态：Accepted
- 日期：2026-08-10
- 决策者：项目维护者
- 落地环节：v0.16.0 M8 W29（规范 + 门禁）／W30（3 个 L3 块落地）
- 相关：ADR-15（块生态架构 · 层级是标签不是目录）、ADR-26（类型词表）、
  ADR-27（第三方块注册表 · 稳定性传递的上游）

---

## 1. 背景

v0.15.0 收官时块库共 105 个块，层级分布 **L0×83 / L1×19 / L2×3**。
`docs/v0.14-v0.15-复盘.md` 已证：**真到跨域场景，L2 数量偏少**——现有 3 个 L2
（`工资条`、`月结单`、`用户档案`）都只在单一领域内聚合，用户问「报销单怎么算」
这类跨财务 + 历法 + 中文的问题时，检索只能给一堆原子块，粘合器要自己拼 6~8 步。

L3 = **跨 L2 的场景块**（`报销单` / `工资册` / `客户对账`）。但 `层级` 字段自
ADR-15 起就只有一句"N = 聚合了 N-1 级块"的口头定义，`_validate` 里更是**只校验
非负整数**（`"层级": 7` 也能过）。没有判定规则就先写块，必然写出一批自称 L3、
实际只包了两个原子块的假聚合，检索侧还会当宝贝往上推。

**所以本轮只定规范 + 上门禁，不写 L3 块本身**（那是 W30）。

## 2. 目标与非目标

**目标**

1. 给出 L3 的**可机检判定**，让"是不是 L3"不靠人眼评审。
2. 把 ADR-27 §2.5 只写了规范没落校验的**稳定性传递**在聚合层落地。
3. 明确**依赖深度上限**，防止层级无限加深。
4. 复用既有 `块.json` 字段表达依赖，**不新造字段**。

**非目标**

- 不追溯存量 L0/L1/L2 块的层级判定（见 §5 已知欠账）。
- 不改块的物理目录布局（ADR-15 §2.2 的"层级是标签不是目录"继续有效）。
- 不写 L3 块、不改索引格式、不动检索排序。

## 3. 决议

### 3.1 层级定义与 L3 判定

| 层级 | 名称 | 判定 |
|------|------|------|
| L0 | 原子块 | 不依赖其它块 |
| L1 | 复合块 | 依赖 L0 |
| L2 | 场景块 | 聚合 L1／L0，通常单领域 |
| **L3** | **跨域场景块** | **见下** |

**L3 判定（满足其一即可）**

1. 直接依赖 **≥ 2 个 L2+ 聚合块**；或
2. 直接依赖 **≥ 1 个 L2+ 聚合块**，且这些直接依赖**跨 ≥ 2 个领域**。

三处措辞是刻意的，逐条说明：

- **"L2+"而不是"恰好 L2"**：L3 依赖另一个 L3 在语义上仍是合法聚合（聚合体
  聚合聚合体）。判定按 `层级 >= 2` 计数，实现里是 `AGGREGATE_LEVEL`。
- **"直接依赖"**：只看 `依赖块` 声明的一跳，不做传递闭包。传递闭包会让判定
  结果随远处的块改层级而漂移，贡献者改自己的块却被别人的改动挂掉门禁。
- **"跨 ≥ 2 领域"取的是依赖方的领域并集**，不是本块自己声明的 `领域`。
  自己的 `领域` 是发布者手填的，想标几个标几个；依赖的领域是从被依赖块的
  元数据算出来的，作不了假。

第 2 条存在的意义：`报销单` 可能只聚合一个 L2（`工资条`）+ 若干跨领域 L1
（历法的 `日序`、中文的 `金额雅写`），条 1 卡它但它确实是跨域场景块。

### 3.2 稳定性传递（扩展 ADR-27 §2.5）

> **v0.17.0 W44 修订**：本节原先只覆盖 `L3 → L2+`，两处刻意收窄已在 W44 放开到
> 全量强度。规则现为：**stable 的聚合块（`层级 >= AGGREGATE_LEVEL`，即 L2 与 L3）
> 不得依赖任何非 stable 块（含 L0/L1 叶子）。** 历史收窄理由与放开依据见文末对照。

**stable 的聚合块（L2+），其全部 `依赖块` 必须也是 stable。**

`deprecated` 一并拒——它是承诺要移除的东西，stable 块压在上面比压在
experimental 上更糟。

**依赖方仍只查 L2+**：叶子块之间（stable L0 依赖 experimental L0）不查。
`稳定性` 对叶子的意义是「这个工具函数的签名会不会变」，把传递性一路压到 L0
会让 83 个原子块互相绑死，收益远小于代价。要收这一层得另立 ADR。

**W44 为什么敢放开**（原收窄理由 vs 现在的处置）：

| 原收窄 | 原理由 | W44 处置 |
|--------|--------|----------|
| 只管依赖方是 L3 | stable L2 依赖 experimental L1 是 v0.14.0 存量形态（`工资条`→`税单`、`用户档案`→`姓名拆分`/`地址剖解`），追溯会让门禁上线即红 | **放开到 L2+**。W44 的任务本身就是清这笔账 |
| 只管被依赖方是 L2+ | 26 个 experimental L0/L1 叶子块，跨域 L3 难完全绕开 | **放开到任意层级**。实测存量违规只有 3 处，不是当年担心的规模 |

三处存量违规的裁决（ADR-28 §6 的「逐个判断，不一刀切」）：
`税单`(L1) / `姓名拆分`(L0) / `地址剖解`(L0) **一并提为 stable**，
而不是把 `工资条` / `用户档案` 降级。依据是**`稳定性` 承诺的是接口兼容
（输出元组的元数与形状），不是解析准确率**——三者的元组形状
（4 元 / 2 元 / 4 元）已定型且不打算再改。准确率的边界（`地址剖解` 对直辖市、
无街道地址是启发式）属于 `描述` 该讲的事，不该拿 `稳定性` 字段代偿。


### 3.3 依赖深度上限：本轮只开到 L3

`层级` 的合法取值从"任意非负整数"收紧为 **0..3**，`层级 >= 4` 由
`load_block_metadata` 直接拒（`MAX_BLOCK_LEVEL = 3`）。

**为什么不顺手开 L4+**

1. **检索解释成本**：ADR-25 的召回要能回答"为什么给你选这个块"。层级越深，
   解释链越长——L4 命中时得讲清它下面 4 层为什么都合适，而用户只想知道
   "这块能不能算我的报销单"。
2. **粘合器推导爆炸**：W3-W4 类型图粘合器按类型链推参。每加一层，候选组合
   在最坏情况下乘一次分支因子；L3 的自动链式覆盖率本来就预期低于 L2
   （WBS W30 已明确"如实记录"），先把 L3 的数字量出来再谈更深。
3. **没有块能证明需求**：现在连 L3 块都是 0 个。开一个没人用的层级，只会
   多一档谁都不敢填的元数据。

要开 L4 必须**另立 ADR**，并拿出两样东西：至少 3 个 L3 块的实测链式覆盖率，
以及一个"用 L3 表达不了、必须 L4"的真实场景。

### 3.4 依赖声明：沿用 `块.json` 的 `依赖块` 字段

**不新造字段。** `块.json` 自 v0.14.0 起就有 `依赖块`：

```json
{
  "名称": "工资条",
  "层级": 2,
  "领域": ["财务"],
  "依赖块": ["税单", "金额报表", "周岁"]
}
```

**字段内容是块的叶名（`名称` 字段值），不是点分全名。** 这与 G11 的既有对账
口径一致：`validate_block` 步骤 6 拿 `依赖块` 与 `.jk` 里 `从 blocks.财务.税单
导入 …` 的**叶段**比对（`_extract_import_deps` 取 `segs[-1]`）。叶名在单个
命名空间内由 `scan_blocks` 的 `(命名空间, 名称)` 去重保证唯一，因此内置块库
范围内解析无歧义。

L3 块的 `依赖块` 与其它层级没有格式差别——只是内容里会出现 L2 块名。

### 3.5 依赖环禁止

`依赖块` 构成的有向图必须**无环**。A 依赖 B 又被 B 依赖，或更长的
A→B→C→A，一律拒。

理由：环让 `层级` 失去偏序含义（谁聚合谁？），也让粘合器的链式推导在候选图
上打转。运行时未必崩（`.jk` 的 `导入` 有模块缓存兜着），**所以只有门禁能在
PR 阶段挡住**，靠跑一遍是发现不了的。

### 3.6 参数收敛：L3 入参必须用类型词表标注

L3 的 `输入[].类型` 与 `输出.类型` 必须达到 ADR-26 的精度：裸 `列表` /
`字典` / `元组` 一律不行，要给到 `元素类型` / `键类型`+`值类型` / `元数`。
这一条**已由 G14（`check_stdlib_type_annotations`）强制**，L3 不需要新门禁，
但规范里必须写明白，因为它是"粘合器能不能自动链式"的前提：

```json
"输入": [
  {"名": "明细", "类型": {"类型": "列表", "元素类型": "数"}},
  {"名": "日期", "类型": {"类型": "元组", "元数": ["数", "数", "数"]}}
],
"输出": {"类型": {"类型": "元组", "元数": ["数", "数", "字符串"]}}
```

`列表<任意>` 等同 `任意`，粘合器只能无差别硬塞——L3 的入参本来就多
（聚合了多个 L2 的参数），一旦退化成硬塞，自动组装的成功率会掉到不可用。

**收敛建议**（规范，非门禁）：L3 入参优先复用被依赖 L2 的输出类型形状，让
`L2.输出 → L3.输入` 能直接对上；能合并成一个元组的参数不要摊成 5 个标量。

## 4. 实现

### 4.1 `src/jikuai/pkg/blocks.py`

| 新增 | 作用 |
|------|------|
| `MAX_BLOCK_LEVEL = 3` | 层级上限，`_validate` 用（§3.3） |
| `AGGREGATE_LEVEL = 2` | "L2+ 聚合块"门槛 |
| `L3_LEVEL = 3` | L3 层级值，避免魔法数字 |
| `build_dependency_graph(blocks)` | 建 `名称 -> [依赖块名]` 有向图 |
| `find_dependency_cycles(graph)` | 三色 DFS 找环，返回闭合路径 |
| `check_dependency_acyclic(...)` | 门禁入口：环列表，空 = 绿 |
| `check_level_consistency(...)` | 门禁入口：L3 层级虚标问题列表 |
| `check_stability_propagation(...)` | 门禁入口：稳定性传递问题列表 |

`_validate` 的 `层级` 校验加上限分支；其余字段校验一字未动。

**环检测算法**：三色 DFS（白=未访问／灰=在递归栈上／黑=子树走完）。碰到指向
**灰**节点的边即后向边，此时递归栈上从该灰节点到当前节点的一段就是环体，
闭合后即为一个环。自环（A 依赖 A）返回 `['A', 'A']`。

不用 Kahn 拓扑排序的原因：拓扑排序只能回答"有没有环"，剩下的节点集是所有环的
并集，报错指不出具体环路；贡献者需要的是「税单 → 工资册 → 税单」这种能照着改
的路径。去重按环体的字典序最小旋转（`A→B→A` 与 `B→A→B` 只报一次），
DFS 起点按名称排序，保证同一份块库每次跑出同样的报错文本（CI 日志可 diff）。

### 4.2 门禁：`scripts/check_stdlib_contract.py`

三条检查串在既有 G13 之后，**归入 G13 家族（输出前缀 `G13+`），不新开门禁号**
——G13 本就是"块间全局一致性"这一类，且 `docs/贡献指南.md` 与 WBS 里的
"六门 G10-G15"表述可以保持不变。

| 检查 | 失败输出 | 退出码 |
|------|----------|--------|
| 依赖环 | `G13+ 依赖图有环（N 个）` + 每条环路径 | 非 0 |
| 层级一致性 | `G13+ L3 层级虚标（N 处）` | 非 0 |
| 稳定性传递 | `G13+ L3 稳定性传递违规（N 处）` | 非 0 |

三者都只扫内置块库（`root=blocks_root()`），与 G14 同策略——本机配了
`JIKUAI_PKG_ROOTS` 不该让内置门禁变红。沿用 G13/G14 的 `try/except` 包裹：
老分支上没有这些函数就打印 `G13+ 跳过（…）` 并放行，不阻塞既有门禁。

### 4.3 对既有能力的影响

| 能力 | 影响 |
|------|------|
| `索引.json` 格式 | **无变化**。`依赖块` 本来就不进索引（检索期用不上） |
| G12 向量索引 | **无需重跑**。嵌入语料是 `名称+领域+描述`，本轮没动 |
| G11 `依赖块` ↔ `导入` 对账 | **无变化**，仍按叶名比对 |
| G14 类型精度 | **无变化**，L3 复用同一条规则（§3.6） |
| 第三方块 | 层级上限对所有块生效；L3 判定与稳定性传递只在被扫进来时参与 |

## 5. 已知欠账与局限

1. **~~存量 stable L2 依赖 experimental L1 未追溯~~**（v0.17.0 W44 已清）：
   `工资条`→`税单`、`用户档案`→`姓名拆分`/`地址剖解` 三处，W44 把三个被依赖块
   （`税单`/`姓名拆分`/`地址剖解`）提为 stable，同时把 §3.2 规则放开到全量强度。
   门禁 `check_stability_propagation` 现覆盖此形态且实测零违规。
2. **L0/L1/L2 无层级判定**：本轮只机检 L3。存量 105 个块是在没有判定规则的
   年代写的，一刀切追溯等于大规模元数据返工。L2 判定留待后续 ADR，届时连同
   存量一起收。
3. **跨命名空间同名块会被并成一个图节点**：依赖图按叶名建（§3.4）。内置块库
   单命名空间无歧义，但若第三方命名空间里出现同名块且都被扫进同一次检查，
   两者会合并，理论上可能报出假环。等第三方 L3 真出现再上"命名空间 + 叶名"
   两级解析。
4. **`依赖块` 装叶名而非全名，与 WBS W29 原文"块全名"不一致**：见 §3.4 的
   理由——改全名要连带翻 G11 与全部现存 L2 块元数据，收益为零。以本 ADR 为准。

## 6. 决策记录

| 备选 | 结论与理由 |
|------|-----------|
| 新造 `依赖` 字段装全名 | **拒**。已有 `依赖块`，新造会与 G11 对账口径分裂，且两个近义字段必然漂移 |
| L3 判定用传递闭包 | **拒**。判定结果会随远处块改层级而漂移，贡献者被别人的改动挂掉 |
| "跨域"按本块自己声明的 `领域` 算 | **拒**。发布者手填，想标几个标几个，作不了假的是依赖的领域并集 |
| 稳定性传递全量强制（含 L2→L1） | **W29 拒 / v0.17.0 W44 采纳**。W29 拒的理由是「门禁上线即红（存量 3 处违规），逼着做无关的存量治理」；W44 的任务本身就是清账，故放开到全量强度（见 §3.2 修订说明） |
| 本轮直接开到 L4/L5 | **拒**。见 §3.3 三条理由：解释成本、推导爆炸、零需求证据 |
| 环检测用 Kahn 拓扑排序 | **拒**。指不出具体环路，报错对贡献者没有可操作性 |
| 新开门禁号 G16 | **拒**。同属"块间全局一致性"，归 G13 家族可保持"六门"表述不变 |
