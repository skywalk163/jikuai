# ADR-31 · 不做 `textDocument/codeAction`（v0.18.0 W53）

- 状态：Accepted
- 日期：2026-08-11
- 决策者：项目维护者
- 落地环节：v0.18.0 M13 W53（第四轮复审 · 终局裁决）
- 相关：ADR-29（跨文件符号表）、`lsp/README.md`「已知缺口」、`docs/BACKLOG.md` §1

---

## 1. 背景：四轮复审的历史

`textDocument/codeAction` 自 v0.15.0 起被提出，**连续三轮判定「可选」并跳过**，三轮理由是同一句话「无新证据说明必要性」：

| 轮次 | 出处 | 原文 |
|------|------|------|
| v0.15.0 W15 | `docs/v0.15.0-WBS.md` L63 | 「新增 `_handle_code_action`（**可选，若时间够**）：光标在注释行时提供「按此需求选块」action」——DoD 未列入必需项，时间不够未做 |
| v0.16.0 W32 | `docs/v0.16.0-WBS.md` L191 | 「`codeAction` **本轮不做**：v0.15.0 已判定可选并跳过，无新证据说明必要性」 |
| v0.17.0 W41 | `docs/v0.17.0-WBS.md` L146/L160 | 「`codeAction` 试水（**可降级项，时间不够就砍**）」——实际砍掉，`CHANGELOG.md` 记「无新证据说明必要性，推 v0.18.0」 |

v0.18.0 WBS W53 明文写死：**「不许第四次跳过」**——本轮要么落地、要么另立 ADR 明确关闭。本 ADR 是后者，且**本轮真的走访了证据**（不是又一次「时间不够」）。

## 2. 走访结果：三条证据

### 2.1 证据一：14 个诊断码里，没有一个存在「唯一确定的机械修复」

`codeAction` 的核心价值是 quick fix：诊断 → 一键修。前提是诊断对应的修复动作**唯一且确定**。逐码走访 `src/jikuai/diagnostics/codes.py` 的 `CODE_TABLE`（全 14 码，与 `docs/诊断编码表.md` 对齐）：

| 错误码 | 含义 | 有唯一机械修复？ | 理由 |
|--------|------|------------------|------|
| JK-E0001 | 非法字符 | 否 | 非法字符成因多样（全角/半角、复制粘贴脏字符），无唯一改法 |
| JK-E1001 | 意外的文件结束 | 否 | 缺的 token 不确定——可能缺句末 `。`、可能缺整个块体缩进段 |
| JK-W1001 | 副词后接非内建动词，按原值透传 | 否（近似候选） | 只有 `spelling.suggest` 恰好给唯一候选时可替换；多候选或编辑距离 >1 时无解 |
| JK-E2001 | 未定义的名称 | 否 | 三种成因并存：拼错 / 没 `导入` / 从未 `定义`。三种修法完全不同 |
| JK-E2002 | 未知的内建动词（含拼写建议） | 否（最近候选） | `Suggestion` 允许最多 3 条并列；且 `model.py` 的 `Suggestion.replace` **当前硬编码为 `None`**，架构上就没有可直接套用的替换文本 |
| JK-E3001 | 动词元数不符 | 否 | 少参/多参都要靠用户判断是哪个参数错，补不出来 |
| JK-E4001 | 类型不匹配 | 否 | 通用类型错，修法完全取决于上下文 |
| JK-E4002 | 路径不安全 / 不可实例化抽象类 | 否 | 前者是安全拒绝**不该**被自动绕过；后者需用户选具体子类 |
| JK-E4003 | 文件超上限 / 抽象方法未实现 | 否 | 能生成 stub 骨架，但方法体内容无从确定，等于生成一个新的编译错误 |
| JK-E5001 | 找不到模块 | 否 | 不知道用户想导入哪个模块名变体 |
| JK-E5002 | 模块未导出该名字 | 否 | 是用户记错导出名，还是模块该扩展？两种修法方向相反 |
| JK-E6001 | 命中 pybridge 拒绝清单 | 否 | 安全拒绝，无绕过修复 |
| JK-W6001 | pybridge 非沙箱信任提示 | 否 | 信息性告知，本就不需要修 |
| JK-E7001 | 超出 AOT 受支持子集 | 否 | 需重写代码避开不支持的构造，无唯一机械变换（见 BACKLOG §2 设计边界） |
| JK-E8001 | 调试能力暂不支持 | 否 | 平台限制，代码层面无修复 |
| JK-W9001 | 两遍分词未收敛，已回退首遍 | 否 | 内部契约问题，用户既无法也不应修 |

**逐码结论：0/14 满足「唯一确定的机械修复」。** 最接近的两个（JK-E2002 拼写建议、JK-W1001 副词内未知动词）都卡在同一处：诊断模型的 `Suggestion.replace` 字段现在是 `None`，且建议本就允许多条并列。**没有可修的诊断，quick fix 就没有落点。**

顺带纠正三个曾被当作 codeAction 用例的假设，它们在极快里都不存在：

- **「变量名不以百家姓开头 → 自动加前缀」**：极快没有这个诊断码。变量名首字不是百家姓时，词法器根本不会把它切成 IDENT（会切成关键字/动词/非法字符），产出的是 JK-E0001/JK-E2002 之类，而不是一句「请加百家姓前缀」。**没有这条诊断，就没有这个 quick fix。**
- **「缺句末 `。` → 自动补」**：极快没有独立诊断码，这种情况落到 JK-E1001（意外 EOF），而 EOF 缺的东西不止 `。`。
- **「导入了未声明的块 → 自动加 `导入`」**：最近的是 JK-E5001（找不到模块），但它不知道正确的块名，推不出该插哪一行。

### 2.2 证据二：唯一被提出过的用例「注释触发选块」已被 `executeCommand` 完全覆盖

四轮里被提出的 codeAction 用例**只有一个**，从 v0.15.0 W15 到 v0.18.0 W53 原文一致：「光标在注释行时提供『按此需求选块』action」。

而这个能力已经在 v0.16.0 W33 落地了，走的是另一条通道：

- LSP 侧：`workspace/executeCommand` 分派 `极快.选块`（`server.py` 的 `_handle_execute_command` → `_exec_select_block`），能力声明在 `capabilities.SERVER_CAPABILITIES['executeCommandProvider']['commands']`
- 编辑器侧：`editors/vscode/src/extension.ts` 无条件注册 `COMMAND_SELECT_BLOCK`，命令面板 `Ctrl+Shift+P` → 输入需求 → QuickPick 展示候选（名称/领域/L层级/分数/描述）→ 选中后把 `从 blocks.<领域>.<块名> 导入 <导出名>。` 插到光标处

把触发方式从「命令面板输入需求」改成「光标停在注释行时弹灯泡」，**增量只是触发入口的便利性，没有新增任何能力**。而代价不是零：

1. `codeActionProvider: true` 进 `SERVER_CAPABILITIES` 是**公开契约变更**，要同步 `freeze_signature()` 与 `tests/test_lsp_capabilityies_freeze.py` 的 `EXPECTED_FREEZE`（12 个顶层 key 的字典序 dict），此后永久承担该 capability 的兼容义务。
2. 这个 action 的 LSP kind 是 `source`（重构/生成类）而不是 `quickfix`——它不修任何诊断。为一个纯 UI 糖开一个通常被理解为「修错」的 capability，会让客户端与用户对该能力的期待与实际不符。

### 2.3 证据三：四轮零外部诉求

全仓库 grep：

- `codeAction` → 30 处命中，**全部是本项目自己的 WBS / BACKLOG / README / 复盘规划文本**，无一条来自外部
- `快速修复` → 1 处，就是 `docs/v0.18.0-WBS.md` W53 的规划文本本身
- `quick fix` / `quickfix` → **0 命中**
- 用户反馈 / issue 类线索 → **0 命中**

从 v0.15.0（2026-08 前）至今四轮，没有任何用户或社区提出过 quick fix 诉求。

**补充走访 W53 原文那问「块生态 112 块里有多少『快速修复』类需求真的存在」**：112 块（L0×83 / L1×19 / L2×3 / L3×7）本身不产生诊断——块是被 `导入` 的库，诊断产生于**使用者写 `.jk` 源码时**，那批诊断就是 §2.1 的 14 码。所以这问的答案是 **0**：块生态规模再涨，也不会新增一个「机械可修」的诊断种类。

## 3. 决议

**不实现 `textDocument/codeAction`。`capabilities.SERVER_CAPABILITIES` 不新增 `codeActionProvider`。**

配套动作：

1. `docs/BACKLOG.md` §1 的 codeAction 条目：优先级由 `低` 改为 **`设计边界`**，目标版本由 `v0.18.0` 改为 **`不做（除非另立 ADR 推翻本 ADR）`**，并链到本文。
2. `lsp/README.md`「已知缺口」表：把 codeAction 从「缺口」移出，改到「刻意不做」表述，指向本 ADR。
3. **v0.19.0 起 `codeAction` 不再作为待办出现在任何 WBS**。要重开必须先推翻 §2 三条证据中的至少一条（见 §5 重开条件）。

## 4. 已知代价（诚实列出，不假装零成本）

1. **失去「注释行弹灯泡选块」的便利**。用户仍需走命令面板（多两次击键 + 手输需求）。这是本决议唯一的真实体验损失，接受。
2. **未来若诊断模型补齐 `Suggestion.replace`，JK-E2002 会变成一个真正可修的诊断**。届时 §2.1 的第一条证据就被推翻——那是重开本议题的正当时机（见 §5）。本 ADR 不预先否决那一天。
3. **对齐主流 LSP 客户端的「完备度」观感有损**。VS Code 用户习惯有灯泡；没有 `codeActionProvider` 会让极快的 LSP 看起来比同类少一项。但「看起来完备」不是实现一个空转能力的理由。

## 5. 重开条件（写死，避免下一轮又靠感觉讨论）

满足**任意一条**即可重开，且重开时必须在 WBS 里引用本节：

1. `Suggestion.replace` 字段落地并至少有 **1 个诊断码**能给出唯一确定的替换文本（推翻 §2.1）。
2. 出现**任何**外部用户/社区关于 quick fix 或「注释触发选块」的具体诉求（推翻 §2.3）。
3. 新增的诊断码里出现「唯一机械修复」形态（例如未来若真加一条「变量名缺百家姓前缀」的专用诊断，且能确定该补哪个姓）。

**不构成重开理由**：「别的语言 LSP 都有」「顺手就能做」「这轮时间富余」——前三轮就是被这类理由反复挂起的，本 ADR 的存在就是为了终结这个循环。

## 6. 决策记录

| 备选 | 结论与理由 |
|------|-----------|
| 落地最小集「注释触发选块」 | **拒**。零能力增量（`极快.选块` 已覆盖），却要付 capability 冻结契约的永久成本；且该 action 是 `source` kind，挂在通常被理解为「修错」的 capability 上会误导客户端与用户 |
| 落地 JK-E2002 的拼写 quick fix | **拒（暂时）**。`Suggestion.replace` 现为 `None`、建议允许多条并列，架构未 ready。列为 §5 重开条件 1 |
| 第四次标「可选，推 v0.19.0」 | **拒**。这正是本 ADR 要终结的行为。三轮同一句「无新证据」已证明「推迟」不会自动产生证据 |
| 实现空壳 `codeActionProvider` 返回空数组 | **拒**。声明了能力却永远返回空，比不声明更糟——客户端会显示灯泡然后给用户一个空菜单 |
| 本方案：明确关闭 + 写死重开条件 | **接受**。三条证据坐实（0/14 可修诊断、唯一用例已覆盖、四轮零诉求），且 §5 给了可判定的重开闸门，不是一刀切封死 |
