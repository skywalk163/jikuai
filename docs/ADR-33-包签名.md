# ADR-33：包签名

- 状态：**已定稿**
- 日期：2026-08-12
- 阶段：v0.20.0 · M19（W73-W76）
- 关联：`docs/ADR-27-第三方块注册表.md`、`docs/ADR-32-块包格式.md`、`docs/包管理.md`、`src/jikuai/pkg/registry.py`、`src/jikuai/pkg/installer.py`、`docs/路线图-v0.19-v0.20.md`
- 前置事实：v0.19.0 已发布（块包一体 + 生态冷启动，本地闭环）；注册表/发布/安装三通道已跑通；HTTP 分发是 M20

---

## 1. 背景与问题

v0.19.0 让「块能通过包管理装、装完 AI 用得上」成立，但整条链路的**信任基础是零**：

- `registry.publish` 只算 sha256 校验和写进索引条目
- `installer.install` 也只**计算**校验和写 `包.锁`，**不做比对**（v0.19.0 实况：没有 verify-on-read）
- 校验和只能证明「文件没被传输意外损坏」，**证明不了「这个包是谁发的」**

沿着 M20 的方向走一步就出事：注册表源一旦支持 `https://` 根，任何能写到那个
根（或能中间人劫持）的人都可以推任意包，而安装方没有任何手段判断包的来源。
`registry.py` 的 docstring 本来就写着「HTTP 分发留到接入 token 鉴权 + 包签名
之后」——**签名是传输的前置，不是配套增强**。

路线图定的顺序是**签名先行、传输在后**：M19 只做签名（本地可验证，跨机之前
先把「可信」立起来），M20 才碰 HTTP。

---

## 2. 决策

### 2.1 算法：Ed25519，**纯标准库自实现**

签名算法选 Ed25519（RFC 8032）；实现落 `src/jikuai/pkg/_ed25519.py`，
**只依赖 `hashlib.sha512` 与 Python 大整数运算**，零第三方依赖。

**为什么必须自实现**（不是偏好，是约束推出来的唯一解）：

`src/jikuai/` 下**运行时零第三方 pip 依赖**是 v0.16.0 起的硬约束。而 Python
标准库**没有任何非对称原语**——`hashlib` 只有哈希，`hmac` 是对称的。三条出路：

- **引 `cryptography` / `PyNaCl`** → 破零依赖约束。**拒**
- **把签名下沉到 `tools/`**（那里允许第三方依赖）→ 但**验签必须在 `jk 包 装`
  的运行时路径上**，即 `installer.py`，在 `src/jikuai/` 里，绕不开。让
  installer 依赖 `tools/` 等于把「桥接工具」变成运行时依赖，比引 pip 包更糟。**拒**
- **按 RFC 8032 自实现** → 满足约束。**选**

**为什么可以接受**：

- **算法标准 + 实现可验证**：RFC 8032 §7.1 给了官方 test vectors，
  `tests/test_ed25519_vectors.py` 全跑（4 组向量 × 公钥推导/签名逐字节一致/
  验签通过，加 5 类反例）。密码学的风险在「自创算法」，不在「照 RFC 实现标准算法」。
- **性能够用**：签名/验签是**离线一次性**操作（发一次包、装一次包）。用扩展
  齐次坐标（extended homogeneous coordinates，全程只在最后压缩点时做 2 次模逆）
  后单次十毫秒量级。不是 TLS 握手那种每秒千次的场景。

### 2.2 签名对象：**校验和字符串**，不是快照字节

签的是 `sha256:<hex>` 这个**校验和字符串的 UTF-8 字节**，不是快照目录本体。

理由：
- 校验和已经是快照内容的密码学摘要，签它等价于签内容（sha256 抗碰撞）
- 签名输入定长 71 字节，与包大小无关 —— 签一个 1KB 的块包和一个 100MB 的包
  耗时一样
- 校验和本来就要在索引条目里存一份，签名与它并列，人肉核对也方便

**代价与前提**：这条链的强度依赖「校验和的计算方式跨端一致」。
`sources.compute_checksum` 必须对同一份内容在任何平台产出同一个 hex ——
这是它既有的承诺（`test_pkg_block_e2e` 里「同源发布必然同和」钉着）。

### 2.3 校验和格式统一为 `sha256:<hex>`（W73 已落地）

v0.19.0 遗留：`registry.publish` 存**裸 hex**（64 字符无前缀），`installer`
往 `包.锁` 写 `sha256:<hex>`。底层同一个 `compute_checksum`，只有包装层不同。

v0.19.0 时这只是「不好看」。**做签名后它是真 bug**：签名对象是校验和字符串，
两端字符串不同 → 签同一个包得到不同签名 → 验签必失败。

W73 已统一为带 `sha256:` 前缀。前缀即算法标识，将来换算法有位置放。

### 2.4 密钥格式与落点

- **私钥**：32 字节种子，base64 存 `<密钥根>/<别名>.私钥`，权限尽力设 0600
- **公钥**：32 字节压缩点，base64 存 `<密钥根>/<别名>.公钥`
- **密钥根**：`$JIKUAI_KEY_ROOT` > `~/.jikuai/密钥/`

Ed25519 的私钥就是 32 字节随机种子（公钥可由种子推出），不需要存密钥对，
**也不该存**——存冗余的公钥副本会引入「私钥和公钥对不上」这种本不存在的故障态。

**Windows 权限说明**：`os.chmod` 在 Windows 上对 0600 的语义与 POSIX 不同
（只能控制只读位）。这里**尽力设置但不因失败而中断** —— 密钥文件权限是纵深
防御的一层，不是唯一防线；跨盘/跨文件系统场景下强求 chmod 成功会让功能在
合法环境里挂掉。

### 2.5 公钥分发：注册表根下 `密钥/` 目录

- 注册表根新增 `密钥/<签名者>.公钥`
- 索引分片条目新增两个字段：`签名者`（别名字符串）、`签名`（base64 的 64 字节签名）
- `sources._fetch_registry` 顺带把用到的公钥拉到本地信任库 `~/.jikuai/信任/`

**这一层的信任模型是 TOFU（Trust On First Use）+ 显式白名单**，不是 PKI：
- 首次见到某签名者 → 拉公钥、记进本地信任库
- 之后该签名者的公钥变了 → 拒装并报「公钥变更」（不静默接受）
- 环境变量 `JIKUAI_TRUSTED_SIGNERS`（分号/`os.pathsep` 分隔）给显式白名单：
  设了就只信名单里的签名者，**即便签名本身有效**

**为什么不做 CA/PKI**：极快的包生态现在有 4 个第三方包，签名者数量是个位数。
引入证书链需要根 CA、吊销列表、有效期，这三样都要有人运维。TOFU + 白名单在
这个规模下提供的实际保护差不多，运维成本近零。等签名者上百再谈 PKI（重开
条件见 §6）。

### 2.6 CLI 面

- `jk 包 密钥 生成 <别名>` —— 生成密钥对
- `jk 包 密钥 列表` —— 列本机密钥
- `jk 包 密钥 导出 <别名>` —— 打印 base64 公钥（给注册表管理员）
- `jk 包 发布 --签名 <别名>` —— 发布并产出签名
- `jk 包 装` —— **自动**校验签名，不可信包拒装（无 flag，安全默认不该 opt-in）

新增 `密钥` 子命令必须同步 `docs/包管理.md` 命令表，否则 **G17 门禁当场红** ——
这正是 G17（v0.19.0 W62）要防的漂移。

### 2.7 未签名包的过渡策略

v0.20.0 期间：装未签名的包 **Warn 但放行**（stderr 中文警告）。
v0.21.0 起：拒装未签名包（`--允许未签名` 显式开逃生门）。

理由：注册表里现在全是 v0.19.0 及之前发的未签包。M19 一上线就硬拒等于把
既有生态一次性打死。给一个版本的过渡期，同时**从第一天就 Warn** ——
静默放行会让所有人以为不签也没事。

## 3. 拒绝的方案（记下来避免下轮重议）

- **`cryptography` / `PyNaCl`**：破 `src/jikuai/` 零运行时依赖硬约束。这条约束
  的价值在嵌入式/Pyodide 场景（v0.18.0 W55 的 PEP 562 解耦就是为它做的），
  为签名破例得不偿失。
- **签名下沉 `tools/`、验签留 `src/`**：验签在 installer 的运行时路径上，让
  installer 依赖 `tools/` 比引 pip 包更糟（`tools/ai-bridge/` 有 numpy 等重依赖）。
- **HMAC + 共享密钥**：对称方案。「谁都能推任意包」的问题变成「谁拿到共享密钥
  都能推任意包」，没解决问题只是换了个说法。远程注册表场景下密钥必然要分发给
  所有安装方，等于公开。
- **RSA**：密钥/签名体积大（2048 位密钥 ≈ 294 字节 DER，签名 256 字节），纯
  Python 实现的模幂比 Ed25519 的标量乘更慢，且安全参数选择（padding、
  e 的取值、密钥长度）比 Ed25519 多得多的坑。Ed25519 参数是固定的，少一整类错误。
- **GPG / `ssh-keygen` 外部命令**：不引 pip 依赖，但引入**外部二进制依赖** ——
  用户机器上没装 gpg 就装不了包，而且要处理 gpg 的 keyring 状态、版本差异、
  输出解析。比自实现 200 行更不可控。
- **PKI / 证书链**：见 §2.5，当前规模不需要，重开条件见 §6。

## 4. 影响面

**Breaking**：
- 索引分片条目新增 `签名者` / `签名` 字段（可选，老条目无此字段 → 走未签名路径）
- 注册表根新增 `密钥/` 目录
- `jk 包` 新增 `密钥` 子命令族（G17 逼同步文档）
- `registry.publish` 的 `PublishReport.checksum` 与索引 `校验和` 字段格式从
  裸 hex 变为 `sha256:<hex>`（W73 已落地，`test_pkg_block_e2e` 断言已更新）

**不动**：
- 块元数据格式（延续 ADR-32 的「最小桥接」精神）
- `包.json` manifest 字段
- `包.锁` 格式（校验和条目本来就是 `sha256:` 前缀）
- 安装落点（`极快_包/<包名>/`）与 `.块根.json` 索引

## 5. 已知局限（明确写下，别当成没写）

- **非常量时间实现**。Python 大整数运算无常量时间保证，理论存在时序侧信道。
  威胁模型：私钥只在**本机开发者手里**签自己的包；攻击者要测时序得先能在同机
  执行代码，那时私钥文件本身已经暴露。**验签路径读的全是公开数据，时序无秘密
  可泄。**
- **无侧信道加固**：不做 blinding、不清零中间变量。同上威胁模型不要求。
- **无密钥吊销机制**。私钥泄露只能换别名重发 + 手工从注册表 `密钥/` 删旧公钥。
  吊销列表是 PKI 的一部分，见 §6 重开条件。
- **TOFU 的首次信任是脆弱的**。第一次拉公钥时如果已被中间人劫持，后续所有校验
  都在验一个假身份。M20 上 HTTPS 后由 TLS 兜首次连接；纯本地/内网文件系统
  注册表场景下这个风险由文件系统权限兜。
- **签名不覆盖注册表索引本体**。攻击者若能写注册表根，可以删条目或改 `依赖`
  字段（不改 `校验和`/`签名` 的话包内容仍验得过，但依赖解析被污染）。索引级
  签名留 M20 与 token 鉴权一起做——写权限本来就该由鉴权拦。

---

## 6. 重开条件

以下任一条成立时，本 ADR 的对应决策应重新评审：

- **签名者数量超过约 50**，或出现「组织内多人共用一个签名身份」的诉求 →
  重议 §2.5 的 TOFU + 白名单，考虑 PKI / 证书链 / 吊销列表
- **实测签名或验签单次耗时超过 200ms** → 重议 §2.1，考虑「可选加速后端」
  （检测到 `cryptography` 就用、没有就落回纯 Python 实现）；注意这不破零依赖
  约束，因为纯 Python 实现始终在
- **出现「包内容极大」场景**（单包 > 1GB）使 `compute_checksum` 本身成为瓶颈 →
  重议 §2.2 的签名对象（可能需要 Merkle 树式增量校验）
- **需要签名注册表索引本体** → 与 M20 的 token 鉴权合并设计，见 §5 末条
