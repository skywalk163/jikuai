# ADR-35：远程发布协议（POST /publish）

- 状态：**已接受**（v0.21.0 M23 · W89）
- 日期：2026-08-13
- 阶段：v0.21.0 · M23（W89-W93）
- 关联：`docs/ADR-34-远程HTTP注册表.md` §2.1/§2.6/§2.7、`docs/ADR-33-包签名.md`、`docs/安全审计-v0.21.md`、`docs/路线图-v0.21.md` §三 M23、`src/jikuai/pkg/backend.py`、`src/jikuai/pkg/registry.py`、`tools/registry-server/`
- 前置事实：M19 包签名已实施（Ed25519 + TOFU + 装包端三道检查）；M20 远程**读**端已实施（`HttpBackend` 只读 + tar.gz 安全解压 + Bearer token）；M22 安全审计已留档并上门禁 G19

---

## 1. 背景与问题

v0.20.0 让包能被可信地**读下来**，但**推上去**仍是本地动作：`jk 包 发布` 只写
`JIKUAI_REGISTRY` 指向的本地目录，`HttpBackend.write_*` 一律抛
`UnsupportedOperation`。第三方作者要发包，必须拿到注册表机器的文件系统写权限
——这在任何多人协作场景下都不成立，生态只能停在「官方自己往里塞」。

写端是攻击面的量级跃迁。读端最坏是读到坏包（签名已兜住），写端最坏是
**任意人往注册表推任意内容、覆盖他人已发布的包、撑爆磁盘**。所以本 ADR 的
主体不是「怎么传字节」，而是**授权、覆盖、配额、审计**这四件事。

ADR-34 §2.6 留白了五件事，本 ADR 逐条定案：报文格式、写路径鉴权与授权、
覆盖策略、配额、审计日志。

---

## 2. 决策

### 2.1 范围：单节点、单管理员、文件系统存储

服务端只做一件事：**把一个已签名的包快照，经授权检查后写进本地注册表目录，
并保持索引一致**。

明确**不做**（要做须另立 ADR 推翻）：

- 集群 / 多副本 / 数据库存储
- Web 管理界面 / 用户自助注册流程 / 找回 token
- 多租户隔离（同一进程服务多个互不可见的注册表）
- 撤回（`unpublish`）的远程接口 —— 已发布版本被撤回会让下游锁文件失效
  （left-pad 教训，`registry.unpublish` 的 docstring 已记）。远程只增不减，
  要删只能上机器手工操作。

**为什么这样切**：远程发布的价值在「作者不需要机器权限」，不在「做一个包仓库
产品」。单节点 + 文件系统正好复用 M20 的读端结论——注册表根目录本身就是
静态可托管的，服务端只是给它加了一个受控的写入口。同一个进程同时提供
`GET`（读，等价静态托管）与 `POST /publish`（写），运维只需跑一个东西。

### 2.2 传输：一次 `POST /publish`，JSON 报文 + base64 归档

**端点**：`POST <base>/publish`（ASCII 路径，非中文）。

> 这是本项目里少见的「不用中文」的地方，理由是它是**运维面**而非用户面：
> nginx 反向代理配置、curl 排障、访问日志、告警规则都要写这个字符串，
> percent 编码的中文路径（`/%E5%8F%91%E5%B8%83`）在这些场景里纯是负担。
> 注册表内的**文件**路径仍是中文（`索引.json` / `分类/` / `密钥/` / `包/`），
> 那些是数据布局，由客户端 percent 编码，人不直接读。

**报文**：`Content-Type: application/json`，UTF-8，字段全中文（与索引条目同风格）：

```json
{
  "协议": 1,
  "名称": "甲包",
  "版本": "1.0.0",
  "分类": "通用",
  "校验和": "sha256:<64 位小写 hex>",
  "签名者": "甲",
  "签名": "<base64 的 64 字节 Ed25519 签名>",
  "条目": { "名称": "甲包", "版本": "1.0.0", "描述": "...", "入口": "主.jk",
            "分类": "通用", "校验和": "sha256:...", "文件数": 3,
            "依赖": {}, "极快版本": ">=0.21.0", "快照": "包/甲包/1.0.0" },
  "归档": "<base64 的 tar.gz 字节>"
}
```

**为什么 base64 塞进 JSON，而不是 multipart 或裸二进制 + 头部元数据**：

- `multipart/form-data` 在标准库里没有可用的服务端解析器（`cgi` 模块 3.13 已移除，
  手写 multipart 分帧是纯粹的自找麻烦）。
- 裸二进制 body + 元数据放 HTTP 头：头只能是 latin-1，中文描述/分类要再编码一层，
  且元数据与内容分离，校验时要分两处取值。
- base64 的代价是 4/3 体积 + 一次内存拷贝。包是**源码**（`.jk`/`.py`/`.json`），
  正常量级几十到几百 KB；配额默认卡 16 MiB（§2.5），这个代价可接受。
- 收益：**整个请求是一个原子单元**，服务端可以在完全不碰磁盘的前提下跑完
  鉴权 → 授权 → 验签 → 校验和复核 → 覆盖检查，任何一步失败都不留半个包。

**响应**：JSON，`{"结果": "已发布", "名称": ..., "版本": ..., "校验和": ...}`；
失败为 `{"错误": "<中文原因>"}` + 对应状态码（§2.7）。

**协议版本**：报文顶层 `协议: 1`。服务端只认自己支持的版本，不认就 400 报清
「服务端支持协议 N，客户端发来 M，请升级其中一端」——版本协商靠显式报错，
不靠猜字段。

### 2.3 授权：token ↔ 包名归属绑定（不是「有 token 即可写」）

**这是本 ADR 最要紧的一条。**「有 token 就能写任意包」等于没有授权：一个作者
的 token 泄露 = 整个注册表可被改写。

服务端配置 `授权.json`（**不进版本库**，与私钥/凭证同一隔离原则）：

```json
{
  "协议": 1,
  "令牌": {
    "<token 的 sha256 hex>": {
      "签名者": "甲",
      "公钥": "<base64 的 32 字节 Ed25519 公钥>",
      "可发布": ["甲包", "甲-*"],
      "每小时次数": 20,
      "单包字节": 16777216
    }
  }
}
```

四条规则：

1. **token 只存哈希**。配置文件泄露不等于拿到可用 token。比对走
   `hmac.compare_digest`（定长比较，不给计时侧信道）。
2. **`可发布` 是白名单**，支持精确包名与 `前缀-*` 通配（一个作者的系列包不必
   逐个登记）。**没有「全部」通配** —— 想给某个 token 全权，只能把所有包名列出来，
   让「授予全权」这个动作在配置里显形。无匹配即拒（默认拒绝）。
3. **公钥由管理员登记在服务端**，报文里**不带**公钥。服务端用登记的公钥验签。
   若允许客户端自带公钥，攻击者就能自签自证——那层签名只是装饰。
   登记是一次性的带外动作（作者 `jk 包 密钥 导出 甲` 把 44 字符 base64 交给管理员）。
4. **签名者必须与 token 绑定的签名者一致**。报文 `签名者` 与 `授权.json` 里该
   token 的 `签名者` 不等 → 拒。防止 A 的 token 推一个署名 B 的包。

### 2.4 覆盖：远程**一律拒**，没有开关

已发布的 `名称@版本` 再次推送 → `409`，且**服务端不提供任何放行开关**。

> **这是对路线图 §三 M23「与本地 `--允许覆盖` 对齐」的有意偏离。**
> 本地覆盖影响的是自己机器上的注册表，作者自负;远程覆盖影响**所有下游**——
> 已经把 `包.锁` 里 `sha256:` 钉住的项目，会在下次装包时校验和不匹配而失败，
> 且失败点在使用者那边，作者甚至不知道自己弄坏了谁。
> 「持有 token 即可覆盖」等价于「持有 token 即可破坏下游」，这不是发布权限
> 该包含的能力。要重发必须提版本号（语义化版本本就该这么用）；确实要删
> 只能上机器手工操作 + 承担后果。
>
> 代价：手滑发错内容的版本号会被永久占用。这个代价远小于下游随机炸掉。

### 2.5 配额：三层，默认保守

| 限额 | 默认 | 覆盖方式 | 为什么 |
|---|---|---|---|
| 单请求体字节 | 32 MiB | `JIKUAI_REGISTRY_SERVER_MAX_BODY` | base64 后的报文上限，先于解析生效——超限直接 `413` 断连，不进内存 |
| 单包归档字节 | 16 MiB | `授权.json` 的 `单包字节`（按 token） | 解出的 tar.gz 上限。源码包正常几百 KB，16 MiB 已是极宽 |
| 每 token 每小时发布次数 | 20 | `授权.json` 的 `每小时次数` | 防刷。正常作者一小时发 20 个版本已属异常 |

解压侧的限额**不重复定义**：服务端复用 `sources._safe_extract_targz`（W86 已带
成员数 / 单成员 / 合计三条上限 + 路径安全）。写端与读端用同一把解压尺，
避免出现「服务端能收、客户端装不了」的口径不一致。

频次计数是**进程内滑动窗口**，重启清零（§4 已知局限）。单节点单管理员场景下
这个精度够用；要持久化配额就意味着要引入状态存储，与 §2.1 的范围冲突。

### 2.6 审计日志：append-only JSONL，**失败也记**

`审计.jsonl`（默认落在注册表根的同级目录，`--审计` 可改），一行一条：

```json
{"时间":"2026-08-13T06:12:44Z","远端":"203.0.113.7","签名者":"甲","名称":"甲包",
 "版本":"1.0.0","结果":"已发布","字节":40960}
{"时间":"2026-08-13T06:13:02Z","远端":"203.0.113.9","签名者":"乙","名称":"甲包",
 "版本":"1.0.1","结果":"拒绝","原因":"越权：token 无权发布 甲包","字节":40960}
```

- **拒绝也写**。审计日志的价值主要在失败侧：连续的越权尝试是入侵信号，只记
  成功等于把最有用的部分丢掉。
- **不记 token**（明文或哈希都不记）。日志的读者是运维，不该从日志里拿到凭证材料；
  `签名者` 已足够定位是谁。
- 逐条 `open(..., 'a')` + `write` + `flush`，不缓存。崩溃时丢的是最后一条，
  而不是一整段。

### 2.7 状态码与错误

| 码 | 场景 | 客户端提示 |
|---|---|---|
| 200 | 发布成功 | 打印名称@版本 + 校验和 |
| 400 | 报文不合法 / 协议版本不认 / 校验和不匹配 / 归档不安全 | 原因原样透出（中文） |
| 401 | 无 token 或 token 不认识 | 提示配 `JIKUAI_REGISTRY_TOKEN` 或 `~/.jikuai/凭证.json` |
| 403 | token 有效但越权（包名不在 `可发布`；签名者不匹配）；未签名 | 中文说明差在哪 |
| 409 | 版本已存在 | 提示提升版本号（并说明远程无覆盖开关） |
| 413 | 请求体超上限 | 报出上限数值 |
| 429 | 触发频次配额 | 报出窗口与上限 |
| 500 | 服务端自身错误 | **不回显内部细节**（栈/路径），只留日志 |

错误信息里**绝不回显服务端文件系统路径**——那是给攻击者的地形图。本地
`LocalBackend` 的报错带路径是合理的（用户自己的机器），跨网就不是。

### 2.8 客户端：`publish_package()`，而**不是**让 `write_text` 能写

`HttpBackend` 新增一个方法：

```python
def publish_package(self, payload: dict) -> dict:
    """POST /publish。返回服务端 JSON 响应。"""
```

`write_text` / `write_bytes` / `remove` **保持抛 `UnsupportedOperation`**。

> **这是对路线图 §三 M23「`HttpBackend` 写操作实装」字面表述的偏离。**
> 逐文件可写意味着客户端要自己「下索引 → 改 → 上传索引」，两个作者同时发布
> 就会互相覆盖掉对方的索引条目（读-改-写竞态），而客户端之间**没有任何**
> 协调手段。索引一致性只能由**唯一写者**保证，那个写者必须在服务端。
> 所以远程写的粒度是「发布一个包」这个业务动作，不是「写一个文件」这个存储动作。
> ADR-34 §2.6 承诺的「不动上层 `publish()` 调用面」仍然成立——变的是
> backend 上多一个方法，`publish()` 里加一个远程分支。

`registry.publish()` 拆成两段：

- `_build_publish_payload(manifest, ...)`：做快照、算校验和、签名 —— 本地/远程共用
- 落盘段：本地走原路径；远程改为 `backend.publish_package(payload)`

**客户端强制签名**：远程发布未提供 `--签名` 直接拒，**不发请求**。比读侧的
「未签名过渡告警」更严，理由是写端**没有存量兼容负担**——注册表里的存量未签名包
是历史，而新推上去的包没有任何理由不签。双端都拒（客户端拒是体验，服务端拒是安全）。

## 3. CLI 表面

不新增子命令。`jk 包 发布` 的目标由 `JIKUAI_REGISTRY` 决定：

```bash
# 本地（不变）
jk 包 发布 --签名 甲 --确认

# 远程
set JIKUAI_REGISTRY=https://reg.example.com
set JIKUAI_REGISTRY_TOKEN=...
jk 包 发布 --签名 甲 --确认
```

`--演练` 对远程同样有效：本地做完快照/校验和/签名后**不发请求**，只打印将要
推送的内容。发布是不可逆动作，远程更是——默认演练的纪律不变。

服务端启动：

```bash
python tools/registry-server/server.py --注册表 D:\注册表 --授权 D:\授权.json \
    --监听 127.0.0.1 --端口 8765
```

## 4. 已知局限

- **配额计数不持久**：进程重启后频次窗口清零。持久化需要状态存储，与 §2.1 冲突。
- **无 TLS 终结**：服务端只说 HTTP，TLS 由前置的 nginx/Caddy 负责。自己实现
  TLS 终结要碰证书管理与协议细节，标准库 `ssl` 能做但运维上没人应该这么部署。
  客户端默认拒明文 `http://`（`JIKUAI_REGISTRY_INSECURE=1` 才放行，M20 已定），
  这条约束在写端**同样**生效——推包比读包更不该走明文。
- **单进程串行写**：索引是全局单点，写路径用一把 `threading.Lock` 串行化。
  吞吐上限就是「一次发布」的耗时。单节点场景下发布是低频动作，不优化。
- **token 轮换靠手工**：改 `授权.json` + 重启（或发 SIGHUP —— 本轮不做，
  重启一个单进程服务的成本低于实现热重载的成本）。
- **没有服务端侧的包内容审查**：服务端验签名、验校验和、验解压安全，**不看
  代码干什么**。恶意但签名正确的包能发上去——这与 pypi/npm 同构，靠的是
  签名的**可追责性**而非内容审查。装包端的 pybridge 边界（ADR-21）才是执行期防线。

## 5. 被拒的方案

- **给 `HttpBackend.write_text` 填实现，客户端自己拼索引** —— 见 §2.8：多客户端
  并发发布会撕裂索引，且客户端无法协调。
- **`multipart/form-data` 上传** —— 标准库无服务端解析器（`cgi` 已移除），
  手写分帧是新增攻击面换零收益。
- **引 FastAPI / Flask 写服务端** —— 零依赖是硬约束（同 W31 拒绝 Web 引框架）。
  `http.server` 支撑单节点静态托管 + 一个 POST 端点完全够。
- **服务端信任报文里自带的公钥** —— 自签自证，签名沦为装饰。见 §2.3 第 3 条。
- **允许远程覆盖（带 `--允许覆盖`）** —— 见 §2.4，等价于把「破坏下游」纳入
  发布权限。
- **服务端做包内容静态扫描** —— 无法定义「恶意」的边界，且会给出错误的安全感。
  签名提供可追责性，执行期边界提供隔离，这两者才是防线。
