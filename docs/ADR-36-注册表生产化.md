# ADR-36：注册表生产化（TLS 契约 / 单写者 / 授权热重载 / 公钥轮换）

- 状态：**已接受**（v0.22.0 M26 · W100）
- 日期：2026-08-13
- 阶段：v0.22.0 · M26（W100-W102）
- 关联：`docs/ADR-35-远程发布协议.md` §4、`docs/ADR-34-远程HTTP注册表.md` §2.1、`docs/ADR-33-包签名.md` §2.5、`docs/路线图-v0.22.md` §三 M26、`tools/registry-server/`、`src/jikuai/pkg/trust.py`
- 前置事实：M23 远程发布已实施（`POST /publish` + token↔签名者↔包名三重绑定 + 三层配额 + append-only 审计）；服务端是 `ThreadingHTTPServer` 单进程，写路径由一把进程内 `threading.Lock` 串行化；`授权.json` 只在启动时加载一次；TOFU 信任库每个签名者别名只能 pin **一把**公钥

---

## 1. 背景与问题

ADR-35 §4 列了五条已知局限。其中四条是「能跑但不能放心交给别人运维」的那一类，
本 ADR 逐条定案；第五条（服务端不做包内容审查）是**刻意**的设计，不动。

要还的四笔账，按「运维踩坑的概率」排序：

1. **无 TLS 终结**。今天服务端只在启动横幅里打一行「无 TLS，请前置 nginx/Caddy」。
   这是一句**建议**，不是**约束**——运维把 `--监听 0.0.0.0` 一敲，token 就在公网上
   明文飞。客户端侧早有 `JIKUAI_REGISTRY_INSECURE` 拒明文，服务端侧一点防护都没有。
2. **`授权.json` 改动要重启**。撤销一个泄露的 token 需要停服务。ADR-35 当时的理由是
   「重启一个单进程服务的成本低于实现热重载的成本」——**这句话在单人自用时成立，
   在「给别人运维」时不成立**：撤销凭证是应急动作，要求停服务等于要求犹豫。
3. **多进程写没有裁决**。写锁是 `threading.Lock`，只在进程内有效。今天没人跑多
   worker，但也**没有任何东西阻止**运维起两个进程指向同一个注册表根——两个进程
   各自持有一把互不相干的锁，并发发布会撕裂索引。这是「没写文档 = 埋雷」。
4. **公钥轮换会集体炸**。TOFU pin 是 `<信任根>/<别名>.公钥` 单文件单公钥。签名者
   换密钥后，注册表侧公钥与本地 pin 不一致，`trust.resolve_and_pin` 抛
   `TrustError` 拒装——**不只是新包装不上，该签名者的所有老包也一起装不上**，
   因为验签走的是同一条路径。今天的自救方式是「手工删掉 pin 文件」，
   而那等于把 TOFU 保护整个关掉一次。

**本 ADR 仍守 ADR-35 §2.1 的范围**：单节点、单管理员、文件系统存储、零第三方依赖。
生产化指的是「误配置会被挡住、应急操作不用停服务、密钥能换」，
**不是**做集群、不是做管理界面。

---

## 2. 决策

### 2.1 TLS：自身永不做 TLS，但把「必须在反代后」从建议升级为可强制的约束

**不实现 TLS 终结。** 标准库 `ssl` 能做，但证书签发、续期、协议版本与套件选择、
OCSP —— 这些是反向代理的本职，自己做一份必然是更差的一份。这条与 W31
「Web 服务不引框架」同源：不做不等于让用户裸奔，而是**把边界讲清并给样例**。

新增两层防护，都在服务端侧：

**(a) `--要求TLS转发` 开关（默认关）**。开启后，`POST /publish` 必须携带
`X-Forwarded-Proto: https`，否则 **403** 并给中文理由。这把「我以为挡在反代后了」
变成一次立刻可见的失败，而不是一个静默的明文通道。

> **为什么这个头可信**：它本身完全可伪造——但只在**服务端绑定回环**时才需要可信。
> 默认 `--监听 127.0.0.1` 下，能连上服务端的只有本机进程（即反代本身），
> 头是谁写的没有歧义。所以本开关的语义是「我确认自己只被反代访问」，
> **不是**「我能鉴别请求是否走了 TLS」。文档必须这么写，不能给错误的安全感。

**(b) 危险绑定的启动横幅告警**。`--监听` 不是回环地址（`127.0.0.1` / `::1` /
`localhost`）且**未**开 `--要求TLS转发` 时，启动横幅打一段醒目的多行警告：
token 会明文传输、任何能路由到本机的人都能试探写端点。**只告警不拒绝启动**——
内网可信段直连是合理场景，硬拒会逼用户去改代码，那比告警更糟。

部署契约（写进 `docs/远程注册表部署.md`，W102）：反代终结 TLS → 转发到
`127.0.0.1:8765` → 反代负责设 `X-Forwarded-Proto`。附 nginx 与 Caddy 各一份
样例、一份 systemd unit。

### 2.2 多进程写：裁决为**单写者**，并用启动期锁文件把约束变成硬的

**不做跨进程文件锁，不支持多 worker。** 裁决理由：

- 跨平台文件锁在零依赖下要两套实现（POSIX `fcntl.flock` / Windows
  `msvcrt.locking`），加上陈旧锁回收、锁升级、NFS 上语义不保证——
  这是一整块新的正确性负担。
- 换来的收益是**零**。索引是全局单点，写路径本来就必须串行；多 worker 只能提升
  **读**吞吐，而读端是静态文件，本该由反代/CDN 直接吐，根本不该经过这个进程。
- 发布是低频动作。为它做并发写是拿正确性换一个不存在的指标。

但「不支持」必须是**可执行的**约束，不能只是文档里一句话。因此：

**启动时抢一把锁文件**：`<注册表根>/.发布锁`。用
`os.open(path, O_CREAT | O_EXCL | O_WRONLY)` 原子创建，内容写当前 pid 与启动时刻；
正常退出（含 `KeyboardInterrupt` / `SIGTERM`）在 `finally` 里删除。
已存在则**拒绝启动**并给出中文理由 + 锁文件里记的 pid + 处置建议。

崩溃留下陈旧锁怎么办：提供 `--强制解锁`，删掉锁文件后继续启动。
**刻意不做「自动探测持锁进程是否还活着」**——`os.kill(pid, 0)` 在 Windows 上不可用，
而 pid 会被系统复用，自动判活在跨平台下必然要么误杀要么误放。让人看一眼再敲一个
参数，比一个有时猜错的启发式好。

> 这条也顺手关掉了另一个坑：两个管理员同时手工起服务指向同一个注册表根，
> 第二个会立刻失败而不是安静地并行写。

### 2.3 授权热重载：每请求 stat + 变更即重载，加载失败保留旧配置

**方式选定 `mtime` 轮询，不用 `SIGHUP`。** `signal.SIGHUP` 在 Windows 上不存在，
而本项目的门禁与 CI 是四平台（ubuntu/windows/macos/freebsd），跨平台是硬需求。
`SIGHUP` 会变成「只有类 Unix 能热重载」的半成品。

**具体机制**：在认证之前，`stat` 一次 `授权.json`，比对
`(st_mtime_ns, st_size)`。变了就重新 `load_auth_config` 并原子替换。
每请求一次 `stat` 的开销对一个低频写端点可以忽略；不额外引入线程或轮询间隔参数
（也就不新增环境变量，不动 G18）。

三条必须守住的性质：

1. **加载失败保留旧配置**。管理员把 JSON 写坏了、正写到一半被读到、文件被临时移走
   —— 这些都不能让服务瘫。捕获异常 → 记日志 → 继续用内存里的旧配置。
   **反过来做（失败即全拒）会让一次手抖变成一次停服**。
2. **频次窗口按 token 哈希延续**。重载时，对**仍然存在**的 token 条目，
   把旧条目的滑动窗口时间戳搬到新条目上。否则「改一下 `授权.json` 的注释」
   就能把配额清零，配额形同虚设。被删掉的 token 连窗口一起丢，正确。
3. **撤销必须立刻生效**。这是本条的主要动机：删掉一个 token 条目后，
   下一个请求就 401。W101 必须有这条的反例测试。

### 2.4 公钥轮换：TOFU pin 改为「一别名多公钥」，且新增公钥只能本地显式授权

这是四条里唯一需要动**数据格式**的。

**pin 文件格式**：从「单行 base64」改为「**每行一把 base64 公钥**」。
第一行是当前主公钥，后续行是仍然受信的历史公钥。

> **向后兼容是零成本的**：既有的单行 pin 文件本身就是一个合法的单行多行文件。
> 不需要迁移脚本，不需要格式版本号。这是选择「多行」而不是「换成 JSON 数组」
> 的全部理由——JSON 化会让所有既有 pin 文件失效。

**验签规则**：签名用 pin 文件里**任意一把**公钥验过即通过。
于是「老包用旧公钥、新包用新公钥」自然成立，轮换不再让老包集体失效。

**新增公钥的授权路径 —— 这是本条的安全核心**：

**绝不能**让「注册表侧出现了一把新公钥」自动并入本地 pin。那样一来，
攻破注册表的人只要往 `密钥/<别名>.公钥` 追加自己的公钥就能签发被信任的包，
TOFU 的全部价值归零。**自动路径只保留 TOFU 原语义：首次见到某别名时 pin 它。**

已 pin 的别名遇到注册表侧公钥不在 pin 列表内时，仍然**拒装**，但错误信息从
今天的「删掉 pin 文件再重装」（等于关掉一次 TOFU）改为指向一个精确的显式动作：

```
jk 包 密钥 信任 <别名> <新公钥base64>
```

新增这个子命令，语义是「我确认这把公钥属于该签名者，追加到信任列表」。
追加而非替换 —— 旧公钥留着，老包照样能装。

配套的 `jk 包 密钥 撤信 <别名> <公钥base64>`：签名者密钥**泄露**时，
要能把那把公钥从信任列表里摘掉（这时候「保留历史公钥」正是要清除的东西）。
轮换与泄露是两个不同的场景，不能只给追加。

**注册表侧**（`密钥/<别名>.公钥`）同步改为多行格式，服务端在落盘时**追加**
新公钥而不是 409 拒绝——但仅当报文签名者的公钥与 `授权.json` 里登记的一致时。
**信任源仍然是 `授权.json`**（管理员显式编辑），不是报文，也不是既有文件。
服务端只是把管理员已经授权的事实分发出去。

**「过渡窗口」的裁决 —— 与路线图原始措辞的偏离**：路线图 §M26 写的是
「多公钥并存 **+ 过渡窗口**」。**我砍掉了时间窗口**。理由：基于时间的过期需要
签名时刻、需要客户端与服务端时钟大致同步、需要过期清理的触发点，而这三样在
「离线也要能装包」的前提下都不可靠——时钟往回拨就能让已撤销的公钥复活。
**多公钥并存本身就是过渡窗口**，窗口的开与关由 `密钥 信任` / `密钥 撤信`
两个显式动作界定，而不是由挂钟界定。这比时间窗口更长（可以无限期）也更短
（撤信立刻生效），且没有时钟依赖。

### 2.5 门禁与文档的连带影响

- **G17**（子命令名 ↔ `docs/包管理.md` 命令表同步）：新增 `密钥 信任` /
  `密钥 撤信` 两个子子命令，实装时必须同步命令表，否则门禁红。
- **G18**（`JIKUAI_*` 环境变量 ↔ `docs/包管理.md` 同步）：本 ADR 的新配置项

  单写者约束、锁文件与陈旧锁处置、token 撤销流程、公钥轮换流程。

## 3. 实施切分

- **W101**：授权热重载（§2.3）+ 公钥轮换（§2.4）。两条都是服务端/信任库内部改动，
  不动协议报文格式，风险可控。含反例测试：撤销后下一请求即 401、
  重载不重置配额、坏 JSON 不致瘫、轮换后老包仍验签通过、
  注册表侧擅自追加公钥**不**被自动信任。
- **W102**：TLS 契约（§2.1）+ 单写者锁文件（§2.2）+ `docs/远程注册表部署.md`。

先做 W101 是因为「撤销 token 要停服务」和「换密钥会炸老包」是两个真实的运维阻塞，
而 TLS 与单写者是「防误配置」——重要，但没人被它们卡住过。

## 4. 已知局限

- **配额计数仍不持久**。进程重启后频次窗口清零（ADR-35 §4 原有局限）。
  §2.3 只解决了「重载不清零」，重启清零依旧。持久化要状态存储，与 ADR-35 §2.1 冲突。
- **`X-Forwarded-Proto` 不能鉴别真实 TLS**。见 §2.1 的说明框。它是一个
  「我确认部署形态」的断言，不是一个密码学保证。
- **单写者是硬约束，不是可调参数**。想要更高写吞吐必须另立 ADR 推翻 §2.2，
  那会连带要求索引分片或引入真正的存储层。
- **锁文件的陈旧回收要人介入**。见 §2.2：`--强制解锁` 是刻意的手工步骤。
- **锁在网络文件系统上不保证**（v0.22.0 W102 实施时补登）。`O_CREAT|O_EXCL`
  的原子性依赖文件系统实现，NFS 上不保证。把注册表根放在多机共享的网络盘上
  再指望这把锁挡住另一台机器 —— 挡不住。单节点范围内（同一台机器上的两个
  进程）它是可靠的，那也是 §2.2 要防的场景。
- **公钥轮换要求管理员两边都动**：`授权.json` 换 `公钥` 字段（服务端），
  装包方各自 `密钥 信任`（客户端）。**没有自动分发**，这正是 §2.4 的安全前提。
  代价是签名者换密钥时下游都要动一次手——这个代价是刻意付的。
- **`密钥 撤信` 只影响本机**。没有吊销列表（CRL）分发机制。单管理员单节点下，
  广播撤销要么靠带外通知，要么另立 ADR 做签名的吊销清单。

## 5. 被拒的方案

- **服务端自己做 TLS 终结（标准库 `ssl`）** —— 见 §2.1。证书生命周期管理不是
  一个包注册表该承担的职责，做出来只会是更差的 nginx。
- **`SIGHUP` 触发重载** —— Windows 无此信号，会做成只有一半平台可用的功能（§2.3）。
- **inotify / ReadDirectoryChangesW 监听授权文件** —— 两套平台 API、两条代码路径，
  换来的只是省掉每请求一次 `stat`。低频写端点上这个开销不值得讨论。
- **热重载失败即全拒（fail-closed）** —— 见 §2.3 第 1 条。会把管理员的一次手抖
  放大成一次停服。凭证系统的可用性在这里比「宁可拒绝」更重要，
  因为**旧配置是已经被审查过的配置**，继续用它不引入新风险。
- **跨进程文件锁 + 多 worker** —— 见 §2.2。收益为零的正确性负担。
- **pin 文件改成 JSON（`{"公钥": [...]}`）** —— 会让所有既有单行 pin 文件失效，
  逼出一个迁移脚本。多行纯文本天然向后兼容（§2.4）。
- **注册表侧新公钥自动并入本地 pin** —— 直接摧毁 TOFU。这是本 ADR 里最不能让的
  一条（§2.4）。
- **基于时间的轮换过渡窗口** —— 依赖时钟同步，且时钟回拨可复活已撤销的公钥（§2.4）。
- **pin 里存「公钥指纹」而非公钥本身** —— 省几十字节，换来的是验签时还得回注册表
  取公钥、离线不可用。空间不是这里的约束。
