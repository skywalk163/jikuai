# ADR-37 · AOT 子集破冰 · 第一切片：容器与下标

- **状态**：已接受（§2.1/§2.2/§2.3 主理人 2026-08-14 拍板；§2.5 实测后新增，见 §5）
- **版本**：v0.22.0 · M27 · W103
- **前置**：ADR-19（AOT：`.jk`→C→系统编译器→原生二进制，无独立文件，正文见 `docs/AOT.md`）
- **推翻/收窄**：`docs/BACKLOG.md` §2「AOT 子集边界」中的两行（见 §1）
- **相关**：`docs/路线图-v0.22.md` M27（W103-W106）、§四风险

> 本 ADR 定第一个垂直切片要落地的东西。§2.1/§2.2/§2.3 三处收窄已由主理人

## 1. 背景：现状与这一版要动的边界

AOT 是独立支线（`tools/aot/jikuai_aot/`，无 C 源文件——C 运行时是
`codegen.py:111` 起的字符串常量 `_C_RUNTIME`）。管线是
`.jk → frontend.compile_source → subset_gate.check → codegen.generate_c → cc`，
**无中间 IR，AST 直接生 C**。

当前子集边界由两份白名单硬性守护（`subset_gate.py`）：动词白名单
`SUPPORTED_VERBS`（21 个算术/比较/逻辑/打印），以及不支持节点黑名单
`UNSUPPORTED_NODE_TYPES`（`subset_gate.py:80`）。命中黑名单即报 `JK-E7001`
并**拒绝产出任何文件**（不降级、不静默）。

`docs/BACKLOG.md` §2 把这些标为**设计边界（不是 bug）**，原文相关两行：

> - 成员访问（`对象.字段` / `对象.方法`）—— 依赖运行时对象模型 | 不做（除非另立 ADR）
> - ListLit / DictLit / Index —— 需要堆分配 + 运行时容器（哈希表）| 不做（除非另立 ADR）

本 ADR 就是那个「另立的 ADR」。路线图 W103 的原话是把
「列表字面量 / 字典字面量 / 下标 / `.成员`」四者一起移进子集。**§2 提议对此做一处收窄。**

C 侧值表示是 tagged union（`codegen.py:124`）：

```c
enum JKTag { JK_NIL, JK_INT, JK_FLOAT, JK_STR, JK_BOOL, JK_RMB };
typedef struct { int tag; union { long long i; double d;
    const char *s; int b; long long fen; } v; } JKValue;
```

**没有任何堆容器 / 引用计数 / GC。** 唯一的堆分配是字符串拼接
`jk_concat`（`codegen.py:217`）的 `malloc`，且**故意不 free**（arena 语义，
注释原文：「AOT 子集是直线代码、进程短命，故拼接结果故意不释放」）。
所以本 ADR 的内存决策是**从零起步**，没有既有 refcount/GC 可延续。

## 2. 决策

### 2.1 第一切片 = 列表 + 字典 + 下标，**不含 `.成员`**（收窄路线图）

**决策**：第一切片把 `ListLit`、`DictLit`、`Index` 三个节点移入子集；
`MemberAccess`（`.成员`）**留在子集外，顺延**。

**理由**：路线图把 `.成员` 和容器字面量并列，但读解释器后发现二者**不是同一
难度层**。解释器里 `_member_lookup`（`evaluator.py:1130`）对 `.成员` 的分派是：

- `ModuleValue` → 模块导出名（`evaluator.py:1151`）
- `PyModule` / `PyCallable` → Python 桥（`:1155`）
- `SuperProxy` → `父类.方法`（`:1163`）
- **`JiKuaiInstance` → 类实例的字段/方法**（`:1178`，含私有成员、方法绑定、继承链）
- `dict` → 键取值（`:1203`）
- 任意 Python 对象 → `getattr`（`:1211`）

这里面**只有 `dict.成员` 一条与容器有关**，其余全是**类/模块对象模型**——而对象
模型（类、继承、方法绑定）正是路线图 §四和 BACKLOG 明确**顺延到 v0.23.0** 的东西。
把 `.成员` 纳入第一切片，等于被迫在 AOT 里实现一个最小对象模型，这正是 §四点名的
「AOT 对象模型陷入泥潭」风险。而 `dict.成员` 这条本身冗余：字典取值的正道是
`字典[键]`（`Index`），已在本切片内。

**因此**：`字典[键]` 支持，`字典.键` 不支持（与解释器行为一致——解释器里
`字典.键` 能走通只是 `dict` 分派的副产物，不是推荐写法，AOT 不必复制）。

**替代方案（否决）**：连 `.成员` 一起做。否决理由如上——它把「容器破冰」偷偷
变成「对象模型破冰」，切片不再垂直，且撞上已顺延项。

**代价**：`.成员` 的 AOT 支持要等 v0.23.0 的对象模型 ADR。可接受——第一切片的
目标是证明「堆容器能在 AOT 里跑通」，`.成员` 不服务于这个目标。

### 2.2 内存管理：第一切片沿用 arena / 一次性分配、**不做 refcount 也不做 GC**

**决策**：容器（列表/字典）在堆上分配，**全程不回收**，进程退出时由 OS 回收。
延续 `jk_concat` 现有的 arena 语义。**本切片显式不引入引用计数，也不引入 GC。**

**理由**：路线图把「refcount vs GC」列为本季度最大不确定项，还预留了
「两周定不下来就降级」的退路。读代码后的判断是：**第一切片根本不需要在这两者
间选**。第一切片的容器操作是——字面量构造、下标读、`遍历 于 列表`——都在直线代码
或**有界**循环内，进程短命。真正逼出内存管理的是「循环里反复创建/丢弃容器导致
常驻内存增长」，而那需要先有循环内的容器可变操作，本切片可以不含（见 §2.3）。
在没有真实内存压力的情况下提前选 refcount/GC，是拿一个没有度量支撑的抉择去堵一个
本切片不存在的问题——违背「宁可切片更小也不留半成品」。

**替代方案（否决）**：
- *现在就上引用计数*：要给 `JKValue` 加 refcount 字段、每次赋值/传参 inc/dec、
  处理循环引用（字典可自引用）。循环引用又把简单 refcount 逼向「refcount + 环检测」。
  为一个不回收也能跑对的切片付这个复杂度，不划算。
- *现在就上 GC*：更重，且需要精确定位栈上根，AOT 直线代码里做根扫描是纯负债。

**代价与触发线**：内存只涨不落。**明确的升级触发条件**（写进 §4 局限，任一命中即
在下一版启动内存管理 ADR）：(a) 本切片扩到「循环体内构造容器」；(b) 出现容器可变
操作（`追加`/下标写入已有容器）进入循环；(c) 真实用例跑出 OOM。在此之前不碰。

### 2.3 下标：第一切片支持**读**，下标**写**顺延

**决策**：`列表[i]` / `字典[键]` 求值（读）纳入切片；`列表[i] = 值`（下标写，
解释器见 `evaluator.py:773`）**顺延**。

**理由**：下标写是「就地可变」，一旦进循环就直接踩 §2.2 的内存触发线（b）。读不
改变所有权、不产生新的生命周期问题，是干净的第一步。把写留到内存管理 ADR 一起做，
让「可变 + 回收」作为一个整体决策，而不是先放进可变、再回头补回收。

**代价**：第一切片的列表/字典是「构造后只读」。够证明容器能跑通，且与 §2.2 自洽。

### 2.4 值模型：扩 `JKTag`，容器持 `JKValue`，键限标量

**决策**：
- `JKTag` 增 `JK_LIST`、`JK_DICT` 两个 tag；union 增一个 `void *obj` 指向堆结构。
- 列表 = `{ JKValue *items; long len; long cap; }`；字典 = 开链或开放寻址的
  `{ 键, 值 }` 表，键、值都是 `JKValue`。
- **字典键第一切片限标量**（int/str/bool/rmb），不支持容器作键。相等与哈希只对
  标量定义；容器作键要先定义容器相等语义，顺延。
- 元素/值可以是任意 `JKValue`，**包括嵌套容器**（嵌套只是指针，不牵扯回收——反正
  不回收）。

**理由**：复用既有 tagged union 是最小改动；键限标量避开「容器相等/哈希」这个能
单独吃掉一周的坑，且与「不做 refcount」自洽（容器作键会立刻牵出所有权问题）。

### 2.5 错误文本：**不能抄解释器**——解释器这条路径本身不合 ADR-09，先修解释器

> 本节是草案定稿前**实测后重写**的。草案原话是「AOT 文案必须与解释器逐字一致，
> W104 第一步去抄解释器的真实文案」。**抄不到**：解释器在这条路径上没有中文文案。

**实测**（`_eval_Index`，`evaluator.py:1350`，本机 v0.22.0 主干实跑）：

- `定义赵表=列 10 20 30。打印 赵表[9]。` → RUNTIME · `list index out of range`
- `定义赵d={"甲": 1}。打印 赵d["乙"]。` → RUNTIME · `'乙'`（**只有一个键的 repr，无任何上下文**）
- `定义赵n=5。打印 赵n[0]。` → TYPE · `'int' object is not subscriptable`
- `定义赵表=列 10 20 30。打印 赵表["甲"]。` → RUNTIME · `invalid literal for int() with base 10: '甲'`

根因：`_eval_Index` 只写了 `obj[idx]` / `obj[int(idx)]`（`evaluator.py:1354-1356`），
不做任何检查，让 Python 原生异常冒到 `evaluator.py:720-731` 被统一包装，
`message=str(e)` —— **原文直通**。对比 `_eval_DictLit` 的键可哈希检查
（`evaluator.py:1365`，ADR-23b）是给了中文诊断的，下标路径是漏的。

这与 ADR-09 冲突：`tests/test_v0_4_0_adr09.py:321` 明令诊断文案不得泄漏 Python
实现细节。上面四条里三条是英文 Python 原文，第四条 `'乙'` 连是什么错都没说。

**决策**：
1. **W104 第一步改为「修解释器」**，不是「抄解释器」：给 `_eval_Index` 补中文诊断
   （越界 / 键不存在 / 非容器取下标 / 下标不是整数），文案在那里**一次性定义**。
2. AOT codegen 再对齐这份新文案，`test_v0_*_aot_*.py` 用「同一份源码，解释器与 AOT
   两路执行，断言 stderr 逐字一致」钉死。方向不变，只是基准从「现状」改成「修好后」。
3. 这是**本 ADR 唯一一处扩大 W104 范围**的地方（多动一个解释器函数 + 其回归）。
   不这么做的话，AOT 二进制会照抄 `list index out of range` 这种英文原文，
   等解释器日后合规，两路又要重新对齐一次。

**顺带实测到的两条静默行为**（AOT 必须显式对齐，不得「顺手改对」）：

- **负下标按 Python 语义生效**：`赵表[-1]` → `30`，不报错。AOT 要复制这个语义。
- **小数下标被 `int()` 静默截断**：`赵表[1.7]` → `20`（即下标 1），不报错也不提示。
  这看着像 bug，但它是现状行为；**本 ADR 不改它**（改了就是行为破坏性变更，得单独
  记一条），AOT 复制截断语义，并在 §4 记为已知差异待议。


### 2.6 门禁定位不变：AOT 仍不进 G10-G19 强门禁

**决策**：沿用 `docs/AOT.md:12` 的现状——AOT 不进 G13/G14 强门禁，靠 CI 的
「gcc 可见性 + AOT e2e 零 skip」步骤（`.github/workflows/ci.yml`）承载。本切片
只**扩充** `test_v0_*_aot_*.py` 的容器用例，不新增门禁脚本。

**理由**：AOT 是实验支线，强门禁绑它会让主干发布被实验特性阻塞，与它的定位矛盾。
零 skip 守卫已足够保证「声称支持的就必须在真编译器上真跑过」。

## 3. 验收（W106 收口时逐条核对）

1. 含列表字面量、字典字面量、下标读、`遍历 于 列表` 的 `.jk` 能 AOT 编译成二进制并
   跑出与解释器**逐字一致**的输出。
2. 下标越界 / 字典键不存在 / 对非容器取下标：AOT 二进制的报错文案与解释器逐字一致，
   有「双路执行断言一致」的测试。
3. `.成员`、下标写、容器作字典键、循环体内构造容器 —— 仍报 `JK-E7001` 且**明确指向
   本 ADR 记录的顺延项**（错误 note 里写清「顺延，见 ADR-37 §x」，不让用户以为是 bug）。
4. 四平台 gcc/clang 下 AOT e2e 零 skip。
5. `subset_gate.py` 的 `UNSUPPORTED_NODE_TYPES` 移除 `ListLit`/`DictLit`/`Index`，
   保留 `MemberAccess`；`docs/AOT.md` 与 `docs/BACKLOG.md` §2 同步这一边界变更。

## 4. 局限（第一切片明确不做，逐条有出处）

- **内存只涨不落**（§2.2）。升级触发线：循环内构造容器 / 容器可变操作进循环 /
  真实 OOM。任一命中即启动内存管理 ADR（refcount vs GC 到那时凭度量选）。
- **`.成员` 不支持**（§2.1），等 v0.23.0 对象模型 ADR。
- **下标写不支持**（§2.3），与内存管理 ADR 一起做。
- **字典键限标量**（§2.4），容器作键要先定义容器相等/哈希语义。
- **异常 / Lambda / 类 / 管道仍在子集外**——本 ADR 不碰，沿用 BACKLOG §2，顺延 v0.23.0。
- **AOT 仍不进强门禁**（§2.6），靠 CI 零 skip 守卫。
- **小数下标被静默 `int()` 截断**（§2.5 实测：`赵表[1.7]`→下标 1，不报错）。现状行为，
  本 ADR 不改；AOT 复制截断语义。是否改成报错留待单独议题。
- **下标错误文案先修解释器再对齐**（§2.5）：W104 第一步给 `_eval_Index` 补中文诊断，
  这是本 ADR 唯一扩大 W104 范围之处。

## 5. 裁定记录

**2026-08-14，主理人拍板，三项全同意**：

1. **§2.1 收窄** —— 同意：第一切片不含 `.成员`，只做 `ListLit`/`DictLit`/`Index`。
2. **§2.2 内存** —— 同意：不做 refcount 也不做 GC，沿用 arena 不回收；三条升级触发线记入 §4。
3. **§2.3 下标写顺延** —— 同意：第一切片只做下标读。

**拍板后新增（§2.5，未经上述三问，属实测发现）**：草案原计划「W104 第一步抄解释器
的中文错误文案」，实测发现**解释器在下标路径上没有中文文案**，四条报错里三条是
Python 英文原文，与 ADR-09 冲突。因此 §2.5 改为「先修解释器再对齐」，这是本 ADR
**唯一一处扩大 W104 范围**的改动（多动 `_eval_Index` + 其回归）。若主理人不认这笔
范围扩大，替代方案是 AOT 侧直接发中文文案、接受两路文案不一致并记为已知差异——
但那等于把对齐工作推到解释器合规之后再做一遍。

W104 即按本 ADR 编码。
