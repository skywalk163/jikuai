## 1. 这是什么

把**受支持子集内**的 `.jk` 源码翻译成 C 中间码，再交给系统 C 编译器产出
原生二进制。目标是验证「极快能否脱离 Python 运行时跑起来」，为文心方向⑤
（适配边缘设备、低资源场景）提供可量化的证据。

链路：

```
.jk ──frontend.compile_source──▶ AST ──subset_gate──▶ codegen ──▶ .c ──cc──▶ 原生二进制
                                        │
                                        └── 命中子集外特性 ▶ JK-E7001 + exit 1 + 零产物
```

**术语纪律（交付总监 D-07 第 4 条）**：只有走「C 中间码 + 系统 C 编译器」这条
路才可称「原生二进制编译」。若将来改走 PyInstaller / Nuitka，产物只得称
「**打包分发**」——那类产物内嵌 Python 运行时，与「原生二进制」是两件事。

## 2. 可行性报告

### 2.1 Spike-AOT 实测结论

按 D-07 第 3 条，降级判定时点为 Spike 结束。本机（Windows 10 / Python 3.13.14）
实测结果：

| 探测项 | 命令 | 结果 |
| --- | --- | --- |
| GNU C 编译器 | `gcc --version` | ❌ 未安装（`CommandNotFoundException`） |
| MSVC | `cl` | ❌ 未安装 |
| LLVM | `clang --version` | ❌ 未安装 |
| PyInstaller | `import PyInstaller` | ❌ `ModuleNotFoundError` |
| Nuitka | `import nuitka` | ❌ `ModuleNotFoundError` |

**结论：本机既无 C 编译器，也无打包工具。**

### 2.2 后端选型与理由

**选定：ADR-19 首选路径（`.jk` → C 中间码 → 系统 C 编译器 → 原生二进制），
代码完整交付，二进制产出环节标注「环境受限未验证」。**

为什么**不**触发 D-07 降级到「打包分发」：

1. 降级的备选路径（PyInstaller / Nuitka）在本机同样不可用，降级不解决任何
   问题——只是把「缺 C 编译器」换成「缺 PyInstaller」。
2. 「打包分发」按 D-07 第 4 条不得称原生二进制编译，对方向⑤（低资源边缘
   设备）的证据价值远低于 C 后端：PyInstaller 产物通常 10 MB 量级并内嵌完整
   Python 运行时，恰好是要摆脱的东西。
3. C 后端的**编译期链路可以在无编译器环境下完整验证**：`--emit-c` 走完
   读源 → 前端 → 门禁 → codegen 全程，只差最后一步 `cc` 调用。这一步是
   标准子进程调用，风险可控、可审计。

因此实际交付形态是：**编译期链路 100% 可验证 + 二进制产出环节代码就绪但
未实测**。这符合 D-07 第 2 条「未达成 GA 不算失败，无结论算失败」。

### 2.3 遇到的技术障碍

| 障碍 | 处理 |
| --- | --- |
| 动态类型 → 静态 C | tagged union `JKValue` + 运行时辅助函数分派（见 §4.1） |
| 人民币精度 | `long long` 存**分**；字面量换算在 Python 侧用 `Decimal` 精确完成，杜绝 double 误差（见 §4.2） |
| 中文字符串跨编译器 | 一律输出 UTF-8 逐字节十六进制转义，不依赖编译器源字符集设置 |
| Windows 控制台中文 | 生成的 `main()` 开头调 `SetConsoleOutputCP(65001)` |
| 浮点打印与解释器不一致 | C 的 `%g` 没有 Python `repr` 的最短往返语义；运行时用「精度 1..17 逐级 + `strtod` 往返校验」复现，并对整数值浮点补 `.0` |
| Python `and`/`or` 返回操作数而非布尔 | `jk_and`/`jk_or` 照抄该语义，不退化成 `int` |
| Python `%` / `//` 符号语义与 C 不同 | 实现 floor-mod 与 floor-div，而非 C 的截断语义 |
| 无 C 编译器 | `--emit-c` 让链路在无工具链环境下仍可端到端验证 |

> （后者会解析成 `Call(verb='人民币')`，不在白名单内）。

## 4. 局限清单

### 4.1 动态类型如何降级

极快是动态类型，C 是静态类型。降级方案是 tagged union：

```c
enum JKTag { JK_NIL, JK_INT, JK_FLOAT, JK_STR, JK_BOOL, JK_RMB };
typedef struct {
    int tag;
    union { long long i; double d; const char *s; int b; long long fen; } v;
} JKValue;
```

所有运算走运行时辅助函数（`jk_add` / `jk_lt` / ...），在函数内按 `tag` 分派
——**等于把解释器的动态派发下沉到 C 层**，而不是做静态类型推导。

- 代价：拿不到静态类型特化的性能上限（每次运算都有一次 switch）。
- 收益：语义与解释器一致、实现量小、可审计。
- 后续可加类型推导做单态化特化，属于优化而非语义变更。

### 4.2 人民币精度

- `JK_RMB` 用 `long long` 存**分**（`￥99.90` → `9990`），**绝不用 double 存金额**。
- 字面量的「元 → 分」换算在 **Python 侧用 `Decimal(str(v)).quantize(0.01,
  ROUND_HALF_UP)` 精确完成**，与 `evaluator.RMB._quantize` 同口径，字面量零误差。
- **已知边界**：运行时「金额 × 浮点因子」（如 `价 乘 1.005`）会经 double 中转，
  在半分位平局时可能与解释器的 Decimal 结果差 1 分。解释器侧是十进制精确
  舍入，C 侧是二进制近似后舍入。金额密集运算请用解释器。

### 4.3 其他已知局限

| 项 | 说明 |
| --- | --- |
| 内存 | 字符串拼接结果 `malloc` 后**故意不释放**（arena 语义）。AOT 子集是直线代码、进程短命，可接受；一旦支持循环必须改。 |
| 大整数 | 极快/Python 的整数是任意精度，C 侧是 `long long`（64 位）。超出即静默溢出，**与解释器不一致**。 |
| 浮点打印 | 用「精度逐级 + `strtod` 往返」复现 Python `repr`。极大值（如 `1.2345678901234567e16`）的指数切换阈值可能与 Python 有细微差异。 |
| 前向引用 | 未先 `定义` 就读取变量 → codegen 报错拒绝编译（解释器是运行期报 `JK-E2001`）。行为等价「都不产出结果」，但错误码不同。 |
| 类型错误 | 解释器抛 `JiKuaiError`；AOT 产物是运行时 `fprintf(stderr)` + `exit(1)`。**退出码一致（非 0），消息文本不保证逐字相同**。 |
| 无诊断行号 | 生成的 C 不带 `#line`，运行时错误无法回溯到 `.jk` 行号。 |
| 单文件 | 只编译单个 `.jk` 顶层程序，无链接、无多模块。 |

## 5. 资源占用实测

### 5.1 C 中间码规模（本次实测）

本机无 C 编译器，故**以 C 中间码规模作为间接指标**（D-07 第 2 条要求如实说明）。

| 样例 | `.jk` 源码 | C 总计 | 其中运行时 prelude | 其中 `main` 体 | C 行数 |
| --- | --- | --- | --- | --- | --- |
| `hello`（打印一行） | 31 B | 13 177 B | 12 927 B | 250 B | 383 |
| `calc`（两次赋值 + 两次打印） | 78 B | 13 294 B | 12 927 B | 367 B | 389 |
| `money`（金额乘法） | 65 B | 13 211 B | 12 927 B | 284 B | 388 |

关键读数：**运行时 prelude 固定 12.9 KB，随程序增长的只有 `main` 体**
（本例 250–367 B）。这是纯 C 源码、零外部依赖（只用 libc + libm），
`gcc -std=c11 -O2` 后可执行文件预期在**几十 KB 量级**（未实测，仅据 C 源码
规模与依赖面推断）。

### 5.2 对照基线：解释器 + Python 运行时（本机实测）

| 指标 | 数值 |
| --- | --- |
| Python 版本 | 3.13.14 |
| Python 标准库目录合计 | 71 841 101 B（**68.5 MB**） |
| `jikuai` 主包 `.py` 源码合计 | 259 697 B（254 KB） |
| 执行 `hello.jk` 端到端耗时（5 次中位数） | **276.0 ms**（min 261.1 / max 292.9） |

### 5.3 对照结论

| 维度 | 解释器路线 | AOT（C 后端）路线 |
| --- | --- | --- |
| 分发体积 | 需 Python 运行时，**68.5 MB 量级**标准库 + 254 KB 主包 | 单个静态可执行文件，C 源码 13 KB → 预期几十 KB |
| 启动开销 | **276 ms**（含 Python 解释器启动 + 导入 + 分词/解析/求值） | 无解释器启动、无导入、无分词解析（编译期已完成），预期 **< 5 ms** |
| 运行依赖 | Python 3.10+ | libc + libm |

**对方向⑤（边缘设备 / 低资源场景）的证据价值**：体积从「几十 MB 级运行时」
降到「几十 KB 级单文件」、启动从「百毫秒级」降到「毫秒级」，量级差异明确。
**但 §5.1 的二进制体积与 §5.3 的启动时间均为推断值，本机未实测**——需要在
有 C 编译器的环境补测才能作为结论性数据。

## 7. 用法

```bash
# 只生成 C 中间码，打到标准输出（无需 C 编译器）
python -m jikuai_aot examples/hello.jk --emit-c

# 生成 C 中间码到文件
python -m jikuai_aot examples/hello.jk --emit-c -o build/hello.c

# 编译成原生二进制（需要 gcc / clang / cl）
python -m jikuai_aot examples/hello.jk -o build/hello

# 指定编译器
python -m jikuai_aot examples/hello.jk --cc gcc -o build/hello

# 保留中间 .c 便于排障
python -m jikuai_aot examples/hello.jk --keep-temp -o build/hello
```

前置：`jikuai_aot` 需能 import 到主包 `jikuai`。开发态可

```bash
set PYTHONPATH=<repo>\src;<repo>\tools\aot      # Windows
export PYTHONPATH=<repo>/src:<repo>/tools/aot   # POSIX
```

### 退出码

| 码 | 含义 | 是否有产物 |
| --- | --- | --- |
| 0 | 成功 | 有 |
| 1 | 命中 `JK-E7001`（超出子集）或前端错误或 codegen 拒绝 | **无**（AC-M6-06-03） |
| 2 | 源文件读不到 / 编码不是 UTF-8 | 无 |
| 3 | 未检测到 C 编译器且未加 `--emit-c` | 无 |
| 4 | C 编译器返回非 0 / 产物校验失败 | 无 |

**「禁止静默产出错误产物」的两层保证**：
1. 门禁不通过时，**在创建任何临时目录之前**就返回——物理上不可能有产物；
2. 通过后也先写临时目录、校验非空、再 `os.replace` 原子落盘，避免半成品。

## 8. 下一步建议

按投入产出排序：

### 8.1 优先级 1：控制流（`If` / `While` / `Repeat`）

代价最小、收益最大——`If`/`While` 直接映射 C 的 `if`/`while`，`Repeat` 映射
计数 `for`。需要做的：

1. `subset_gate`：从 `UNSUPPORTED_NODE_TYPES` 移除对应节点。
2. `codegen`：语句发射器从「线性追加」改为**带缩进的嵌套块**，把 `_lines`
   换成树状 emitter（或维护缩进层级）。
3. **变量作用域**：当前的「预扫顶层 + 全部声明在 `main` 顶」模型在有块作用域后
   要改。极快的循环体不引入新作用域（`定义` 是就地赋值），所以仍可全部提到
   `main` 顶部，但预扫必须递归进块。
4. **内存**：一旦有循环，`jk_concat` 的「不释放」策略立刻变成泄漏。需引入
   引用计数或 arena + 显式回收点。

### 8.2 优先级 2：列表（`ListLit` / `Index` / 列表动词）

需要一个 `JKList` 堆结构 + 长度/容量管理 + 越界检查，并把 `JKValue` 扩一个
`JK_LIST` tag。这是内存管理正式登场的地方，建议与 8.1 的内存改造合并做。

### 8.3 优先级 3：用户函数（`FuncDef` / `FuncCall`）

- 无闭包的顶层函数最简单：直接映射 C 函数，签名统一 `JKValue f(JKValue...)`，
  在 prelude 之后生成前向声明解决互递归。
- **闭包（`Lambda`）需要环境捕获**，代价高一个量级：要么做逃逸分析把捕获变量
  提到堆，要么生成显式 env 结构体 + 函数指针对。建议先只做无捕获函数。

### 8.4 基础设施补齐

- **`#line` 指令**：在生成的 C 里插 `#line N "源文件.jk"`，让 C 编译器报错与
  运行时崩溃能回溯到 `.jk` 行号。低成本、高排障收益。
- **补测二进制**：在装有 gcc 的环境跑 `tests/test_v0_7_0_aot.py::TestBinaryCompile`
  （当前无编译器时 `skip`），把 §5.1 / §5.3 的推断值换成实测值。
- **大整数**：要么接受 64 位截断并在文档写明，要么引入 128 位/bignum。
  当前是**静默溢出**，与解释器不一致，属于该优先修掉的语义漏洞。
