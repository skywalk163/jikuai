## 一、被证实的判断

### 1. 路线 2「槽名字面匹配」在 L3 扩容后依然吃得住

W50-W51 把 L3 从 3 块 20 槽扩到 7 块约 50 槽。W17 起沿用的 ADR-30
（`match_slot_name`：精确 1.0 / 后缀 0.8 / 包含 0.6，同级多命中即歧义留空）
+「同型槽不复用同一变量」在新样本上依然保持 v0.17.0 W43 的两条底线：

- **场景甲（共享按槽名命名）** 100%：只要调用方按块的入参名命名共享常量，
  就一定链得上，无回归。
- **场景乙（无字面线索）** 硬塞 0 次：拿不到就诚实留空 + 拒绝理由。

**结论**：v0.17.0 关于「不引 embedding，只做字面匹配」的路线选择在 3→7
块量级仍成立；下一次需要复审是**引入非中文 L3 块**时（英文 / 混合），
`strip_surname` 的百家姓假设届时可能失效。

### 2. ADR-31 codeAction 关闭是对的

四轮复审（v0.15/v0.16/v0.17/v0.18）零社区诉求 + 14 个诊断码无一满足
「唯一机械修复」+ 唯一候选用例被 `极快.选块` 覆盖，这三条组合起来的证据强度
比「留个坑等未来说不定用得上」高得多。**明确关闭比无限期挂着好** ——
BACKLOG 少一条，每次开发者读到「留待 v0.NN+1 复审」的心智负担就少一点。

### 3. G16 的双向 diff 抓得住真漂移

写完 G16 后回头看 v0.17.0 W47 的手工同步动作 —— 那六个漂了一年半的
W31/W46 端点，如果 G16 早半年上线就是当次 PR 直接红，根本不需要专门排一个
W47 去审计。

写测试时刻意造了 6 类反例（文档漏写、代码漏声明、方法写错、id 占位不同写法、
文档小节缺失、server 缺清单），每类都单跑一次门禁确认真会红 —— 只测正例
的门禁跟没有门禁没区别，这条经验以后每个门禁都要抓紧。

### 4. 集成反馈的 P0/P1 混合优先级判断

quye 集成方的 5 条建议里，P0（arity 一致）是纯正确性 bug、无 opt-in 争议、
一次性修完；P1（示例填参）有语义 tradeoff（链式上下文里覆盖 `赵果i`）所以
落成 opt-in 开关；P2（Hit 带示例 / --with-examples / pkg 解耦）都是「不影响
默认路径」的增强。**按 opt-in 层次分优先级**比按「重要/次要」分更好裁 ——
它自然对应「默认路径动不动」这条硬边界。

## 二、被证伪或修正的判断

### 1. `_token_at` 的字符边界扫描是够用的（v0.15 判断）

W41 时把 `_token_at` 的边界扫描当「一般够用」，留了个「定义X / 赋值X
拿不到符号，绕开：把光标放到使用位置」的边角注记。W56 实际做时才发现，
用户在**定义位置**发起 rename 是最自然的入口，绕开等于劝退。

**修正**：`_token_at` 优先走 lexer，只在 lexer 抛异常时才回落字符边界扫描。
lexer 已经知道 `定义`(KEYWORD) 与 `赵共享`(IDENT) 是两截，直接用就行了 ——
之前是懒于导入 lexer，代价却让「关键字紧贴标识符」这种极常见形态哑火。

### 2. `pkg` 只需要「函数内 import」就能解耦（集成反馈 §4.2 建议）

quye 的原建议是「resolver/installer 的 `from .sources import ...` 改成
函数内 import」。实际做时发现，Python 导入子模块（`from jikuai.pkg.blocks
import ...`）**必先执行父包 `__init__`**，而 `__init__.py` 里的
`from .installer import ...` 就把整条链拉起来了。函数内 import 只解决了
resolver → sources 那一小段，主要瓶颈在父包 `__init__`。

**修正**：改用 PEP 562 `__getattr__` 让父包 `__init__` 惰性加载安装执行层，
既保持 `from jikuai.pkg import install` 的公开 API 不变，又真正把「拉 blocks
时不拉 sources」做到位。这条偏离已在与用户的问答中裁决通过。

### 3. 「多标签实时同步不做」的评估在 v0.18.0 仍不变

W31/W46 两轮判定 loopback-only 本地工具，同机双标签编辑同一份方案极罕见，
W46 的 409 乐观锁已兜数据安全。v0.18.0 无新证据推翻，继续保持「不做」。

## 三、错估的成本 / 优先级

### 1. G16 的实现复杂度低估

初版脚本用「AST 扫方法体收字符串常量」，被 `路径.startswith('/api/')` 的
守卫串 + 错误文案里的 `/api/blocks、/api/能力` 拼接串弄到误报。改用
「在 server.py 加模块级 `_GET路由` / `_PUT路由` / `_DELETE路由` 显式清单，
门禁读这四张字面表」这条**服务端主动声明**路线才干净。**教训**：
反向抽取（从实现里嗅探清单）永远比正向声明（服务端主动挂清单）更脆。

### 2. `synthesize` 的示例参数提取有陷阱

初版用正则 `\((.*?)\)` 从示例 `打印 增税(113, 0.13)。` 里拿参数串 ——
遇到 `打印 顺排(列 1 2 3)。` 会在第一个 `)` 之前停（这是块内部允许再嵌
`(` 的情况）。改用**逐字符括号平衡扫描**才对。写正则是本能反应但错的，
碰到 JiKuai 语法允许嵌套括号的场景要多想一步。
