## 一·补 · 语言能力探路结论（2026-08-11 实测）

W67 早期探路脚本已跑（`分割 / 子串 / 长度 / 【N】索引 / 替换` 逐条验证 +
内置动词表 `keywords.py` 全表核对），结论落地如下，直接决定候选可行性：

- **切分任意分隔符**：✅ 内置动词 `分割 <文本> <分隔符>` 透传 `str.split`，
  `分割 "a;b;c" ";"` → `['a','b','c']`；`文本切分` 块是其薄封装。
  → `Cookie解析` **可做**。
- **子串 / 长度 / 按下标取字符**：✅ `子串 s 0 2`、`长度 s`、`s【0】` 全部可用。
  → 字符串位置类算法可做。
- **替换**：✅ `替换 s 旧 新`（全部替换，非正则）。→ `敏感词遮罩` 的替换动作可做。
- **字符↔码点（ord/chr）**：❌ **内置动词表零命中**，纯 .jk 拿不到「字符的
  数值」，也无法由码点造字符。→ `百分号解码`（`%20`→字节）、`全半角`
  （U+3000→U+0020 区间加减 0xFEE0）**在纯 .jk 内无法实现**，只能走 `蟒:`
  Python 桥（即变成 ADR-16 混合模块，不是纯块）。
- **位运算（与/或/异或/移位）**：❌ 零命中（`且/或/非` 是逻辑非按位）。
  → base64 一类比特算法纯 .jk 同样做不了，维持「不做」。

**对候选的直接影响**：
- 候选 C 的 `百分号解码` 从「中风险待验证」**降级为「纯 .jk 不可做」**——
  本轮**砍掉**，C 定为 2 块（`MIME类型` + `Cookie解析`）。
- 候选 D 的 `全半角` 同理不可做；`敏感词遮罩` 可做但价值一般；
  `中文数字解析` 是纯列表/字符串逻辑、不依赖码点，**可做**。

## 二、候选包（4 个，按风险从低到高）

### 候选 A · `数据统计`（statx）· **推荐必选**

- **需求来源**：浏览器工作台常见数据分析；stdlib 数据领域已有均值/中位数/方差/
  标准差/极值/求和，但没有分位数、众数、前缀和、归一化——这些是数据分析的
  **基础日常**。
- **命名空间**：`数据统计`（= 包名）
- **携带块**：
  - `百分位` · L1 · [数据] · 导出 `分位` · 求第 p 分位数（依赖 `升序`）
  - `众数` · L0 · [数据] · 导出 `众数值` · 出现最多的值（同频取任一）
  - `前缀和` · L0 · [数据] · 导出 `累和表` · 返回累计和列表
  - `归一化` · L1 · [数据] · 导出 `归零一` · min-max 缩放到 [0,1]（依赖 `极值`）
- **可行性**：**低风险**。全是列表算术，语言能力充分，可参照 `求和.jk` /
  `均值.jk` / `极值.jk` 的模式实现。依赖块 `升序` / `极值` 都是 stdlib 现成的，
  W65-W66 已让第三方块能引用内置块（跨命名空间导入）。
- **块数**：4。取下限 3 时可去掉 `归一化`。

### 候选 B · `财务扩展`（finx）· **推荐必选**

- **需求来源**：quye 反馈明写的财务参数示例值表——**这是 quye 用户实际场景
  的直接印证**。stdlib 有 21 个财务块但 `等额本息` 没对应的 `等额本金`（还款
  另一大主流方式），毛利/成本加成也是财务常识缺口。
- **命名空间**：`财务扩展`
- **携带块**：
  - `等额本金` · L1 · [财务] · 导出 `本金还` · 递减还款法（依赖 `保留分`）
  - `毛利率` · L0 · [财务] · 导出 `毛利` · `(售价-成本)/售价`
  - `成本加成` · L0 · [财务] · 导出 `加成价` · `成本 × (1+加成率)`
- **可行性**：**低风险**。纯算术，可参照 `等额本息.jk` / `单利.jk` / `换汇.jk`
  的模式。依赖 stdlib `保留分`（跨命名空间）。
- **块数**：3。

### 候选 C · `网页数据`（webdat）· 中风险

- **需求来源**：quye 是浏览器工作台，处理浏览器数据是核心场景。stdlib 网络
  领域有 URL/查询串/请求组装/响应处理，但没有 Cookie、Base64、MIME 判定——
  在浏览器里这三个几乎每次都用得上。
- **命名空间**：`网页数据`
- **携带块**：
  - `MIME类型` · L0 · [网络] · 导出 `文型` · 按扩展名查表返回 content-type
  - `Cookie解析` · L1 · [网络] · 导出 `饼干表` · `"a=1; b=2"` → 键值列表
    （依赖 stdlib `文本切分`）
  - `百分号解码` · L0 · [网络] · 导出 `百解码` · `%20`→空格 URL decode
- **可行性**：**中风险**。
  - `MIME类型` 是查表，无风险。
  - `Cookie解析` 依赖字符串切分——需要真验证 `文本切分` 能吃分号或空格。
  - `百分号解码` 需要按十六进制两字符组合还原字节——需要**字符↔码点**转换
    能力，目前不确定 极快 有无。这条**做前必须先在 W67 早期开一小时探路脚本
    验证**，走不通就砍掉此块或整包降级为 2 块（`MIME类型` + `Cookie解析`）。

### 候选 D · `中文扩展`（zhx）· 高风险

- **需求来源**：`数字中文` 是阿→中的单向映射，逆向（中→阿）在处理中文表单
  时常需要；全半角、敏感词遮罩都是浏览器输入常遇场景。
- **命名空间**：`中文扩展`
- **携带块**：
  - `全半角` · L0 · [中文] · 导出 `半角化` · 全角字符 → 半角
  - `中文数字解析` · L1 · [中文] · 导出 `解汉数` · "三百二十" → 320
  - `敏感词遮罩` · L1 · [中文] · 导出 `遮敏` · 命中词替换为 `*`（依赖 `文本切分`）
- **可行性**：**高风险**。
  - `全半角` 需要码点级运算（U+3000→U+0020 等区间加减 0xFEE0），依赖字符
    ↔码点的能力，同 `百分号解码` 的疑问。
  - `中文数字解析` 逻辑复杂（万亿单位、"三百零五" 中的零处理），像**中位数**
    级别的复杂度但对字符串。
  - `敏感词遮罩` 需要按位置替换子串，同样依赖字符级操作。
  - **建议只做 `中文数字解析`（作为 `数字中文` 的逆向）**，另外两块推迟到
    v0.20.0 或作为纯 Python 混合模块（ADR-16）实现。**或整包不做**。

## 三、拒绝的候选（记下理由避免下轮重议）

- **`base64编/解码`**：极快是否有位运算操作码未确认，就算能做逻辑也很长；
  quye 若急需可用 Pyodide 侧 `atob/btoa`，不算真的语言层缺口。**不做**。
- **`CSV 解析/生成`**：语法边界复杂（引号、转义、换行），做出来的对不齐 RFC
  4180 反而误导用户。**不做**，等 stdlib 或第三方生态成熟。
- **`社保公积金`**：地域政策差异大（各城市基数上下限、比例都不同），做通用
  版没意义、做具体城市版又不通用。**不做**。
- **`日期区间/工作日跳过`**：`历法` 已有 `挪日` / `日差` / `月长`，工作日跳过
  还要判节假日（真做要外部数据源），超出块生态零依赖底线。**不做**。
