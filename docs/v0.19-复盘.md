## 一、被证实的判断

### 1. 「先做块包能装 + 有内容，HTTP 才有车可跑」的版本切分

路线图起草时定的主轴：v0.19.0 做本地闭环（块包桥接 + 生态内容），v0.20.0 才做
HTTP 分发 + 签名 + 鉴权。三个月做完回头看，这个顺序是对的 ——

W68 造端到端钉板时才发现「检索侧是第三根块根系统」（详见下节）。如果本轮先建
HTTP，这个断层会在跨机分发的时候暴露，排查面从「一个进程内三处读路径」变成
「两台机器 + 网络 + 三处读路径」。**本地闭环是远程分发的调试地基**，不只是
优先级排序问题。

### 2. ADR-32「最小桥接」死守边界是对的

W63 立 ADR 时刻意把边界画得很窄：**块元数据格式一字不动**，包 manifest 只加
一个可选 `块` 字段声明块根，安装器只负责落地 + 写索引。拒绝了「把块和包模型
统一」的方案。

结果 W65-W66 的实现改动面小到超出预期 —— `installer.py` 加一个 `_收集块根` +
`_写块根索引`，`blocks.py` 的 `extra_roots()` 多读一个 JSON 文件，就完事了。
两套模型强行统一的那个版本，光是「块的版本号 vs 包的版本号谁说话」就够吵一周。

**教训**：桥接类设计的成本主要来自「顺手统一一下」的诱惑，而不是桥本身。

### 3. 门禁必造反例，第三次验证

G17（W62）沿用 W55/G16 的规矩造了 3 类反例（文档漏子命令、代码加未文档化
子命令、别名对不上），每类单跑一次确认真会红。三个版本三个门禁（G15/G16/G17）
都这么干，没有一次白花时间 —— 每次都在写反例的过程中发现门禁本体的边界 bug。

这条已经不是「建议」了，是**新门禁的准入条件**。

### 4. G17 上线即证明「文档 ↔ CLI」漂移是系统性问题

W61 清的是七个版本的漂移（BACKLOG 说注册表是占位、`jk 包 发布` 未落地 ——
两条都是错的，v0.11.0 就实现了）。W62 上 G17 之后，这类漂移再也回不来。

**但值得记的是漂移的成因**：不是有人偷懒不改文档，而是「实现完了忘了回头改
BACKLOG，下一轮开发者读 BACKLOG 建立错误前提，在错误前提上排期」。这是**判断
污染**而不是文档洁癖问题 —— 路线图起草时如果不做那次能力盘点，v0.19.0 本来
要花两周「重做注册表基建」。

## 二、被证伪或修正的判断

### 1. 「块根系统有两根」（W64 判断）→ 实际三根

W64 桩验证时数出「发现侧（`scan_blocks`/`extra_roots`）+ 执行侧
（`module_loader._block_root_parents`）」两根，判定桥接接这两处就闭合。

W68 造端到端钉板时发现**检索侧是第三根**：`ai/retrieval.py` 只读
`stdlib/blocks/索引.json`，第三方块根本不进候选池。这意味着 W65-W66 做完
「装得上」之后，第三方块在 AI 桥接侧仍然是死的 —— 用户装了包，`jk 块 选`
搜不到。

**教训**：数「有几处独立读同一类资源」时，别只数**写**路径，**读**路径也算
一根。W64 数的是「谁把块根写进搜索路径」，漏了「谁读块清单」。

### 2. 包名原子性门禁该放在 `validate_package_name`（第一版判断）

W69 第一版把「包名必须能过 lexer 原子性」的检查放进 `validate_package_name`，
对**每个**包都查。实测当场误杀 —— `my-pkg` 是完全合法的包名（`_NAME_RE`
允许 `-`/`_`/拉丁），只是永远做不了命名空间。

修正：挪到 `_validate_block_roots`，**只对声明了 `块` 字段的包**查。

**根因**：包名字符集与点分模块路径段字符集**是两套不兼容的集合**，把它们当
一套是错的。只有携带块的包才会被当命名空间用，所以门禁只该在那一侧收紧。

### 3. 「第三方块会污染内置块检索排序」（W69 风险预案）

WBS 把「命名空间遮蔽」列为风险，预案是打包名命名空间 + W69 专项验证。实测
**风险没兑现**：`scan_blocks` 的去重键是 `(命名空间, 名称)`，内置块命名空间
是空串、第三方是包名，键不同所以两条都活；排序键也是
`(命名空间, 名称)`，空串字典序最小让内置块恒排最前。

`Hit.namespace` 刻意设 `compare=False` —— 命名空间不参与排序/相等语义，
跨命名空间同名块不会被当成「不同分数」影响 order。

**但这个设计有个副作用**，见下节遗留第 2 条。

## 三、估算偏差

- **M16 给了四周（W61-W64），实际前三周够**。文档纠偏（W61）+ G17（W62）
  可并行，ADR-32（W63）因为边界画得窄所以定得快，W64 桩验证一次通过。省下的
  时间流到 W67 造内容。
- **W67 造 3-5 个块包，实际造了 4 包 10 块**。WBS 写「下限 3」，实际做到 4 ——
  这是三个版本以来**第一次估算没有比现实好看**。原因：选题从真实集成方需求
  反推，每个块的「要不要做」判断很快；不像 L3 扩容那样每块都要设计聚合逻辑。
- **W69 溢出**：原计划是「粘合/检索回归 + 命名空间隔离验证」，实际做成了
  「命名空间贯通 + 包名门禁放位」—— 因为 W68 暴露的第三根系统连带出 `_导入行`
  去重键缺命名空间的 bug，修它比跑 bench 更要紧。四套 bench 因此没在 W69 跑
  （块库内置条目未变，理论无回归），**这是本轮唯一没兑现的 DoD**。

## 四、遗留（→ v0.20.0）

1. **checksum 格式不一致**：`registry.publish` 存裸 hex（64 字符无前缀），
   `installer` 往 `包.锁` 写 `sha256:<hex>`。底层同一个
   `sources.compute_checksum`，只有包装层不同。现在只是不好看；M19 做签名要
   跨端比对时会变成真 bug。`test_pkg_block_e2e.py` 有断言钉住现状 + 注释说明。
   → **v0.20.0 W73 前置清账**
2. **`_块元数据表` 键冲突**（`tools/ai-bridge/glue.py`）：按纯 `m.name` 键，
   跨命名空间同名块静默覆盖，且 `scan_blocks` 排序把空命名空间排最前 = **第三方
   覆盖内置**。W69 判定当前 glue-plan 侧无实际用例暴露它，未修。
   注意这与上面「命名空间隔离没被污染」不矛盾 —— `scan_blocks` 层面两条记录
   都在，是 glue 建表时被压成一条。**隔离在数据层生效，在消费层失效。**
   → **v0.20.0 W73 前置清账**
3. **`blocks_cli._块目录` / `_推导出名` 与 `server._校验块存在` 硬编码
   `stdlib/blocks/<领域>/<块>`**：第三方块查不到 → `jk 块 组`/`跑` 与
   Web `/api/组`、`/api/跑` 对第三方块必挂。检索侧通了、粘合侧通了，**校验侧
   没跟上** —— 同一个断层的两侧。
   → **v0.20.0 W73 前置清账**
4. **L3 A 类失配 22 槽（占失配 100%）**：需要路线 2「槽名语义匹配（形参名 +
   需求文本）」。工具的建议从 v0.17 起没变过，是最大的确定性收益点。本轮没碰。
5. **四套 bench 未在 W69 重跑**：内置块条目未变，理论无回归；但没有实测数字
   兑现「双集 + 分任务类型」的报数纪律。→ v0.20.0 M21 全量回归时补。

| 1. 块包桥接闭环（装完能检索到并组/跑） | **部分达成**。装 → 检索 → 粘合通了（端到端钉板在 CI）；但 `jk 块 组` 走 `blocks_cli._校验方案` 的路径对第三方块会挂（遗留 3）。钉板测试走的是 `发布→装→检索→导入并跑`，绕过了 `_校验方案` |

| 3. 文档零漂移（G17 上线） | **达成**。G17 + 3 类反例；BACKLOG/`包管理.md`/`sources.py` docstring 与代码零偏差 |
| 4. 块格式不被破坏（ADR-32 最小桥接） | **达成**。块元数据格式未动；命名空间隔离在数据层生效 |
| 5. 零回归零新依赖 | **达成**。2121 passed；九门全绿；`src/jikuai/` 运行时 pip 依赖仍为 0 |

**六项里五项达成、一项部分达成**。度量 1 的缺口就是遗留 3 —— 它没在 W68 的钉板
里暴露，因为钉板走 API 而不是 CLI 的 `_校验方案` 路径。**这是「端到端测试要走
用户真实入口」这条老规矩的又一次学费**：绕过一层薄壳换来的报错清晰度，代价是
那层薄壳里的 bug 测不出来。
