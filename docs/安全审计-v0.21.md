# 极快 JiKuai · 安全审计报告 · v0.21.0 M22

> 起草：2026-08-13（W85-W86）
> 范围：路径解析 / 依赖获取与解压 / 动态代码执行 三链路
> 前置：v0.20.0（M19 包签名 + M20 HTTP 远程注册表读侧）
> 关联：`docs/路线图-v0.21.md`、`docs/ADR-21-pybridge安全边界.md`、
>       `docs/ADR-33-包签名.md`、`docs/ADR-34-远程HTTP注册表.md`、`docs/BACKLOG.md`
> 关联 ADR：无新立 ADR（本轮全部是补齐 defense-in-depth，未推翻既有边界）

---

## 一、动机

v0.20.0 让包能被**可信地读下来**（M19 签名 + M20 HTTP 只读）。v0.21.0 M23 要开
**远程发布（POST）** —— 攻击面量级跃迁：读端最坏是读到坏包（M19 签名兜住），
写端最坏是任意人往注册表推任意内容、覆盖他人包、撑爆磁盘。所以顺序必须是
**审计先行**（与 v0.20.0 「签名先行、传输在后」同源）。

本审计是**首次贯通式**：单点加固此前有，但从未把三链路一次审干净并留档。

---

## 二、审计方法与范围

**取证方法**：只读代码分析 + 反例测试，不改行为不做静态扫描工具（工具能捕获的
问题多是低质量的），聚焦「外部可控输入 → 关键副作用」的数据流。

**三链路的选择理由**：远程写端一开，三处是攻击面主要交汇 ——
- **路径解析**：决定「写到哪」，任何 path traversal 都在这里
- **依赖获取与解压**：决定「读到什么、能写多少」，tar bomb / zip slip / SSRF 在这里
- **动态代码执行**：决定「谁的代码能跑起来」，pybridge / 侧车 / eval / subprocess 在这里

**未纳入本轮的**：语言解释器自身、AOT 编译器 —— 这两者的输入是**本地文件系统上的
`.jk`**，不是外部网络输入；即使有内存安全或语义 bug，攻击者必须先能写文件才能触发，
比写端注册表低一个量级。留待后续 ADR 再评。

## 三、审计取证摘要（W85）

### 3.1 路径解析

**每个白名单正则原文**：

| 位置 | 正则 | 允许字符 |
|---|---|---|
| `manifest._NAME_RE` | `^[\u4e00-\u9fffA-Za-z0-9_\-]{1,64}$` | CJK + ASCII 字母数字 + `_` + `-` |
| `blocks._NAME_RE` | `^[\u4e00-\u9fffA-Za-z0-9_\-]{1,64}$` | 同上（不套保留字） |
| `keys._ALIAS_RE` | `^[\w\u4e00-\u9fff-]{1,64}$` | `\w`(Unicode) + CJK + `-` |
| `semver._VERSION_RE` | `^\s*v?(\d+)\.(\d+)\.(\d+)(?:-([0-9A-Za-z.\-]+))?(?:\+[0-9A-Za-z.\-]+)?\s*$` | 版本号预发布段允许 `.` / `-`，无路径分隔符 |

**核心防线**：`backend._normalize_rel()` 拒绝以 `/` 开头、拒绝 `..` 段、拒绝空段；
`LocalBackend.path_of()` 二次用 `commonpath` 做前缀归属检查。

**入口点覆盖情况**：所有把「包名 / 版本 / 签名者 / 分类 / 块名 / 命名空间 / 领域」
拼进路径的位置，都在拼接前经过对应白名单校验。`installer.uninstall` 有额外的
`dirname==base` 归属检查。`_收集块根` 有 `commonpath` 归属检查。

### 3.2 依赖获取与解压

- `_safe_extract_targz` 的四条既有拒绝面（软/硬链接、设备节点、绝对路径、越出目录）
  实现正确：路径判定用 `abspath` + `commonpath == dest_abs`（不是 `startswith`），
  能挡住 `/a/b` vs `/a/bb` 的假匹配；Windows 反斜杠归一后再判绝对。
- 3.12+ 叠 `filter='data'` 官方过滤器；3.10/3.11 依赖前置手写预检。
- git 来源：`shell=False` + argv 列表 + `--` 分隔符（挡 `--upload-pack=` 类注入）。
- HttpBackend URL 拼接：每段 `urllib.parse.quote(p, safe='')`，包名里的 `/`/`..` 被
  percent 编码不会跨段；明文 `http://` 默认拒（`JIKUAI_REGISTRY_INSECURE=1` 才放）。

### 3.3 动态代码执行

- 生产代码里**无**直接的 `eval` / `exec` / `compile` / `pickle` / `marshal` /
  `yaml.load` / `os.system` / `os.popen`（`Evaluator.eval(ast)` 是极快自己的 AST
  求值方法，名字撞车不算）。
- 五个入口点全部识别：`pybridge._load_sidecar`、`module_loader._load_python_backing`、
  `pkg.cli` 的 `jk 包 运行 <脚本>`（`shell=True`）、`sources._fetch_git`、
  `ai.embed_client` sidecar。
- pybridge `DENY_LIST` 与 `os.popen`/`os.system` 的字面量存在但**从未在生产代码
  实际调用**——只出现在拦截列表、docstring、文档、负向测试里。

## 四、发现（W86 已修）

### F1 · `.块根.json` 读侧信任「路径」字段（真缺陷）

**风险**：`installer.read_block_roots_index()` 与 `module_loader._block_root_parents()`
只 `isinstance(rel, str)` 判空，不拦 `..` / 绝对路径 / 归一后越界。

**利用性**：写侧 `_收集块根` 有 `commonpath` 归属检查兜住，但索引文件本身**可随项目
分发**（vendor `极机_包/` 进版本库的团队会把它一起带走）。而这个 rel 一旦解析成目录，
就会进 `module_loader` 搜索路径，`.jk` 命中后同目录同名 `.py` 会被 `spec.loader.exec_module`
执行（ADR-16 §3.3 混合模块）—— 等于是**指向任意目录的代码执行重定向原语**。

远程发布（M23）开写端后，攻击者能通过污染的包让别的用户从注册表装到含恶意
`.块根.json` 的包时，脱离 `极机_包/` 载入任意目录的 `.py`。

**裁决**：读侧必须自证。加校验，不信任写侧的历史约束（defense-in-depth）。

**修复**（W86）：`installer.安全块根路径()` 拒绝三类（绝对路径 / `..` 段 / `commonpath`
越界）；`read_block_roots_index()` 与 `module_loader._block_root_parents()` 都改走
同规则。读侧越界条目**静默跳过**（与既有版本不符处理同强度——不因可选索引挡住 `导入`）。

**测试**：`tests/test_w86_security.py::test_安全块根路径_*`、`test_read_block_roots_index_跳过越界条目`、
`test_module_loader_块根父目录_同规则跳过越界`，7 个用例。

### F2 · `_safe_extract_targz` 无解压炸弹防护（真缺陷）

**风险**：路径安全挡的是「写到哪」，体量不限则 tar bomb（每个成员路径都合法，
但解压后能撑爆磁盘）能过。恶意注册表包 `getmembers()` 阶段本身也能耗尽内存。

**修复**（W86）：加三条上限：
- `_MAX_MEMBERS = 4096`（可用 `JIKUAI_PKG_MAX_MEMBERS` 覆盖）
- `_MAX_MEMBER_BYTES = 64 MiB`（`JIKUAI_PKG_MAX_MEMBER_BYTES`）
- `_MAX_TOTAL_BYTES = 256 MiB`（`JIKUAI_PKG_MAX_TOTAL_BYTES`）

判定时机：**解压前**按 tar 头部 `size` 字段累加，不需要真的写盘才发现。环境变量
非法值（负数、非数字）静默回落默认——安全网配错应退回更安全的默认，不应崩溃。

**测试**：`test_解压_成员数超上限_拒绝`、`test_解压_单成员超上限_拒绝`、
`test_解压_合计超上限_拒绝`、`test_解压_默认上限内的小归档正常放行`、
`test_解压_环境变量非法值回落默认`，5 个用例。

### F3 · `HttpBackend._request` 无响应体上限（真缺陷）

**风险**：`resp.read()` 无字节上限，恶意注册表用超大响应让客户端 OOM——同族问题
的下载侧。不能信 `Content-Length`（可伪造）。

**修复**（W86）：分块读（每块 64 KiB）+ 按累计字节比对上限：
- `_MAX_RESPONSE_BYTES = 512 MiB`（`JIKUAI_REGISTRY_MAX_RESPONSE`）
- 与 F2 的总解压上限（256 MiB）对齐留余量：归档压缩后小于解压后是常态；
  归档本身若超此上限，解压后必超 F2，不值得下载完再拒。

**测试**：`test_http_响应体超上限_中断下载`、`test_http_响应体在上限内_正常返回`，
2 个用例（本机 `http.server` 端到端 mock）。

## 五、已知的、按 ADR 明确声明的取舍（不算缺陷，本轮不动）

以下每一条都在既有 ADR/文档里明确标记为**信任边界**或**设计取舍**，本轮审计
仅确认它们与实际实现一致；要改动须另立 ADR。

| 位置 | 边界 | 依据 |
|---|---|---|
| `jk 包 运行 <脚本>` 用 `shell=True` 执行 `包.json.scripts` | 信任边界 = 项目主人（清单作者） | `cli.py:274-277` 注释 |
| 第三方包 `.py` 侧车在 `导入` 时自动 `exec_module` | ADR-16 §3.3 混合模块契约 | `module_loader.py:35-59` |
| pybridge `DENY_LIST` 是**黑名单缓解**而非沙箱，可被 `importlib` 等间接路径绕过 | ADR-21 §2 明确声明「不是沙箱，只适用于可信代码」 | README.md 顶部安全声明 + `docs/安全边界.md` |
| git 子进程未做协议白名单（`ext::` / `file://`）| 依赖用户系统 git 配置默认 `protocol.ext.allow=never`；`--` 分隔符已挡 `--upload-pack=` 类注入 | `sources._fetch_git` 注释 |
| 先解压后验签（校验和/签名对象是解压后目录，不是归档字节）| tar 解析器在验签前已暴露 —— 本轮的 F2 上限已收缩这一窗口的最大损失，进一步隔离需引入独立 tar 解析器（另一个量级） | `installer._verify_registry_signature` docstring |
| Ed25519 走纯标准库 RFC 8032 实现 | 品牌硬约束：零第三方依赖（v0.16.0 起） | ADR-33 §3.1 |

## 六、门禁 G19（W87 · 后续）

**目标**：把 F1-F3 里「可机检」的不变量固化，避免下一版靠人肉复查。

**候选断言**（沿用 G16/G17 的双向 diff 思路）：
- G19a：全仓不存在把外部路径拼到文件系统而不经 `_normalize_rel` / `commonpath` 检查的
  静态模式（用 AST 扫，不用文本 grep）
- G19b：`_safe_extract_targz` 有 `_MAX_MEMBERS` / `_MAX_MEMBER_BYTES` / `_MAX_TOTAL_BYTES`
  三个常量声明，值不为 0/负数
- G19c：`HttpBackend` 有 `_max_response` 槽，且 `_request` 以分块方式读

G19 具体形态与实现留 W87 落地；本节仅列不变量。

## 七、对 M23（远程发布）的输入

审计过程中沉淀出的、必须写进 ADR-35 的约束：

1. **签名前置于解压**：M23 客户端发布时，签名对象必须与读端一致（校验和字符串），
   不能引入新的签名对象。
2. **写端授权粒度**：token ↔ 包名归属绑定必须写清（不能只做「有 token 即可写」，
   参见风险 §5 第 4 条）。
3. **未签名包写端硬拒**：读端 v0.20.0 是过渡告警，写端没有存量兼容负担，直接拒。
4. **默认拒覆盖已发布版本**：`--允许覆盖` 必须显式开，且**服务端**拒（不是客户端）。
5. **配额**：单包体积上限与 F2/F3 对齐（256 MiB 解压 / 512 MiB 传输）。

这些进入 ADR-35 章节 § 授权 / § 覆盖 / § 配额。
