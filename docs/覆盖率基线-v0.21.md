# 极快 JiKuai · 覆盖率基线 · v0.21.0 M24 W94（W97 已勘误重测）

> 首次量化。测量命令、口径、基线数字与低覆盖区排期都记在这里。
> **本轮刻意不设 `fail_under` 阈值**——先有基线再定目标，避免为覆盖率写空测试。

---

## 〇、勘误（W97 · v0.22.0 · M25）

**v0.21.0 首版基线的口径是错的，据此排出的「低覆盖区」优先级不可用。**
按 v0.19.0 W61 的纪律，错误留档不静默覆盖：

**错在哪**：coverage.py 默认**只记发起它的那个进程**。而本仓有 **17 个测试文件**
用 `subprocess` 起子进程跑被测代码——`lsp_helpers.start_lsp_process()` 起
`python -m jikuai_lsp`（LSP 全部能力都在子进程里跑）、`test_pkg_remote_publish_e2e.py`
起注册表服务端、`test_v0_7_0_tutorial.py` / `test_v0_4_0_examples.py` /
`test_v0_14_0_demos.py` / `test_blocks_cli.py` shell out 跑 `.jk` 与 CLI。
这些路径**实际被测到了，却没记进基线**。

**怎么发现的**：准备按首版排期给 `completion.py` 补测试时，先跑
`test_lsp_completion.py`（8 例）单测它的覆盖率——8 例全过，覆盖率却仍是 25.0%。
覆盖发生在子进程里，父进程看不见。

**修法**（W97 落地，见 §一）：coverage 官方的 subprocess 测量三件套——
`parallel = true` + `COVERAGE_PROCESS_START` 环境变量 + site-packages 里的
`.pth` 启动钩子。封装成 `scripts/coverage_baseline.py` 一条命令。

**被推翻的结论**：首版点名的「三处 <55% 真空洞」里**有两处是测量假象**，
第三处也被大幅低估。详见 §三的对照表。真空洞只有一个。

## 一、测量口径

配置在 `pyproject.toml` 的 `[tool.coverage.run]` / `[tool.coverage.report]`。

- **范围**：只量 `src/jikuai/`。`lsp/`、`tools/`、`scripts/`、`benches/` 不进基线
  —— 它们靠 e2e 与契约门禁自证（`tools/registry-server/` 有跨进程 e2e，
  `scripts/check_*.py` 每个都有正例 + ≥3 类反例的门禁自测）。
- **分支覆盖开启**（`branch = true`）。lexer / parser / evaluator 的绝大部分
  逻辑是控制流分支，只看行覆盖会严重高估。
- **含子进程**（`parallel = true` + 启动钩子）。这是 W97 修正的核心。
- **排除**：`pragma: no cover`、`raise NotImplementedError`、
  `if __name__ == '__main__':`、`if TYPE_CHECKING:`。

**唯一正确的复现方式**：

```powershell
python -m pip install -e ".[dev]"
python scripts/coverage_baseline.py --按覆盖率升序
```

**不要**直接 `coverage run -m pytest` —— 那样跑出来的就是被推翻的父进程口径数字。
脚本会临时往可写的 site-packages 装 `.pth` 钩子并在 `finally` 里删掉；
找不到可写目录时**直接失败而不降级**，因为没钩子测出的数字不可信。

代价：全量测量约 **265 秒**（普通回归 107 秒，2.5 倍）——子进程都开了 coverage。
所以覆盖率测量**不进常规 CI**，按需跑。

## 二、基线数字（2026-08-13，v0.21.0 tag 之后）

含子进程的真实口径：

- **语句**：8681 条，未覆盖 **1234** 条
- **分支**：3218 个，部分覆盖 **493** 个
- **总覆盖率：83.4%**
- 测量时全量回归 2247 passed / 34 skipped，`combine` 汇总了 **131 份**进程数据

对照首版的父进程口径 81.5%——总数只差 1.9 个点，**但单模块的差异极大**，
这正是首版排期失效的原因：总数看起来没问题，掩盖了个别模块被系统性低估。

83.4% 高于我发布前的主观预期（当时估 70% 上下）。原因是这个项目的测试
一直是「端到端优先」——2247 条里大量是跑真实 `.jk` 源码的集成用例，
一条用例横穿 lexer→parser→evaluator，天然把核心链路的分支压得很实。

## 三、父进程口径 vs 真实口径（差异最大的几处）

- **`completion.py`：25.8% → 78.2%**。**首版最严重的误判**。LSP 补全内核整条
  被 `python -m jikuai_lsp` 子进程打过。已达标，不需补。
- **`service/text_document_store.py`：54.5% → 86.1%**。同上，LSP 增量同步在子进程里。
  已远超目标。
- **`main.py`：49.5% → 71.7%**。教程/示例/demo 三组测试 shell out 跑 `.jk`，
  顶层 CLI 因此被打到。已过 70%。
- **`src/jikuai/__main__.py`：0.0% → 100%**。就是被 `python -m jikuai` 打的那一行。
- **`module_loader.py`：82.5% → 87.7%**、**`pkg/blocks.py`：84.1% → 84.6%**、
  **`pybridge.py`：84.5% → 85.0%**、**`parser.py`：94.7% → 95.2%**：小幅上修。
- **`pkg/cli.py`：41.8% → 41.8%（一点没变）**。这条最有信息量：`jk 包` CLI
  **确实没有被子进程测到**（`test_v0_8_0_pkg.py` 只有 1 处 subprocess，且不走 CLI 分派）。
  它是**唯一的真空洞**。
- **纯内核模块的首版数字本来就是可信的**（lexer / parser / evaluator / ast_nodes
  在父进程内被直接调用），只是被上修了零点几个点。

## 四、低覆盖区（真实口径，升序，只列 < 80%）

- **`pkg/__main__.py` — 0.0%（1 条语句）**
  `python -m jikuai.pkg` 的转发 shim。**不排期**：兄弟文件 `src/jikuai/__main__.py`
  同形且已 100%，这一条的正确性由 `jk 包` 的 console_script 入口间接覆盖。
- **`pkg/cli.py` — 41.8%（318 条，漏 179）**
  **唯一真空洞，v0.22.0 M25 的唯一必做项。** `jk 包` 的子命令分派与**参数组合**
  分支（`--演练`/`--确认`/`--允许覆盖`/`--签名` 交叉，远程 vs 本地分派）几乎没测。
  G17 门禁保证了命令表与文档一致，但那只管「子命令名存不存在」，不管行为。
  M23 刚加的远程发布分支欠账也压在这里。
- **`pkg/blocks_cli.py` — 68.4%（707 条，漏 199）**
  `jk 块` 子命令，语句数最多的单文件。漏的多是交互式输出分支（表格/JSON/详略），
  风险低于 `pkg/cli.py`。**排期 v0.23.0**。
- **`pkg/lockfile.py` — 68.4%（100 条，漏 25）**
  锁文件读写，可复现构建的地基。**排期 v0.22.0**：要先分清漏的是「损坏锁文件的
  容错路径」还是「正常路径」——若是后者必须补。
- **`pkg/sources.py` — 70.1%（220 条，漏 66）**
  依赖获取（本地/git/注册表/远程 tar.gz）。**排期 v0.22.0**：W86 的解压三道限额
  有 `test_w86_security.py` 覆盖，但 **git 来源的失败路径**（网络错误、ref 不存在）
  基本空白。
- **`main.py` — 71.7%**、**`frontend.py` — 74.1%**、**`repl_session.py` — 76.3%**
  顶层 CLI 与 REPL 交互。**不单独排期**：都已过或接近 70%，且交互式路径的
  自动化成本高、回报低。等有具体 bug 再补针对性用例。
- **`completion.py` — 78.2%**、**`ai/embed_client.py` — 79.8%**
  **不排期**。前者已达标；后者在离线环境下大部分分支走降级路径（本机连不上
  huggingface 是既知状态），补它要 mock 一整套远端。

## 五、阈值决策（W97 重定）

首版立的纪律不变——**点阈值优先于面阈值**，理由也不变：全局阈值把压力平摊到
所有文件，而风险集中在少数模块，平摊等于鼓励刷最容易涨的那些。

基于真实基线 83.4% 的具体决定：

- **v0.22.0 M25 的目标收窄到一个点**：`pkg/cli.py` 41.8% → **70%+**。
  首版列的另三个（`completion.py`/`main.py`/`text_document_store.py`）**已达标，取消**。
- **顺带补两条中风险**：`pkg/lockfile.py` 与 `pkg/sources.py` 各 → 78%+。
- **`fail_under` 设 80**（不是首版设想的「达标后再设 80」——现在 83.4% 已经在 80 之上，
  直接设即可，留 3.4 个点缓冲吸收正常波动）。**不进 G 门禁体系**：覆盖率是趋势
  指标不是契约，红了给告警不阻断合并。
- **不追 95%**。首版的这条判断继续有效。
