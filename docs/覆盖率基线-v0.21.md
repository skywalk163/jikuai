# 极快 JiKuai · 覆盖率基线 · v0.21.0 M24 W94

> 首次量化。测量命令、口径、基线数字与低覆盖区排期都记在这里。
> **本轮刻意不设 `fail_under` 阈值**——先有基线再定目标，避免为覆盖率写空测试。

## 一、测量口径

配置在 `pyproject.toml` 的 `[tool.coverage.run]` / `[tool.coverage.report]`：

- **范围**：只量 `src/jikuai/`。`lsp/`、`tools/`、`scripts/`、`benches/` 不进基线
  —— 它们靠 e2e 与契约门禁自证（`tools/registry-server/` 有 27 例跨进程 e2e，
  `scripts/check_*.py` 每个都有正例 + ≥3 类反例的门禁自测）。
- **分支覆盖开启**（`branch = true`）。lexer / parser / interpreter 的绝大部分
  逻辑是控制流分支，只看行覆盖会严重高估。
- **排除**：`pragma: no cover`、`raise NotImplementedError`、
  `if __name__ == '__main__':`、`if TYPE_CHECKING:`。

复现：

```powershell
python -m pip install -e ".[dev]"
python -m coverage run -m pytest tests -q
python -m coverage report --sort=cover
```

## 二、基线数字（2026-08-13，v0.21.0 tag `c830ae7`）

- **语句**：8681 条，未覆盖 1395 条
- **分支**：3218 个，部分覆盖 486 个
- **总覆盖率：81.5%**（语句 + 分支合并口径）
- 测量时全量回归 2247 passed / 34 skipped

81.5% 高于我发布前的主观预期（当时估 70% 上下）。原因是这个项目的测试
一直是「端到端优先」——2247 条里大量是跑真实 `.jk` 源码的集成用例，
一条用例横穿 lexer→parser→interpreter，天然把核心链路的分支压得很实。

## 三、低覆盖区（按覆盖率升序，只列 < 85%）

- **`__main__.py` / `pkg/__main__.py` — 0.0%（各 1 条语句）**
  `python -m jikuai` 的转发 shim。**不排期**：这一条语句的正确性由
  `jikuai` / `jk` 两个 console_scripts 入口的 e2e 间接覆盖，为它写测试是形式主义。
- **`completion.py` — 25.8%（180 条语句，漏 122）**
  LSP 补全。**排期 v0.22.0**：这是本轮最大的真空洞。补全是用户每秒都在碰的
  路径，靠 LSP 集成手测撑着，回归里几乎没有。优先补「关键字/块名/成员」三类
  候选的生成与排序。
- **`pkg/cli.py` — 41.8%（318 条，漏 179）**
  `jk 包` 的子命令分派与参数解析。**排期 v0.22.0**：G17 门禁保证了命令表与文档
  一致，但**参数组合**的分支基本没测（`--演练`/`--确认`/`--允许覆盖`/`--签名`
  的交叉）。远程发布刚加了新分支，这块欠账在涨。
- **`main.py` — 49.5%（77 条，漏 36）**
  顶层 CLI 入口（`jk 跑`/`jk 编`/`jk 版本`…）。**排期 v0.22.0**，与 `pkg/cli.py` 同批。
- **`service/text_document_store.py` — 54.5%（79 条，漏 34）**
  LSP 文档增量同步。**排期 v0.22.0**：增量 `didChange` 的区间拼接算错会让
  整个 LSP 会话静默错位，是高危低覆盖组合。
- **`pkg/blocks_cli.py` — 68.4%（707 条，漏 199）**
  `jk 块` 子命令。语句数最多的单文件。**排期 v0.23.0**：漏的多是交互式输出
  分支（表格/JSON/详略），风险低于上面几条。
- **`pkg/lockfile.py` — 68.4%（100 条，漏 25）**
  锁文件读写。**排期 v0.22.0**：锁文件是可复现构建的地基，漏的分支要看清是
  「损坏锁文件的容错路径」还是「正常路径」——若是后者必须补。
- **`pkg/sources.py` — 70.1%（220 条，漏 66）**
  依赖获取（本地/git/注册表/远程 tar.gz）。**排期 v0.22.0**：W86 刚加了解压
  三道限额，限额分支有 `test_w86_security.py` 覆盖，但 git 来源的失败路径
  （网络错误、ref 不存在）基本空白。
- **`frontend.py` — 74.1%**、**`repl_session.py` — 76.3%**
  REPL 与前端交互。**不单独排期**：交互式路径的自动化成本高、回报低，
  维持现状，等有具体 bug 再补针对性用例。
- **`ai/embed_client.py` — 79.8%**
  向量嵌入客户端。**不排期**：离线环境下大部分分支走降级路径（本机连不上
  huggingface 是既知状态），补它需要 mock 一整套远端。
- **`pkg/backend.py` — 80.2%**、**`pkg/manifest.py` — 80.5%**
  刚被 M23 改动过的两个文件。**v0.22.0 顺手补**：漏的主要是错误分支
  （异常状态码、畸形 manifest 字段），补起来便宜。

## 四、不设阈值的理由（W94 纪律）

路线图原话是「**不预设 95% 目标** —— 先看基线，再定本版目标（拍数字容易
催生为覆盖率而写的空测试）」。现在基线是 81.5%，据此的判断：

- **不设全局 `fail_under`**。全局阈值会把压力平摊到所有文件，而真正的风险
  集中在上面三条 <55% 的模块。平摊等于鼓励去刷最容易涨的那些文件。
- **v0.22.0 的目标改成「点」而非「面」**：把 `completion.py`、`pkg/cli.py`、
  `main.py`、`service/text_document_store.py` 四个抬到 **70% 以上**，
  总覆盖率随之自然到 84-85%。达成后再考虑设 `fail_under = 80` 防退化。
- **CI 不因覆盖率红**。本轮只产出数字与排期，不加门禁。
