# 极快 JiKuai 路线图 · v0.22.0（一个季度）

> 起草：2026-08-13（v0.21.0 发布当日）
> 周期：W97-W108（约 3 个月，12 周）
> 前置：v0.21.0（M22 安全审计 + M23 远程发布 + M24 覆盖率基线/四平台 CI；回归 2247 passed / 34 skipped；G10-G19 全绿；覆盖率基线 81.5%）
> 关联：`docs/BACKLOG.md`、`docs/覆盖率基线-v0.21.md`、`docs/ADR-35-远程发布协议.md`、`docs/安全审计-v0.21.md`
> 主题：**把上一季度留的四条尾巴一次收齐——质量补洞、注册表生产化、AOT 子集破冰、生态再上量**

---

## 一、这一版为什么是「四线并进」而非「单一主轴」

v0.19-v0.21 三个季度每季都有一条清晰主轴（块生态运转 → 可信读 → 可信写）。
v0.22.0 不同：可信写端已闭环，没有单一的下一个「大主轴」在催，反而是四处
**具体的、有据可查的欠账**同时到期。逐条都有前序版本留下的明确落点，不是拍脑袋：

- **质量补洞**：W94 已量出基线 81.5%，并点名三处 <55% 真空洞。基线出来了不补，
  等于白量。
- **注册表生产化**：ADR-35 明确把 TLS / 多进程写 / 公钥轮换 / 授权 warm reload
  划到「下一轮」。远程发布已能用但只能单进程、必须挡在反代后，这是明写的欠账。
- **AOT 子集破冰**：BACKLOG §2 + v0.21 路线图 §1.2 都记着 AOT 的真瓶颈是子集太窄，
  且明确「要扩须先立 ADR 推翻设计边界」。这条拖了三个季度没动。
- **生态再上量**：L3 聚合块在 v0.17-v0.18 扩到 7 个后没再动；块库要继续长。

**风险自陈（务必先读 §四）**：四线并进在 12 周里是**紧的**。尤其 AOT 破冰，
真做完整对象模型 + 栈展开 + 堆容器远超一个季度。本路线图对 M27 只承诺
**第一个垂直切片**（容器 + 成员访问），异常 / Lambda / 类显式顺延 v0.23.0。
其余三条按「先易后难、可独立交付」排序，任一条延期不阻塞其他三条发布。

---

## 二、目标

一句话：**v0.21.0 让写端能用，v0.22.0 让四条已知欠账各还一截——质量看得见、
注册表能上生产、AOT 迈出子集扩宽第一步、块库继续长。**

排序原则：**风险与依赖解耦**。四个里程碑之间无强依赖，各自可独立回归、独立发布。
先做确定性高的（质量补洞、注册表生产化），把不确定性最高的 AOT 破冰放在中段
（留足试错窗口，且它单独失败不影响其余三条收尾）。

## 三、里程碑

### M25 · 质量补洞（W97-W99）

**W97 已完成，且推翻了本节的原始范围。** 首版 M25 承诺把四个模块抬到 70%+，
那是基于 v0.21.0 W94 的**错口径**数字排的——coverage 默认只记父进程，而本仓
17 个测试文件用 `subprocess` 跑被测代码，LSP / CLI / 服务端的覆盖全被漏掉。
详见 `docs/覆盖率基线-v0.21.md` §〇 勘误。

- **W97 修测量 + 重测（已完成）**：落地 coverage 官方 subprocess 三件套——
  `pyproject.toml` 开 `parallel`、`tests/conftest.py` 注入 `COVERAGE_PROCESS_START`、
  `scripts/coverage_baseline.py` 装/卸 `.pth` 启动钩子并编排 erase→run→combine→report。
  真实基线 **83.4%**（父进程口径 81.5%）。
  **原定四个目标里三个已达标**：`completion.py` 25.8%→**78.2%**、
  `main.py` 49.5%→**71.7%**、`service/text_document_store.py` 54.5%→**86.1%**。
- **W98 `pkg/cli.py` 41.8% → 92.0%（已完成）**：**唯一的真空洞**（重测后一点没变，
  说明 `jk 包` CLI 确实没被任何子进程测到）。新增 `tests/test_pkg_cli.py` 54 条，
  按子命令补齐参数组合与错误分支：`--确认`/`--允许覆盖`/`--签名` 交叉、演练 vs 正式、
  远程 vs 本地目标名、`_parse_add_source` 全部缺参与来源互斥、`列表` 三种安装状态。
  G17 门禁只管子命令名存不存在、不管行为，这层行为契约由本文件兜住。
- **W99 两条中风险各 → 78%+（已完成，双双超标）**：
  `pkg/lockfile.py` 68.4%→**100%**（`tests/test_pkg_lockfile.py` 24 条：拒读损坏锁
  文件的全部分支 + 写出字节的确定性）；`pkg/sources.py` 70.1%→**92.8%**
  （`tests/test_pkg_sources.py` 42 条：三种来源的失败路径、W86 三条解压上限、
  路径穿越与链接/设备节点拒绝）。
  git 分支用 monkeypatch 替掉 `subprocess.run`，**不依赖本机装 git**，CI 上不飘。
  实测漏的主要是容错路径——正常路径本来就被 installer 跑透了。
- **设 `fail_under = 80`（已完成）**：现状 83.4% 已在 80 之上，直接设即可，留 3.4 个点缓冲。
  **不进 G 门禁体系**——覆盖率是趋势指标不是契约，红了告警不阻断合并。
  覆盖率测量耗时 265 秒（普通回归 107 秒），**不进常规 CI**，按需跑。

**验收（M25 已全部达成）**：`pkg/cli.py` 92.0% ≥70%；`lockfile.py` 100% /
`sources.py` 92.8% 各 ≥78%；`fail_under=80` 已上线；
`scripts/coverage_baseline.py` 是唯一正确的测量入口。
回归 2367 passed / 34 skipped（W97 前 2247），G10-G19 全绿。

**顺手记一处死代码**（本次不改）：`sources._iter_source_files` 里
`if fn.endswith('.tmp'): continue` 不可达——上一行已要求 `fn` 以
`.jk`/`.py`/`.json` 结尾，不存在同时以 `.tmp` 结尾的文件名。留给后续清理。


### M26 · 注册表生产化（W100-W102 · ADR-36）

还 ADR-35 明记的四条欠账。**仍守单节点、零第三方依赖**——生产化不等于做集群。

- **W100 ADR-36（已完成）**：`docs/ADR-36-注册表生产化.md` 四条全部定案——
  (1) **TLS**：自身永不做，新增 `--要求TLS转发`（缺 `X-Forwarded-Proto: https` 即 403）
  + 非回环绑定且未开该开关时启动横幅醒目告警。把「必须挡在反代后」从建议升级为可强制的约束；
  (2) **多进程写**：裁决为**单写者**，不做跨进程文件锁（零依赖下两套平台实现，
  收益为零——索引本就必须串行，读端该走反代/CDN）。改为启动时抢
  `<注册表根>/.发布锁`（`O_CREAT|O_EXCL`），已被占用即拒绝启动，陈旧锁靠 `--强制解锁`
  手工清（不做自动判活：Windows 无 `os.kill(pid,0)`，且 pid 会复用）；
  (3) **授权 warm reload**：每请求 `stat` 比对 `(mtime_ns, size)`，变更即重载。
  **不用 SIGHUP**（Windows 没有，会做成半个平台的功能）。三条硬性质：加载失败保留旧配置、
  重载按 token 哈希延续频次窗口（否则改配置就能清零配额）、撤销下一请求即生效；
  (4) **公钥轮换**：TOFU pin 文件从「单行」改「每行一把公钥」，旧文件天然兼容零迁移；
  任一受信公钥验过即通过，于是老包不再集体失效。
- **W101 实装 warm reload + 公钥轮换（已完成）**：这两条纯服务端/信任库内改动，风险可控。
  ADR-36 §3 的五条反例测试全部落地（见下「W101 的落地与偏离」）。
- **W102 部署契约文档 + TLS 契约 + 单写者锁文件**：新增 `docs/远程注册表部署.md`
  （nginx / Caddy / systemd 样例、锁文件与陈旧锁处置、token 撤销流程、公钥轮换流程）。

**W100 的两处偏离（已在 ADR-36 记账）**：
1. **砍掉「过渡窗口」的时间语义**。本节原文写「多公钥并存 + 过渡窗口」，
   ADR-36 §2.4 只保留前者：时间过期要求时钟同步，且**时钟回拨能复活已撤销的公钥**。
   多公钥并存本身就是窗口，开关由 `密钥 信任` / `密钥 撤信` 两个显式动作界定。
2. **新增公钥必须本地显式授权，不做自动分发**。绝不能让「注册表侧出现新公钥」
   自动并入本地 pin——那样攻破注册表即可签发受信包，TOFU 归零。
   因此新增 `jk 包 密钥 信任 <别名> <公钥>` / `密钥 撤信 <别名> <公钥>`
   两个子命令（**连带 G17 命令表同步**）。代价是签名者换密钥时下游都要动一次手，
   这个代价是刻意付的。
   新配置项全走 CLI 参数、**刻意不新增环境变量**，不给 G18 加负担。

**W101 的落地与偏离**：

落地面：`auth.AuthProvider`（每请求 `stat` 比对 `(mtime_ns, size)` +
`AuthConfig.carry_rate_windows_from` 延续频次窗口 + 失败保留旧配置且不推进
stamp 以便下次重试）；`server.build_server` 把 `授权` 包成 provider，`_发布`
在认证前取 `授权源.current()`；`trust.py` 改多公钥（`_read/_write_pinned_keys`
每行一把、`pinned_keys`/`trust_key`/`untrust_key`/`resolve_trusted_keys`、
`verify_signature` 试全部受信公钥、`_验签失败说明` 区分「疑似轮换」与「疑似篡改」）；
CLI `密钥 信任` / `密钥 撤信`。

1. **纠正 v0.21.0 的一处安全判断，而不只是加功能**。旧行为是「注册表公钥 != pin
   就拒装」。这是错的：pin 过之后 pin 才是权威，注册表侧那份公钥只是分发渠道上的
   副本。只要签名验得过某把已 pin 的公钥，包就没被动过，改注册表那个文件不该有
   任何效果。相应地：
   - 服务端与 `registry.publish` 写注册表公钥文件从「不一致就 409」改为**追加多行**
     （权威仍是管理员显式编辑的 `授权.json`，不是报文）；
   - 原 `test_公钥变更_拒装` 与 `test_同别名换身份被拒` 断言的是旧（错的）行为，
     已改写为 `test_注册表公钥被换_pin是权威_照样装得上` /
     `test_注册表公钥文件是追加而非拒写`，并新增
     `test_注册表换公钥且包重签_拒装并指向密钥信任` 覆盖真正的轮换/投毒场景。
2. **G17 暴露出一层深度盲区**。`密钥` 的子子命令不在 `_ALIASES` 里，G17 看不见；
   把 `trust`/`untrust` 的英文写法写进「英文别名：」段落会被 G17 当成顶层别名报红。
   本轮只把它们移到该段落之外（G17 恢复绿），**没有**顺手扩 G17——那是独立改动。
   已记入 BACKLOG，目标 v0.23.0。这条值得单独记账：G17 当初就是为防这类漂移建的，
   现在它自己漏了一层。
3. **`密钥 撤信` 的语义边界**：撤到一把不剩会**删掉** pin 文件而非留空文件，于是
   回到「未建立信任」，下次装包重走 TOFU 首次 pin。留空文件会让 `ls` 看起来像还
   信着，误导人。

**验收**：`授权.json` 改动无需重启即生效并有反例测试；签名者轮换公钥后老包仍验签通过、
新包用新公钥；部署文档含 TLS 反代样例；多进程策略有明确裁决与对应测试或告警。


### M27 · AOT 子集破冰 · 第一切片（W103-W106 · ADR-37）

**这是本季度最大不确定项，只承诺第一个垂直切片。** 见 §四风险。

- **W103 ADR-37**：推翻 BACKLOG §2 的部分设计边界。定清**运行时对象模型**的最小形态
  ——如何在 C 侧表示极快的列表/字典（堆分配 + 引用计数 or 简单 GC？），
  以及成员访问的降级路径。**只定第一切片要的，不预设异常/类的模型**。
- **W104-W105 实装容器 + 成员访问**：把「列表字面量 / 字典字面量 / 下标 / `.成员`」
  从 AOT 子集外移进子集内。C 运行时补堆容器 + 引用计数。
- **W106 端到端 + 守卫**：现有 `test_v0_*_aot_*.py` 系列扩容器用例；确保新特性在
  四平台 gcc/clang 下真跑（沿用 AOT e2e 零 skip 守卫）。
- **显式顺延 v0.23.0**：异常 / Lambda / 类 / 管道的 AOT 支持。它们要栈展开与闭包捕获，
  是独立的大工程，本季度不碰。

**验收**：含列表/字典/成员访问的 `.jk` 能 AOT 编译成二进制并跑出正确结果；
四平台 e2e 零 skip；ADR-37 明确记录第一切片的边界与顺延项。

### M28 · 生态再上量 + 收尾（W107-W108）

- **W107 L3 扩容 + 第三方块包**：L3 聚合块从 7 个继续长（从真实集成方需求反推，
  沿用 W67「不为凑数造玩具」纪律）；块库总条目随之增长，过 G12/G13/G13+/G14 门禁。
- **W108 发布**：全量回归 + G10-G19 全绿 + CHANGELOG + 版本号 bump（只动 `_version.py`
  四处投影）+ 缓冲。

**验收**：新增 L3 块有真实需求出处；全平台 CI 绿；v0.22.0 发布。

## 四、风险

- **四线并进撑爆季度**（全局头号风险）。**应对**：四个里程碑无强依赖，按确定性排序
  （M25/M26 高确定 → M27 高风险 → M28 收尾）。**任一里程碑延期不阻塞其余发布**——
  实在做不完，砍 M27 切片范围或把 M28 的 L3 扩容并入下一版，M25/M26 单独也能构成一次有效发布。
- **AOT 对象模型陷入泥潭**（M27）。真瓶颈在此。**应对**：ADR-37 只定第一切片
  （容器 + 成员访问）的模型，不预设异常/类；引用计数 vs GC 的选型若两周内定不下来，
  降级为「只做不可变列表/字典 + 值语义」的更小切片先出。宁可切片更小也不留半成品。
- **公钥轮换破坏既有信任**（M26）。老包验签集体失效是最坏情况。**应对**：TOFU 库改多公钥
  并存 + 过渡窗口，W101 必须有「轮换后老包仍验签通过」的反例测试。
- **补覆盖率倒退成刷空测试**（M25）。**应对**：点阈值而非全局阈值；每个补的用例必须
  断言真实行为（补全候选的正确性、参数分支的实际效果），不为覆盖率写只调用不断言的测试。
- **注册表生产化滑向做产品**（M26）。**应对**：ADR-36 守单节点、零依赖、不做 Web 管理界面；
  TLS 靠反代不自做，与 W31/ADR-35 同源。

## 五、成功度量（达成 ≥4/5 视为季度成功）

1. **质量看得见**：`completion.py`/`pkg/cli.py`/`main.py`/`text_document_store.py`
   四个模块各 ≥70%，总覆盖率 ≥84%，`fail_under=80` 上线（M25）。
2. **注册表能上生产**：warm reload + 公钥轮换实装且各有反例测试；部署文档含 TLS 反代样例（M26）。
3. **AOT 迈出第一步**：含列表/字典/成员访问的程序能 AOT 编译运行，四平台 e2e 零 skip（M27）。
4. **AOT 边界留档**：ADR-37 明确第一切片范围与 v0.23.0 顺延项，无半成品（M27）。
5. **生态继续长**：新增 L3 块有真实需求出处并过全部块门禁（M28）。

## 六、本季度刻意不做的（逐条 + 理由）

- **AOT 的异常 / Lambda / 类 / 管道** —— 需栈展开与闭包捕获，是独立大工程，顺延 v0.23.0（§三 M27）。
- **注册表集群 / 多租户 / Web 管理界面** —— 沿用 ADR-35，守单节点单管理员。
- **LLVM 后端 / 静态类型推导 / 异步 / 图形标准库** —— 沿用 v0.21 路线图 §1.2 裁决，均需另立 ADR。
- **LSP `codeAction`** —— ADR-31 已关闭，无新社区诉求不重开。
- **全局覆盖率冲 95%** —— W94 已立纪律：点阈值优先于面阈值，避免刷空测试。
