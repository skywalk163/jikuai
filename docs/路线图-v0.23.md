## 一、这一版为什么是「单主轴 + 两条待需求项」

v0.22.0 一次收了四条尾巴（质量/注册表/AOT/生态）。到 v0.23.0，手上明确「必须做」的
大主轴只剩一条真正有价值主张支撑的：**中文分词词典**。它是六域之一「中文」的门面能力，
565 条词典对外称不上一个卖点。这条不依赖任何外部需求触发，是主动补强。

另两条 BACKLOG 候选项都**卡在「等具名需求」**，本版不作主轴、只在有余量时机会性推进：

- **L3 块扩容（§4）**：v0.22.0 W107 查证后顺延——现有 7 块自 v0.18.0 起零「不够用」
  反馈，按 W67「不为凑数造玩具」纪律，无具名需求不补。
- **AOT 异常 / Lambda / 类（§2）**：v0.22.0 只做了容器 + 成员访问第一切片，其余顺延；
  但这些都是「设计边界，要动先立 ADR」级别，不该在没有真实 AOT 用户催的情况下硬推。

所以 v0.23.0 = **一条主轴（M29 分词词典）+ 机会性清账**。这是刻意收窄，不是没活干：
分词词典的真实工作量在数据来源、授权、质量核查与门禁，不在算法，值得一个版本认真做。

## 二、目标

一句话：**把 `stdlib/分词` 的词典从 565 条扩到约 2.9 万条通用 + 域内词，
让「中文」域第一次有一个拿得出手的分词能力，且授权链条干净、体积与幂等可控。**

验收总纲（细分见各里程碑）：

1. 词典达约 2.9 万条（jieba top20000 ∪ 现有 565 种子 ∪ THUOCL 财经/法律），
   现有 565 条**一条不少**。
2. 授权链条完整落档，两份 MIT + THUOCL 引用声明齐全。
3. FMM 切分在典型中文文本上相比现状**可感知变好**，用一个人工标注的小切分基准量化
   （不是检索指标——见 ADR-38 §2 非目标）。
4. 幂等三条 AC 与「无 global / frozenset」静态断言继续绿；新增种子必留、词长上限、
   词典 sha256 三条门禁。
5. 回归全绿，词典文件纳入打包清单，`.vsix` / wheel 真机验证词典可加载。

## 三、里程碑

### M29 · 中文分词词典扩容（主轴）

按 ADR-38 落地。拆成可独立回归的四步，W 编号接 v0.22.0 的 W108。

#### W109 · 生成管线与数据落地

- 写 `tools/dict/重生成词典.py`：读三个上游源（jieba `dict.txt`、THUOCL
  `caijing`/`law`），按 ADR-38 §3 过滤（2≤长度≤8、全汉字）、按词频取 jieba top20000、
  并入现有 565 种子与两个 THUOCL 表，去重、码点升序排序，产出：
  - `stdlib/分词词典.txt`（明文，约 2.9 万行 / 289 KB）
  - `stdlib/分词词典.元信息.json`（每源 URL/license/取用规则/条数 + 合并 sha256）
  - `stdlib/分词词典来源.md`（人读授权，转录两份 MIT + THUOCL 引用格式）
- **脚本内断言 `seed - merged == ∅`**（ADR-38 §3.2 必留约束），断言失败即拒绝产出。
- 脚本要能离线复跑：上游源缓存到 `tools/dict/上游/`（不入仓，`.gitignore`），
  有缓存就不联网。记录每源下载 URL 与取用日期。

#### W110 · 加载改造与词长上限

- 改 `stdlib/分词.py`：删除 7 段内联字面量（`_RAW_*` / `_ALL_RAW`），
  `_build_dictionary()` 改为读同目录 `分词词典.txt` 构建 `frozenset`；文件缺失
  **抛异常，不静默降级**（ADR-38 §8）。
- `_build_dictionary()` 过滤条件加词长上限 8；`MAX_WORD_LEN` 推导逻辑不变（自然变 8）。
- 保持纯函数与幂等：读文件只在导入期，`segment()` 运行期不碰文件。
- 更新模块 docstring（词典来源、条数、词长上限）与 `docs/标准库.md` §分词的
  「已知限制」（565 → 约 2.9 万；仍是 FMM、仍不做词性/NER/新词）。

#### W111 · 测试与门禁

- 改 `test_词典至少500条` → 下界上调到 `>= 40000` 并加上界哨 `<= 80000`（ADR-38 §9，
  防「守卫绿≠守卫在守」）。
- 新增：`test_种子集全部在库`（读原 565 种子清单比对）、`test_词长上限为8`、
  `test_词典文件sha256与元信息一致`。
- 幂等专项 `test_v0_6_0_segmenter_idempotent.py` 全绿（AC-M5-07-01/02/03 不变）；
  确认 `test_AC_M5_07_02_源码无global与可变模块级容器` 仍通过（改造不得引入 global）。
- G10 契约（`分词.jk` 导出与文档一致）复跑绿。词典文件与元信息一致性可挂一条
  轻量门禁进 `scripts/check_stdlib_contract.py`（可选，做不成不阻塞）。

#### W112 · 切分质量基准与打包

- 建一个**人工标注**的小切分基准 `tools/dict/切分基准.json`（50-100 句中国式业务
  文本，人工给出期望切分），量化扩容前后的词级 F1 或边界准确率。这是 ADR-38 §2
  验收标准 3 的落地——量分词质量本身，**不碰检索指标**。
- 把 `stdlib/*.txt`（含 `分词词典.txt`）纳入打包清单（wheel `MANIFEST.in` /
  `pyproject.toml` package-data、`.vsix` 打包脚本），真机装一次确认词典能加载、
  `分词` 能用。参照 v0.18.0 教训「vsix 真机验证要先 npm install + pip install -e」。

### 机会性清账（无强承诺，有余量才做）

- **L3 扩容**（BACKLOG §4）：仅当本版周期内出现具名需求（新集成方反馈 / 具名待建块）
  才启动；否则继续顺延。启动则须重跑 `tools/ai-bridge/generate_embeddings.py` 过 G12。
- **文档债**（BACKLOG §7）：14 个无独立文件的 ADR 编号，可顺手补几个高频被引的。

## 四、风险与边界

- **最大的坑是「把词典扩容当成检索救星」**。ADR-38 §2 已把非目标钉死：不改
  `_tokenize_chinese`、不以检索指标验收。评审时任何「顺便把检索也调一下」的提议
  都要挡回去——那是另一条待定项，要单独按双集纪律走。
- **jieba dict.txt 上游语料授权不可逐条追溯**（ADR-38 §7 已如实记录）。风险处置是
  「换源重生成」，因词典是生成产物。这条要在来源文档里写明，不藏。
- **词长上限 8 是有损决策**：丢了 0.15% 的长词换 28% 速度。若日后有「必须整体成词的
  9+ 字业务词」的具名反例，再单独评估放宽——但那多半是短语，应走短语识别而非塞进 FMM。
- **体积**：534 KB 明文词典（top50000）。相比 `向量索引.bin` 不算大，但要确认它没被误打进
  某些体积敏感的分发物（如若有精简版 wheel）。
- 本版主轴单一，交付风险低于 v0.22.0 的四线并进。主要不确定性在「切分质量基准
  怎么标才有说服力」——W112 若标注争议大，退而求其次报「边界准确率 + 抽样人工复核」。

## 六、M29 实施结果（2026-08-15）

### 落地数字

- 词典 `stdlib/分词词典.txt`：**58713 条 / 547251 字节（534 KB）**，
  sha256 `5205f8393c897df4…`。组成：种子 565 + jieba top50000 + THUOCL 财经 3771 +
  THUOCL 法律 6226（去重后）。词长范围 [2, 8]。
- 构建耗时约 **50 ms/进程**（`_PY_BACKING_CACHE` 保证只付一次）。原来的逐字符
  `all()` 过滤要 150 ms，换成编译正则 `_合法词` 后降到 50 ms，结果一字不差。
- 切分质量（`tools/dict/切分基准.json`，40 句人工标注中国式业务文本，基线=逐字切）：
  - 边界 F1 **0.513 → 0.864**（+0.351）
  - 词级 F1 **0.004 → 0.741**（+0.736）
  - 整句全对 **0 → 21/40**
- 分词专项测试 59 passed（含新增 4 条：种子必留、词长上限、sha256 一致、缺文件即抛错）。

### 与计划的偏离（两处，都是实测推翻计划）

1. **top20000 → top50000**：起草时按体积/加载耗时定 top20000。W112 的尺寸扫描发现
   FMM 速度几乎与词条数无关（O(1) 集合查表），真正的速度杠杆是词长上限；而质量在
   top50000 处到拐点，再往上到全量词典**质量回退**（低频垃圾词造出坏长匹配）。
   全套扫描数据在 ADR-38 §3.1 更正块。
2. **压缩 → 明文**：拍板时选了压缩存储，实测只省约 84 KB，代价是 git diff 完全
   不可读、gzip 要固定 mtime 才字节可复现、加载还更慢。改明文 + sha256 记账。
   详见 ADR-38 §5.2。

### 挂账（不在本轮做）

- **打包清单没落**：W112 计划里的「把 `stdlib/*.txt` 纳入 wheel / `.vsix`」**没做**。
  查证结论是这不是本轮引入的缺口——**整个 `stdlib/` 目录一直都不在 wheel 里**，
  项目靠 `pip install -e .` + `__file__` 相对回溯工作。这是仓库级既有缺口，
  且 ADR-16 §3.4 的 data-files 原方案**本身不成立**（`data_files` 装到 `sys.prefix`，
  与代码的 `../../stdlib` 回溯对不上，这才是它三个版本没落地的真实原因）。
  **完整口径、7 处待改定位点、修法与验收已收敛到 `docs/BACKLOG.md` §10**，
  触发条件是「首次发 PyPI / 首次分发非 editable wheel 之前必须做」。
  `分词.py` 的「文件缺失即抛 RuntimeError」就是为这种发布事故留的兜底。
