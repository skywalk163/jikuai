## 一、进场第一件事:订正规划文档的错误前提

`规划-未来三月.md` 原文断言「现在零自动化门禁,全靠人肉在本机跑」,并把覆盖率线上化
(W94)、macOS CI(W95)记成两笔待清的老挂账。**逐条核实后这几条都不成立**:

- `.gitea/workflows/ci.yml` 那条 Gitea Actions 流水线**早就在跑**——自建 FreeBSD
  host runner(`runs-on: freebsd`),到 2026-08-16 已累计 **34 次 run**,最近一次
  (`ci.yml #34`)压在 `64e9da4` 上,耗时 27m43s。全量 pytest、G10–G19、AOT 零 skip
  守卫都在那儿卡着。
- `.github/workflows/ci.yml` 有 379 行五个 job(ubuntu 3.10/3.11/3.12 矩阵 +
  windows + macos + freebsd VM + 独立 coverage job)。
- **W94/W95 早已完成**,在 `e82866c`(v0.21.0 M24)。覆盖率硬门禁还在 2026-08-14
  于 github 的 ubuntu 3.12 job 上**真跑通过一次**——证据留在
  [`覆盖率下限.json`](覆盖率下限.json) 的 `_已知风险` 字段里。

所以本轮不是「从零建 CI」。**真实缺口是四条**,都比原命题窄、也更具体:

1. **发布准入的两道检查从未进过任何 CI**。G20(`check_wheel_contents.py`)只在
   `check_stdlib_contract.py` 末尾打一行提示,靠人记得单独跑;干净 venv wheel e2e
   只有 `.ps1` 版,而 gitea 那台 runner 上没有 pwsh。BACKLOG §10 那次事故
   (PyPI `jikuai 0.4.1` 的 wheel 里零个 stdlib 文件,坏了三个版本没人发现)就是
   这个缺口的实测代价。
2. **gitea 的覆盖率步骤是 `continue-on-error`**,只打数字不卡门。硬门禁只长在
   github 那条**推不上去**的流水线里——这正是 v0.22 那条「守卫绿≠守卫在守」教训
   的另一面:守卫存在、但装在跑不起来的地方。
3. **lsp / dap 两包从未在任何 CI 里被构建过**。v0.24.0 给它们钉了 `jikuai>=0.24.0`
   下界,元数据坏掉只有发版当天才知道。
4. **tag 触发的发版流水线为零**。发版全靠人按 `路线图-v0.24.md` §六 手敲 build +
   twine,漏一步没有任何东西会拦。

## 二、拍板:CI 落在 Gitea Actions

**决定**:主战场 `.gitea/workflows/`。`.github` / GitCode 两条保留为「可公开验证」
的镜像,不再往里加新门禁。

依据不是「github 慢」,而是**只有 gitea 这条真在跑**。本机推 github 反复 300s 超时
(v0.24 教训),GitCode 流水线要在控制台单配、至今没配。门禁装在跑不起来的流水线上
等于没有门禁。

**代价要写清**:PyPI Trusted Publishing(OIDC)**用不了**——它只认 GitHub / GitLab /
Google Cloud 等几个身份提供方,自建 Gitea 不在名单里。所以规划文档里「不再存长效
token」那条在 gitea 上做不到。本轮的处置是**根本不上传**(见 W123),于是一个 token
都不用存,反而比存 CI secret 更干净。

**已知短板**:runner 只有 `freebsd` 一个 label,**跨平台矩阵在 gitea 上做不到**。
Windows / macOS / ubuntu 的平台守卫仍只在 `.github` 那条上,而那条跑不起来。这是本轮
**不解决**的缺口,已记进 BACKLOG。

## 三、里程碑 M26 · W121–W124

### W121 · 把发布准入两道检查搬进 Gitea CI

- 新增 [`scripts/verify_wheel_e2e.sh`](../scripts/verify_wheel_e2e.sh)——`.ps1` 版的
  POSIX 等价物。**为什么要有两份**:`.ps1` 依赖 PowerShell 5.1(BOM 要求、
  `$LASTEXITCODE`),FreeBSD runner 上跑不了;而这一步是**唯一能抓住「editable 恰好
  还能回溯到旧位置」这种假绿的检查**。只有 `.ps1` 版就等于这一步永远进不了 CI。
  两份要保持行为等价(五步验收项清单)。
- `.gitea/workflows/ci.yml` 加四步:构建 wheel(**一次,G20 与 e2e 共用**)→
  `check_wheel_contents.py "$WHEEL"`(G20)→ `sh scripts/verify_wheel_e2e.sh "$WHEEL"`
  → 构建 lsp/dap 两包 + `twine check` 三包元数据。
- 持久 venv 依赖表加 `build`。

**验收**:e2e 断言的是**内容**不是退出码——词典没随包发行时 `分词` 会静默退化成
逐字切、退出码照样 0,这正是 0.4.1 那次事故的形状。

### W122 · 覆盖率从「只打数字」转真门禁(gitea)

去掉 `continue-on-error: true`。原来那个理由写得没错(点阈值是 Windows + Python 3.14
标定的,在没标定过的第三个平台上开硬阈值,红了大概率是平台差异),现在改判的依据是两条:

- 阈值已在**两个**平台被真正执行并通过(Windows 本机;2026-08-14 github ubuntu job),
  跨平台落差没有吃掉设计时留的那 ~5 个点余量。
- 更要紧的是缺口 2:硬门禁只长在跑不起来的流水线上。

**红了怎么办**(写进 YAML 注释,不然下次会有人为了变绿调低阈值):先判是不是平台差异,
是的话把 FreeBSD 实测数字补进 `覆盖率下限.json` 的 `_实测`(那里至今只有 Windows 一列),
再带理由调阈值;**不许为了让流水线变绿而调低**。

### W123 · tag 触发发版流水线(半自动,刻意不上传)

新增 [`.gitea/workflows/release.yml`](../.gitea/workflows/release.yml),触发条件
`v[0-9]+.[0-9]+.[0-9]+`。链路:tag↔版本号一致性断言 → 全量测试 → G10–G19 → 构建三包
(sdist + wheel)→ G20 → `twine check` → 干净 venv e2e → 留 artifact → 打印人该做的两步。

**它不上传**,三条理由:

1. 发正式 PyPI **不可逆**。版号发错无法覆盖,撤只能 yank,而 **yank 连 API 都没有**
   (`pypi-` token 只授权 upload 端点;yank 走登录 session + CSRF 的网页表单)——
   v0.24 教训坑 1。自动化一个不可逆且撤不回的动作,收益远小于风险。
2. Gitea 用不了 Trusted Publishing(见 §二),自动上传就必须存长效 token。
3. **真正值钱的不是那条 upload 命令,是它前面那串检查**。人肉发版出事故从来不是
   因为敲不对 twine,而是因为漏跑 G20 / e2e。

新增一道原先没有的检查:**tag 名 ↔ `_version.py` 一致**。G15 只保证
`_version.py ↔ pyproject ↔ CHANGELOG ↔ 扩展 package.json` 四处互相一致,**它管不到
tag**——打错 tag 照样能过 G15,然后发出去一个版号与 tag 不符的包。

### W124 · 收尾

- BACKLOG 新增 §11 记 CI 现状与残留缺口(矩阵做不到 / Trusted Publishing 用不了 /
  FreeBSD 覆盖率数字未采集 / 大端真机)。
- `.gitattributes` 钉 `*.sh` 为 LF。
- **`jikuai` 0.4.1 的 yank 拍定「不做」**(此前记作 W120 挂账):yank 无 API 只能人在
  网页点,而 0.4.1 已被 0.24.0 取代、`pip install jikuai` 默认拿最新版,伤害面接近零。
  改判条件:有人报「装到 0.4.1、装完不可用」。
- 版本号四处投影推到 0.25.0 + CHANGELOG(过 G15)——**留到本轮 CI 全绿之后再做**,
  版号不该在门禁还没验通时先推。

### W125 · 修 `确认 gcc 在位` 这一步的假红(首跑实测暴露)

`ci.yml #35` 第二步就红:`确认 gcc 在位(AOT 端到端用例需要)` exit 1。

**根因不在本轮改动,是那一步本身写错了**:它硬跑 `gcc --version` 且只认
`shutil.which('gcc')`,而**这台 FreeBSD runner 上根本没有 gcc**——base system 自带的是
clang(`cc` 指向它)。文件头那句「gcc 已在 runner 预装」是错的。

真正要跑的 AOT 用例并不要求 gcc:`driver.py` 的 `_CC_CANDIDATES` 是
`("gcc", "clang", "cc", "zig", "cl")`,clang 命中即可;`.github` 的 freebsd job 也是查
`cc`/`clang`,注释还明写「不需要装 gcc」。**同一件事两个文件两套口径,宽的那个才是对的。**

改法:`cc --version || clang --version` + `which('gcc') or which('clang') or which('cc')`,
与 AOT 探测和 `.github` 对齐;`release.yml` 补同一道检查(缺编译器会让 AOT e2e 静默
skip,发版前该拦住)。顺手订正文件头注释与 AOT 守卫的报错文案。

**留个教训**:门禁的探测条件比被守护对象的真实要求更严,产出的红是**假红**——比没有
门禁更糟,因为它训练人忽略红灯。而它能藏住,恰恰因为**没人确认过那条流水线是绿的**
(本轮之前也只看到 run 有耗时,没看到成败)。这是「守卫绿≠守卫在守」的镜像版本:
**守卫红≠真的有问题**。

### W126 · `.sh` 里的变量名必须 ASCII(第二跑实测暴露)

W125 修完编译器探测,`干净 venv wheel e2e 验收` 这步暴露下一个问题:

```
scripts/verify_wheel_e2e.sh: 仓库根=/var/db/.../hostexecutor: not found
scripts/verify_wheel_e2e.sh: 失败数=0: not found
...
scripts/verify_wheel_e2e.sh: arithmetic expression: expecting primary: "失败数 + 1"
```

**根因:POSIX shell 的 name 产生式是 `[A-Za-z_][A-Za-z0-9_]*`,中文标识符不合法。**
FreeBSD `/bin/sh` 把 `仓库根=/x` 当成**命令**去执行,报 `not found` 后带着空值继续走。
改法:把 `仓库根`/`失败数`/`记失败`/`源stdlib`/`期望` 五个标识符全改 ASCII
(`repo`/`fails`/`note_fail`/`src_stdlib`/`expected`)。注释和 `echo` 里的中文不受影响,
**只有标识符受限**。

**两条值得记的**:

1. **这个 bug 推不出来,只能实测。** 孪生的 `.ps1` 里用中文变量名完全正常(PowerShell
   支持 Unicode 标识符),照着它写 `.sh` 就会踩。这正是「两份实现要同步」这条纪律的
   反面代价——语义等价不等于**写法可平移**。
2. **本机 `sh -n` 验不出来。** git-bash 的 `sh` 是 bash,bash **允许**非 ASCII 变量名,
   所以坏版本在本机语法检查里是绿的。**能查这类问题的只有真 POSIX sh**;要在本机
   兜住,只能靠 grep 找「`=` 或 `()` 前面出现非 ASCII 字符」的行。

**顺带确认了 e2e 的核心断言真的在生效**(这一跑前三步全过):
`分词输出：['个人所得税', '起', '征', '点']` —— 整词切出,证明词典真随包发行(退化成
逐字切时退出码照样 0,只有内容断言抓得住);
`stdlib_dir = /tmp/jk_e2e/venv/lib/python3.11/site-packages/jikuai/stdlib` —— 落在
site-packages 而非回落源码树。**W121 想验的东西已经验到了**,挂在第 4 步的覆盖口检查上。

### W127 · `twine check` 换成 G21(第三跑实测暴露)

W126 修完,e2e 五步全绿,下一步 `构建 lsp / dap 两包并校验元数据` 红在 `pip install twine`:

```
× installing build dependencies for nh3 did not run successfully.
    Unsupported platform: 311
    Rust not found, installing into a temporary directory
ERROR: Failed to build 'nh3' when installing build dependencies for nh3
```

**根因:`twine check` 在这台机器上装不上。** twine → readme_renderer → `nh3`,nh3 是
Rust 扩展、PyPI 上没有 FreeBSD 轮子,pip 只能回源码构建,于是要 maturin + Rust 工具链。
查过 readme_renderer 42.0/43.0/44.0/45.0 的 `requires_dist`,**全都**钉 `nh3>=0.2.14`
——「降个版本就不用 Rust」这条路不存在。给 runner 装 Rust 是运维活,而且每跑都要
从源码编 nh3,代价远超收益。

**改法:不迁就工具,重新问「这一步到底要守什么」。** `twine check` 的价值有两块:

- 元数据合规 —— 我们真正需要的那块,纯标准库就能查。
- long_description 能否在 PyPI 页面渲染 —— **正是需要 nh3 的那块**。

于是新增 [`scripts/check_dist_metadata.py`](../scripts/check_dist_metadata.py)(**G21**,
零第三方依赖)承接第一块,断言五条:

- `Name` 规范化后与包名一致;
- `Version` == `src/jikuai/_version.py` 的单一真源 —— 这条 **G15 管不到**,G15 只查
  源码里的四处投影,`dist/` 里躺着上一版 wheel 照样过 G15 然后被一起 upload 出去;
- 有 long_description 就必须有 `Description-Content-Type`;
- lsp / dap 对主包**必须钉 `>=` 下界**(W118 手改的东西,掉了没人会发现,而 PyPI 上
  0.4.1 是个装完不可用的坏包);
- `--要求成对` 时 wheel 与 sdist 都得在(只给 release.yml 用;常规 CI 主包是
  `--wheel` 单构的,缺 sdist 是预期)。

第二块**明确不覆盖**,写进脚本 docstring 和收尾输出:由发版流程里人做的 **TestPyPI
预演**兜住 —— 传上去打开页面看一眼,比渲染器更可信。

**下界正则刻意放宽**:同时认 `jikuai>=0.24.0` 与老 setuptools 的 `jikuai (>=0.24.0)`。
只认一种就会在 setuptools 版本不同的机器上假红 —— 这一轮已经栽过两次同类跟头
(W125 只认 gcc、W126 中文变量名),**凡是「产物长相依赖工具版本」的地方都放宽**。

本地验证(含负例,守卫得证明自己在守):5 个产物全过;`--要求成对 dist` 正确报「只有
wheel,缺 sdist」exit 1;下界正则对 `jikuai` / `jikuai==0.24.0` / `jikuai-lsp>=1.0`
判否,对 `jikuai>=0.24` / `jikuai (>=0.24.0)` / `jikuai[extra]>=0.24.0` 判是。

### W128 · 覆盖率门禁跑不完:coverage 回退到纯 Python tracer(第四跑实测暴露)

W127 之后 G21 那步过了,`覆盖率门禁` **20m43s 只走到 45%**。日志第一行给了答案:

```
CoverageWarning: Couldn't import C tracer: No module named 'coverage.tracer'
(no-ctracer)
```

**不是卡住,也不是 job 超时,是回退到纯 Python tracer 了。** 逐行回调走 Python 层,
比 C tracer 慢一个数量级;照 45% / 20m 外推,整跑要 ~45 分钟。成因:PyPI 上 coverage
**没有 FreeBSD 轮子**,pip 只能装 sdist,建持久 venv 那会儿 C 扩展没编出来,而 coverage
缺 C tracer 时**只 warn 不报错**(设计如此),于是静默降级。

对照:本机 Windows 上 `coverage.tracer` 是 `tracer.cp314-win_amd64.pyd`,C tracer 在位
—— 所以 `覆盖率下限.json` 里那份 Windows 实测数字是**在快路径上**测的,慢是 FreeBSD
独有的问题,不是阈值定得不对。

改法(**修根因,不是放宽门禁**):W125 已经确认这台机器有 clang(`cc` 指向它),那就
强制 `pip install --force-reinstall --no-deps --no-binary coverage 'coverage>=7.0'`
就地把扩展编出来。持久 venv 会留着它,只有第一次花时间。

两条刻意的设计:

- **编不出来就明确失败,不静默走慢路**。慢到 45 分钟的门禁等于没有门禁 —— 它会先撞
  job 级超时,然后被人当噪音关掉。
- 覆盖率那步加 `timeout-minutes: 25`。**超时本身就是要报的结论**(说明 C tracer 那步
  没生效),比让它慢慢啃掉整台 runner 的时间片好。

**这条与前三次假红不同**,值得区分:W125/W126/W127 是门禁的前提假设太严造成的假红;
这次门禁的判据没错,是**执行环境退化到慢路径**。共同点仍在于「本机绿 ≠ 那台机器上
成立」—— 本机有 C tracer,所以本地怎么跑都测不出这个问题。

## 四、本轮明确不做

- **跨平台矩阵上 gitea**:runner 只有 freebsd 一个 label。加 Windows/macOS runner 是
  运维活不是本仓库的活,写了 YAML 也永远排不到队。
- **自动上传 PyPI**:见 W123 三条理由。
- **大端 s390x QEMU runner**(BACKLOG §10.1):gitea runner 是 host 模式无 Docker,
  上 QEMU 要先解决容器,成本远超「大端平台罕见」这个收益。继续挂账。
- **修 github/gitcode 那两条流水线**:本机网络问题,不是 CI 设计问题。

## 五、成功度量

1. **达标**（`ci.yml #39`，2026-08-16）：gitea 一次 run 里 G20、wheel e2e、G21 都真执行且
   绿，不是 skip、不是 `continue-on-error`。
2. **达标**：覆盖率步骤以硬门禁身份跑过并通过 —— 阈值跨 Windows / ubuntu / FreeBSD
   三平台成立。**尚未采集**：FreeBSD 的逐文件数字（`覆盖率下限.json` 的 `_实测` 至今
   只有 Windows 一列，跨平台落差仍是推断）。
3. **未验**：打 tag 让 `release.yml` 跑完并留下三包 artifact。要验就得先把版号推到
   0.25.0（`release.yml` 第一步就断言 tag ↔ `_version.py` 一致）。

**从 W121 推上去到 #39 绿，一共红了四跑**（W125→W128）。四次根因**全在门禁自己或它的
执行环境**，被守护的对象（测试、块库、三包产物）一次没出问题。这个比例本身是结论，
记在 BACKLOG §11.1。
