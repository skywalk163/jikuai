# 远程注册表部署

> v0.22.0 · M26 · W102。设计裁决见 [`ADR-36-注册表生产化.md`](ADR-36-注册表生产化.md)，
> 协议见 [`ADR-35-远程发布协议.md`](ADR-35-远程发布协议.md)。
> 本文只讲**怎么部**与**出事怎么办**，不重复裁决理由。

服务端就是 `tools/registry-server/server.py`，零第三方依赖，一个进程同时做两件事：

- `GET <任意路径>` —— 把注册表根目录当静态镜像原样吐出（读端）
- `POST /publish` —— 唯一写入口，走认证 → 授权 → 频次 → 体量 → 验签 →
  校验和复核 → 覆盖检查 → 原子落盘

## 目标形态

```
客户端 --HTTPS--> 反向代理（终结 TLS，设 X-Forwarded-Proto）
                      |
                      +--HTTP--> 127.0.0.1:8765  server.py（--要求TLS转发）
                      |
                      +--直接吐静态文件--> <注册表根>/   （读端，绕过 server.py）
```

三条契约：

1. **服务端自身永不做 TLS**。证书签发、续期、协议版本与套件选择、OCSP 是反代
   的本职，自己做一份必然是更差的一份。
2. **服务端只绑回环**。`--监听 127.0.0.1`（默认）。能连上它的只有本机进程，
   也就是反代自己。
3. **读端最好绕过服务端**。`索引.json` / `分类/*.json` / `包/**.tar.gz` /
   `密钥/*.公钥` 都是静态文件，让反代直接吐，别让每个 `jk 包 装` 都去唤醒一个
   Python 进程。server.py 的 `GET` 是为「只想跑一个进程」的最简部署留的兜底。

## 启动

```bash
python tools/registry-server/server.py \
    --注册表 /srv/jikuai/注册表 \
    --授权   /etc/jikuai/授权.json \
    --监听   127.0.0.1 \
    --端口   8765 \
    --审计   /var/log/jikuai/审计.jsonl \
    --要求TLS转发
```

参数速查：

- `--注册表`（必填）：本地注册表根目录，写入目标。
- `--授权`（必填）：`授权.json` 路径。**改动无需重启**，见下「撤销一个 token」。
- `--监听` / `--端口`：默认 `127.0.0.1:8765`。
- `--审计`：append-only JSONL；**拒绝也记，且从不记 token**。省略即不写。
- `--要求TLS转发`：`POST /publish` 必须带 `X-Forwarded-Proto: https`，否则 403。
- `--强制解锁`：启动前删掉陈旧的 `.发布锁`，见下「陈旧锁」。

环境变量只有一个：`JIKUAI_REGISTRY_SERVER_MAX_BODY`（单请求体上限，字节，
默认 32 MiB，先于 JSON 解析生效，超限直接 413）。其余开关刻意都走命令行参数
——systemd unit 里看得见，比藏在环境里更可审计。

退出码：`0` 正常 / `2` 授权配置错 / `3` `.发布锁` 冲突。

### `--要求TLS转发` 的准确语义

它断言的是「**我确认自己只被反代访问**」，**不是**「我能鉴别请求是否走了 TLS」。
`X-Forwarded-Proto` 本身完全可伪造 —— 但在回环绑定下，能写这个头的只有反代
自己，所以头是谁写的没有歧义。

推论：**如果你把服务端绑到了非回环地址，这个开关给不了你任何安全保证**，
它只会挡住忘记设头的反代。这种情况下服务端启动时会打一段醒目的横幅告警
（但不拒绝启动 —— 内网可信段直连是合理场景）。

## nginx

```nginx
server {
    listen 443 ssl http2;
    server_name 注册表.example.com;

    ssl_certificate     /etc/letsencrypt/live/注册表.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/注册表.example.com/privkey.pem;

    # 写端点：转给 server.py，必须带 X-Forwarded-Proto
    location = /publish {
        proxy_pass http://127.0.0.1:8765;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-Proto $scheme;   # ← --要求TLS转发 靠它
        proxy_set_header X-Forwarded-For   $remote_addr;

        # 报文是 base64 后的 tar.gz，默认 1m 会把正常发布卡掉。
        # 与服务端 JIKUAI_REGISTRY_SERVER_MAX_BODY 及各 token 的
        # 「单包字节」对齐，取最小者生效。
        client_max_body_size 32m;
        proxy_request_buffering on;
        proxy_read_timeout 120s;
    }

    # 读端：静态文件直接吐，不经过 Python 进程
    location / {
        root /srv/jikuai/注册表;
        autoindex off;
        # 索引与分片会变，别让客户端缓存太久；归档按内容不可变，可长缓存
        location ~ \.tar\.gz$ { expires 30d; add_header Cache-Control immutable; }
        location ~ \.json$   { expires 1m; }
    }
}

server {                      # 80 → 443
    listen 80;
    server_name 注册表.example.com;
    return 301 https://$host$request_uri;
}
```

> `root` 指向注册表根后，`.发布锁` 也会落在那个目录里，理论上可被 `GET` 读到
> （里面只有 pid 与启动时刻，不含机密）。想干净些就加
> `location = /.发布锁 { return 404; }`。

## Caddy

```caddyfile
注册表.example.com {
	# 写端点
	handle /publish {
		reverse_proxy 127.0.0.1:8765 {
			header_up X-Forwarded-Proto {scheme}
		}
	}

	# 读端：静态文件
	handle {
		root * /srv/jikuai/注册表
		file_server
	}

	request_body {
		max_size 32MB
	}
}
```

Caddy 默认自动申请与续期证书，且默认就会设 `X-Forwarded-Proto`，
上面写出来只是为了让契约显式可见。

## systemd unit

```ini
# /etc/systemd/system/jikuai-registry.service
[Unit]
Description=极快远程注册表服务端
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=jikuai
Group=jikuai
WorkingDirectory=/opt/jikuai
ExecStart=/usr/bin/python3 /opt/jikuai/tools/registry-server/server.py \
    --注册表 /srv/jikuai/注册表 \
    --授权 /etc/jikuai/授权.json \
    --监听 127.0.0.1 --端口 8765 \
    --审计 /var/log/jikuai/审计.jsonl \
    --要求TLS转发

# SIGTERM 走正常退出路径，finally 里会删掉 .发布锁
KillSignal=SIGTERM
TimeoutStopSec=20
Restart=on-failure
RestartSec=3

# 只让它写这三个地方
ReadWritePaths=/srv/jikuai/注册表 /var/log/jikuai
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
NoNewPrivileges=yes

[Install]
WantedBy=multi-user.target
```

**不要**配 `Restart=always` 配合 `ExecStart` 里的 `--强制解锁`：那等于把单写者
约束自动绕过，崩溃循环时会有两个进程交替写同一个注册表根。

文件权限建议：

- `/etc/jikuai/授权.json` → `0640 root:jikuai`（里面是 token 的 sha256，
  不是明文 token，但仍不该让全机可读）
- `/srv/jikuai/注册表` → `0755 jikuai:jikuai`（读端要能读）
- `/var/log/jikuai/审计.jsonl` → `0640 jikuai:jikuai`

## 单写者与 `.发布锁`

服务端是**单写者**：启动时用 `O_CREAT|O_EXCL` 原子创建
`<注册表根>/.发布锁`，写入自己的 pid 与启动时刻；正常退出（含 Ctrl-C 与
SIGTERM）在 `finally` 里删除。

**不支持多 worker，也不支持两个进程指向同一个注册表根。** 索引是全局单点，
写路径本来就必须串行；多 worker 只能提升读吞吐，而读端应该由反代直接吐。

第二个进程启动时会立刻失败（退出码 3）：

```
无法启动：该注册表根已有一个服务端持锁（持锁 pid=41234，启动于 2026-08-14T02:11:07Z）。
本服务端是单写者（ADR-36 §2.2），不支持多进程同时写同一个注册表根。
  · 若确实还有进程在跑：先停掉它。
  · 若那是崩溃留下的陈旧锁：确认该 pid 已不存在后，加 --强制解锁 重启。
  （刻意不自动判活：pid 会复用，自动判断必然有猜错的时候。）
```

### 陈旧锁

进程被 `SIGKILL`、机器断电、容器被强杀 —— 这些情况下锁文件会留下。处置：

```bash
cat /srv/jikuai/注册表/.发布锁          # 看里面记的 pid
ps -p <pid>                             # 确认它真的不在了（Windows: tasklist /FI "PID eq <pid>"）
# 确认之后再加参数重启
python tools/registry-server/server.py ... --强制解锁
```

**为什么不自动判活**：`os.kill(pid, 0)` 在 Windows 上不可用，而 pid 会被系统
复用。跨平台的自动判活必然要么误杀一个活着的进程，要么误放一把该拦的锁。
让人看一眼、自己敲一个参数，比一个有时猜错的启发式可靠。

## 运维流程

### 撤销一个 token

`授权.json` 的改动**无需重启**：服务端每个请求前 `stat` 一次该文件，
`mtime_ns` 或 `size` 变了就重载。

```bash
# 1. 从 授权.json 的「令牌」里删掉那条（键是 token 的 sha256 hex）
vim /etc/jikuai/授权.json
# 2. 完事。下一个带该 token 的请求就是 401。
```

两条附带性质：

- **重载不重置频次配额**。仍然存在的 token 会把滑动窗口原样延续过来 ——
  否则「改一下配置」就成了清零配额的后门。
- **写坏了不会致瘫**。JSON 语法错、`协议` 版本不认、文件正被替换而暂时不存在
  —— 这些都只记一条 warning 日志，继续用上一份已生效的配置，并在下一个请求
  再试一次。改对了立刻生效，不用重启。

对应地：**启动期**读不出配置就是硬失败（退出码 2）。运行期的宽容不适用于启动期。

### 新增一个发布者

```bash
# 发布者本机：
jk 包 密钥 生成 甲          # 生成 Ed25519 密钥对
jk 包 密钥 导出 甲          # 打印 44 字符 base64 公钥，交给管理员

# 管理员在服务端：把公钥和 token 的 sha256 登记进 授权.json
python -c "import hashlib,sys;print(hashlib.sha256(sys.argv[1].encode()).hexdigest())" '<明文token>'
```

```json
{
  "协议": 1,
  "令牌": {
    "<上面算出的 64 位 hex>": {
      "签名者": "甲",
      "公钥": "<jk 包 密钥 导出 甲 的输出>",
      "可发布": ["甲包", "甲-*"],
      "每小时次数": 20,
      "单包字节": 16777216
    }
  }
}
```

`可发布` 支持精确名与 `前缀-*` 通配，**没有**「全部」通配（纯 `*` 在加载配置时
就会被拒）。明文 token 由管理员通过带外渠道交给发布者，发布者放进
`JIKUAI_REGISTRY_TOKEN` 或 `~/.jikuai/凭证.json`。

### 轮换一个发布者的公钥

轮换要**两边都动**，没有自动分发 —— 这正是 TOFU 的安全前提。

```bash
# 1. 发布者：生成新密钥对，导出新公钥
jk 包 密钥 生成 甲-2026
jk 包 密钥 导出 甲-2026

# 2. 管理员：把 授权.json 里该 token 的「公钥」字段换成新公钥。
#    无需重启。此后该 token 发布的包用新钥验签；
#    注册表侧 密钥/甲.公钥 会在下一次发布时**追加**新公钥（不是替换）。

# 3. 每个装包方（下游）：确认新公钥确属该签名者后追加进本地信任库
jk 包 密钥 信任 甲 <新公钥base64>
```

第 3 步之前，下游装**新**包会被拒，错误信息会直接把该敲的命令打出来：

```
签名者「甲」的签名验不过本地已信任的 1 把公钥，但注册表里出现了一把新公钥
——可能是密钥轮换，也可能是投毒。**不自动接受**。
确认这把公钥确实属于该签名者后，执行：
  jk 包 密钥 信任 甲 <新公钥base64>
旧公钥会保留，用旧钥签的老包不受影响。
```

**旧公钥保留 → 用旧钥签的老包照样能装。** 轮换不会让该签名者的历史包集体
失效，这是 v0.22.0 修掉的痛点。

### 私钥泄露

轮换是「多一把钥」，泄露是「少一把钥」，两件事不一样：

```bash
# 服务端：立刻从 授权.json 删掉该 token（下一个请求即 401），
#         再按上面「轮换」流程登记新公钥。
# 每个装包方：把泄露的那把公钥从信任库摘掉
jk 包 密钥 撤信 甲 <泄露的公钥base64>
```

`撤信` 撤到一把不剩会删掉该别名的信任文件，回到「未建立信任」，下次装包
重走首次信任（TOFU）。

⚠️ **`撤信` 只影响本机**。没有吊销列表（CRL）分发机制 —— 单管理员单节点的
范围内，通知下游是人的事。用泄露私钥签过的**历史包**在没执行 `撤信` 的机器上
仍然验得过。

### 审计

`审计.jsonl` 每行一条 JSON，append-only：

```json
{"时间":"2026-08-14T02:31:09Z","远端":"127.0.0.1","签名者":"甲","名称":"甲包","版本":"0.2.0","字节":40960,"结果":"已发布"}
{"时间":"2026-08-14T02:33:40Z","远端":"127.0.0.1","签名者":"?","名称":"?","版本":"?","字节":0,"结果":"拒绝","原因":"token 不认识；请检查 ..."}
```

**从不记录 token**（明文或哈希都不记）。拒绝也记 —— 只记成功的审计日志在排查
攻击时等于没有。`远端` 在反代后会是 `127.0.0.1`，想看真实来源就看反代的
access log 或让反代设 `X-Forwarded-For`（服务端目前不解析它，见下）。

轮转用 `logrotate` 时选 `copytruncate`：服务端持着追加句柄，`rename` 式轮转会
让它继续往已改名的文件写。

## 排障

- **403 且提到 `X-Forwarded-Proto`** → 反代没设那个头，或客户端绕过反代直连了
  服务端端口。检查 nginx 的 `proxy_set_header`。
- **401 `token 不认识`** → token 的 sha256 没登记，或刚被撤销（热重载已生效）。
- **403 `越权`** → 包名不在该 token 的 `可发布` 里，或报文 `签名者` 与登记的
  签名者不一致。
- **403 `签名验证失败`** → 客户端签的私钥与服务端登记的公钥不是一对。多半是
  轮换只做了一半。
- **409** → `名称@版本` 已存在。**没有覆盖开关**，提升版本号。
- **413** → 报文超上限。可能卡在反代的 `client_max_body_size`、服务端的
  `JIKUAI_REGISTRY_SERVER_MAX_BODY`、或该 token 的 `单包字节`，三者取最小。
- **429** → 触发该 token 的每小时次数。
- **启动就退 3** → `.发布锁` 冲突，见上「陈旧锁」。
- **启动就退 2** → `授权.json` 读不出或不合法。**启动期不宽容**。

## 已知局限

照抄 ADR-36 §4 与 ADR-35 §4 里与部署直接相关的几条，免得部署时才发现：

- **频次配额进程重启后清零**。窗口在内存里，没有状态存储。
- **`X-Forwarded-Proto` 不是密码学保证**。见上「准确语义」。
- **不解析 `X-Forwarded-For`**：审计里的 `远端` 在反代后恒为 `127.0.0.1`。
  真实来源看反代日志。
- **单写者是硬约束，不是可调参数**。要更高写吞吐得另立 ADR 推翻 ADR-36 §2.2。
- **陈旧锁要人介入**（`--强制解锁`）。刻意的。
- **锁在网络文件系统上不保证**：NFS 的 `O_EXCL` 原子性依赖实现。别把注册表根
  放在多机共享的网络盘上再指望锁能挡住另一台机器。
- **没有 CRL**：`密钥 撤信` 只改本机信任库。
- **公钥轮换要下游各自动手**。没有自动分发，这是 TOFU 的前提而非缺陷。
