## 2. 架构决策（架构师）

### ADR-09 · 类作用域限定白名单（**采纳 X1**）

这是 G5 的根因决议，也是本轮的架构主线。

| 方案 | 内容 | 结论 |
|------|------|------|
| **X1** | `DefEntry` 记录字符区间，`_try_user_def_strict` 按 `pos` 查 `ScopeMap` 判定白名单是否生效 | ✅ **采纳** |

| X3 | 同名直接报错 | ❌ 否决：破坏现有代码，违反 AC-66「期望内建与用户定义共存」 |

**采纳依据**
1. 语义精确对齐 AC-66 ~ AC-70；
2. 保留 R-E 单入口，不引入第二条解析通道；
3. 与 G2（元数守卫）、G3（Python 桥）**正交**，互不牵连；
4. 作用域是纯静态字符区间，可独立单元测试，验证成本低。

### ADR-10 · Python 桥独立模块 + `蟒:` 前缀

- 新增独立 `pybridge.py`，Python 模块以 `蟒:` 前缀显式导入。
- 否决「无前缀先查 `.jk` 再查 `.py`」：模块解析产生歧义、错误诊断复杂化。

### ADR-11 · Python 函数必须括号调用，不进 `VERB_ARITY`

- 否决无括号调用：C 扩展函数签名不可探测，且会破坏「元数集中声明、可审计」这一 G2 基本性质。

### ADR-12 · 元数守卫从 evaluator 前移到 parser

使元数错误在语法期即被拦截，配合 ADR-11 保持元数声明的单一权威来源。

### 类型映射表

`整数↔int` / `小数↔float` / `字符串↔str` / `布尔↔bool` / `空↔None` / `列表↔list` / `字典↔dict` / `人民币↔Decimal`；**`BoundMethod` 禁止跨界传递**。

### 安全约束（交付总监重点确认项）

## 6. 分歧与裁决记录

### 6.1 DEF-01 · AC-68「同类内内建动词遮蔽」语义之争

**分歧点**
类 `甲` 中定义了 `方法 长度` 后，在**同一个类**的另一方法体内写裸名 `长度 自身.吴项`，当前实现走 IDENT 路径并报「未定义的标识符：长度」，未回落到内建动词 `长度`。PRD AC-68 的字面表述要求此处内建语义仍然可用。

**各方立场**

| 方 | 立场 |
|----|------|
| 产品经理（PRD 原文） | AC-68 字面要求：类内定义同名方法后，内建动词语义不应丢失 |
| 工程师 | 当前语义是 ADR-09 X1 的正确结果：类作用域内该名字归属本类方法，本就应可见 |
| QA | 按 PRD 字面应判 FAIL；但**实质上支持工程师的语义**。强行让同类内裸名回落内建会与 `自身.长度()` 产生二义，属 X3 级改动。建议拆分 AC，但不代产品经理改写，交交付总监裁决 |

**裁决：采纳 QA 的拆分建议（含交付总监追加约束）**

1. **AC-68 判定口径变更为跨作用域语义** —— 「某内建动词名被某类登记后，该名字在**该类作用域之外**（其他类、顶层、REPL 顶层）仍保留内建动词语义」。按此口径本轮 **PASS**。
2. **新开 AC-68b** —— 同类内名字被本类方法遮蔽时，诊断文案必须可操作，例如：
   「`长度` 已被本类方法遮蔽，请改名或使用 `内建:长度`」
   实现范围**严格限定**为 evaluator 的错误建议逻辑，不触碰解析语义，纳入 M1 尾段。
3. 要求**产品经理回填 PRD 修订版**（AC-68 rev.2 + AC-68b），本裁决作为变更依据留痕。交付总监不越权直接改写 PRD 原始产出。

**裁决依据**

1. **「类内方法名在本类内可见」是作用域语义的定义性后果，不是缺陷。** 若反其道让同类内裸名回落内建，则 `长度` 与 `自身.长度()` 在同一作用域内指向两个不同实体，是真正的语义事故。
2. **架构约束优先于实现协商。** 让同类内裸名回落内建属 X3 级语义改动，而 ADR-09 已明确否决 X3（破坏现有代码、违反 AC-66）。按「架构 vs 实现：以架构约束为先，实现细节可协商但不得越界」原则，不能反向要求实现突破已裁定的架构边界。
3. **非本轮回归。** legacy 模式（`JIKUAI_LEGACY_ADR06=1`）同样失败，证明这是 v0.3.2 起就存在的既有行为，不是 ADR-09 引入的退化。质量红线约束的是「零回归」，此项不触红线。
4. **PRD 字面 vs 实际业务价值。** AC-68 的业务意图是「内建动词不因某处类定义而**全域**失效」，该价值已由 AC-66 / AC-67 / AC-69（含已修复的 REPL 路径）完整覆盖。字面表述把作用域范围写得过窄，属 **AC 表述缺陷，而非实现缺陷**。
5. **但不允许用"解释"关闭缺陷。** 用户在此处遇到的「未定义的标识符：长度」确实是误导性文案 —— 名字明明存在，只是被遮蔽。这是真实的体验缺口，故必须以 AC-68b 作为**补偿性交付**同步落地，且不得顺延出 M1。

### 6.2 DEF-05 · AC 编号区间与用例组数不匹配

**分歧点**
AC-78 ~ AC-90 为 13 个编号，但 PRD 声明 15 组边界用例，无法建立 1:1 追溯。

**候选口径**
- (a) 以编号为权威，删减 2 组用例；
- (b) 以组数为权威，将区间扩展为 AC-78 ~ AC-92；
- (c) 保持主区间不变，溢出 2 组使用子编号。

**裁决：采纳 (c) —— 子编号方案，新增 `AC-90a` / `AC-90b`，不做全局重编号。**

**裁决依据**

1. **不能删组。** 15 组边界用例的运行时行为已 **15/15 实测通过**，是真实且已验证的覆盖面。删减 2 组等于主动丢弃已获得的质量证据 —— 违反「实现 vs 测试：以质量红线为先」。故 (a) 排除。
2. **不能扩区间。** AC-91 ~ AC-123 已分配给 M2/M3，扩展到 AC-92 会与之**正面冲突**，并触发全局连锁位移，导致 PRD / 架构文档 / QA 报告中所有既有 AC 引用失效。故 (b) 排除。
3. **子编号成本最低且追溯完整。** `AC-90a` / `AC-90b` 可与另外 13 条并列达成 1:1 映射，零连锁成本，不破坏任何既有引用链。
4. 执行归属产品经理（编号是 PRD 制品），交付总监只给口径不代改，纳入 M1 尾段行动项 A-01。
