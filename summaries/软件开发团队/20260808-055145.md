## 2. 架构决策（架构师）

### 2.1 目标架构（6 层）

```
L5  editors/vscode        VS Code 前端（TextMate 高亮 / 扩展宿主）
L4  lsp/ + dap/           语言服务与调试适配服务层（独立发行包）
L3  src/jikuai/service/   会话管理与位置映射（LSP 与 DAP 共用）
L2  src/jikuai/diagnostics/ 诊断内核（唯一真源）
L1  src/jikuai/ 13 模块   编译前端 + 运行时（改造）+ frontend.py / completion.py / stdlib_contract.py
L0  stdlib/ + tools/aot/  标准库与实验工具
```

依赖方向严格自上而下，L1/L2 不得反向依赖 L3+，保证主包在不安装 pygls / lsp / dap / aot 情况下 258 用例全绿（由 QA 物理隔离验证守护）。

### 2.2 ADR 精要（ADR-14 .. ADR-21）

- **ADR-14 诊断内核**：`diagnostics/` 为唯一真源；`errors.py` 降级为兼容外壳（保留 `ErrorInfo/ErrorFormatter/ErrorCategory/JiKuaiError/spelling_suggestion` 全部公开符号）；`Diagnostic` 数据模型（code / severity / category / message / span / subject / suggestions / notes，`sort_key()` 决定性排序）+ 错误码分段 `JK-{E|W}0xxx..9xxx`；CLI 与 LSP 均为**纯投影消费者**，不得各自造语义。**追加条款（总监裁定）：错误码是稳定契约，渲染文案不是。**
- **ADR-15 LSP 选型**：采用 **pygls**（纯 Python），压缩技术栈数量，实质缓释风险 R1；M4 交付协议桩，M5 交付正式服务；VS Code 经 `python -m jikuai_lsp` stdio 拉起。
- **ADR-16 stdlib 契约**：`__导出__` 显式导出机制；未声明符号触发 `JK-E5002`；不存在模块触发 `JK-E5001`（含模块名）。**追加条款（总监裁定）：①物理布局固定为仓库根 `stdlib/`；②须定义 `.jk` / `.py` 同名混合模块的优先级与合并语义（`校验.jk` + `校验.py` 已实存）；③`stdlib/` 的 sdist/wheel 分发方式须在 `pyproject.toml` 显式声明（用 data files，不移动目录）。**
- **ADR-17 ADR-06 X2 闭环**：`frontend.py` 两遍分词（Pass1 启发式 → parse → `ClassRegionTable` → Pass2 权威区间）+ 收敛检测；`JK-W9001` 兜底诊断；`JIKUAI_LEGACY_ADR06` 守护开关；性能超 10% 则降级上报。
- **ADR-18 分词副作用治理**：明确 lexer 层全域副作用与 stdlib 分词幂等是**同名不同物**，分别治理，互不混用结论。AC-M5-07-01/02 由 stdlib `分词` 保证，AC-M5-07-03 由 `frontend.py` + `分词` 联合保证。
- **ADR-19 AOT 边界**：支持子集明确化（字面量 + 变量赋值 + 基本运算/比较 + 打印 + 顺序执行；不支持类/继承/异常/管道/pybridge/闭包）；C 中间码为首选后端；`subset_gate.py` 做能力边界自证（`JK-E7001`）。**追加条款（总监裁定）：留痕升级为 ADR-19 强制修订记录 + 对外表述必须区分「打包分发」与「原生二进制编译」。**
- **ADR-20 DAP 协议**：复用 L3 `service/`；`Evaluator` 引入 `ExecHook`（before_stmt / on_break）支撑断点与单步；MVP 不支持条件断点与表达式求值。
- **ADR-21 pybridge 安全边界声明（总监本轮新增）**：文档级 ADR，明确不实现完整沙箱、黑名单的能力边界、适用与禁用场景；不含代码沙箱实现。

## 5. 分歧与裁决记录

### D-01 · pybridge 安全声明缺架构落点（总监三查发现）

- **PM 立场**：US-M5-08 为 Must，须交付安全声明。
- **架构师立场**：6 层架构与 ADR-14..20 未涵盖，无归属层、无 ADR。
- **工程师立场**：已在 WBS 中以 T-M5-P01..P03 覆盖（实现先行于架构）。
- **QA 立场**：未给出该项 AC 可测性结论。
- **裁决**：**追认工程师 P 支线；新增 ADR-21《pybridge 安全边界声明》（文档级 ADR，不含代码沙箱）**。交付物落点固定为 `docs/安全边界.md` + `pybridge.py` 模块 docstring + README 安全声明段；QA 须补**要点清单式文档验收**（文档存在性 + 必含要点逐条核对），纳入 G14 文档类门禁范畴。
- **依据**：Must 级需求不允许无架构承载。安全限制的正确处理方式是「显式声明 + 可验证」，而非「实现缺席 + 文档口头描述」。三方产出不一致时以补齐架构而非削减需求收敛。

### D-02 · 冻结点 F1..F4 无执行载体（总监三查发现）

- **架构师立场**：F1..F4 是硬冻结点，不冻结不得下游开工。
- **工程师立场**：WBS 中仅有月末集成收口窗，未登记冻结点任务。
- **裁决**：**F1..F4 须在 WBS 中登记为零工时 Milestone Gate**，每个 Gate 明确通过判据与责任人；F1 的通过判据强制包含「CLI + LSP 桩双消费者实证」。未过 Gate，下游支线不得开工。
- **依据**：架构约束优先。冻结点若无任务载体，实践中必然被跳过，风险 R3（诊断内核单点）的缓释即失效。

### D-03 · 诊断建议文案变更（架构师上报）

- **架构师立场**：「建议：是否想输入…」→「您是否想输入 `<正确动词>`？」，更具体、更贴合中文语感，预设采纳待裁决。
- **QA 立场**：属输出断言变更，会影响现有用例快照。
- **裁决**：**采纳文案变更。标记为 `Changed`，不标记为 BREAKING。** 配套三项强制动作：
  1. CHANGELOG `Changed` 节明确记录旧 → 新文案；
  2. QA 同步更新受影响用例，并新增「提示含正确动词建议」的断言；
  3. **现有 258 用例中任何对旧文案的精确字符串断言，一律改为对结构化诊断字段断言**。
- **依据**：诊断提示文案属人类可读辅助输出，不构成语言语义、API 契约或退出码，v0.x 阶段不在兼容承诺范围内，故非 BREAKING。同时在 ADR-14 中确立「**错误码是稳定契约，渲染文案不是**」，从根上解耦文案与测试 —— 这既是本次裁决依据，也是防止同类分歧复发的机制。

- **PM 立场**：未拿到 R1–R6 原文，按上下文推断了六条并请求确认。

### D-05 · stdlib 路径分歧（工程师上报）

- **工程师立场**：WBS 写为 `src/jikuai/stdlib/*.jk`，与实际不符，请求裁定。
- **事实核验（总监执行）**：仓库根 `g:\jikuai\stdlib\` 实存 `工具.jk` / `校验.jk` / `校验.py` / `历法.py`；`src/jikuai/` 下不存在 stdlib 目录。
- **裁决**：**统一为仓库根 `stdlib/`**。工程师须将 WBS 中所有 `src/jikuai/stdlib/*` 路径改写为 `stdlib/*`；QA 测试路径同步以实际布局为准。
- **依据**：
  1. 现状即事实。迁移将破坏 `module_loader` 现有解析路径与 v0.4.1 已发布的用户可见路径，向后兼容成本高于收益；
  2. `stdlib/` 是 `.jk` 源码资产而非 Python 包内容，置于 `src/jikuai/` 下会与 13 个扁平模块混淆职责边界，并引入 `package_data` 打包复杂度；
  3. 与架构 L0 层「stdlib + 工具」的仓库根平级布局定义一致。
- **连带指派**：架构师在 ADR-16 追加两条款 —— ①`stdlib/` 的 sdist/wheel 分发方式须在 `pyproject.toml` 显式声明（用 data files，不移动目录）；②**`校验.jk` + `校验.py` 同名双形态已实存**，`__导出__` 契约必须定义混合模块的优先级与合并语义，QA 须为此加用例。

### D-06 · ADR-06 X2 若 M4 不可行的降级预案

- **PM 立场**：定性为缺陷 Must-fix，不可行则降级为文档化限制，上报裁决。
- **架构师立场**：ADR-17 已内置 `JIKUAI_LEGACY_ADR06` 开关与 `JK-W9001` 兜底；性能超 10% 则降级上报。
- **QA 立场**：提供消噪性能测量法作为判定数据源。
- **裁决**：确立如下**不可协商的降级机制**。

  **触发条件（任一命中即触发；判定时点 = M4-W2 结束 Spike-ADR06 出结论时，最迟 M4-W3 结束）**
  - T1：两遍分词导致 258 用例总时长增幅 **> 10%**（按 QA 消噪测量法）
  - T2：`ClassRegionTable` 收敛检测在 M4-W3 结束时仍存在无法收敛的已知反例
  - T3：引入的回归破坏 G1..G8 任一门禁，且 3 个工作日内无解

  **降级后动作（全部强制，不可选）**
  1. `JIKUAI_LEGACY_ADR06` 保持默认 ON（维持旧行为），新路径以 opt-in 形式存在
  2. `JK-W9001` 兜底诊断保留并转为**默认输出**，让限制对用户可见
  3. 定性从「缺陷 Must-fix」改写为「已知限制 + 有兜底诊断」，写入 `docs/已知限制.md` 与 CHANGELOG `Known Issues`
  4. US-M4-06 的 AC 改为「限制被诊断覆盖 + 已文档化」；**v0.5.0 照常发布，不因此延期**
  5. 顺延至 M5-W1 复评一次；若 M5 仍不可行，正式立项为 v1.0 前置阻塞项，停止按月滚动延期

  **判定权归属**：QA 提供数据 → 架构师给技术结论 → **交付总监拍板**。工程师无权自行降级。
- **依据**：质量红线优先，但不允许单一遗留项挟持整月交付。ADR-06 X2 已延期一次，本次必须以「闭环或正式降级留痕」二选一收尾。**可见的限制优于不可见的错误。**

### D-07 · AOT 定位与降级路径判定权

- **PM 立场**：US-M6-06 定为 Could + Experimental，对外措辞已给出。
- **架构师立场**：ADR-19 划定支持子集，C 中间码为首选后端，降级 PyInstaller/Nuitka 须留痕。
- **裁决**：
  1. **确认 Experimental + Could**：不进 v0.7.0 兼容承诺，不进 G13/G14 强门禁；
  2. **结论型验收**：交付最小链路 + 可行性报告 + 局限清单 + 边缘/低资源部署实测数据。**未达成 GA 不算失败，无结论算失败**；
  3. **降级判定时点** = M6-W1 Spike-AOT 结束；
  4. **降级判定权** = 架构师提议 + **交付总监批准**；留痕形式由「须留痕」升级为 **ADR-19 强制修订记录 + 本 Summary 追加记录**；
  5. **对外表述强制区分**：PyInstaller/Nuitka 路径只得称「**打包分发**」，不得称「原生二进制编译」；
  6. **`subset_gate.py` 是本方向唯一不可降级项** —— 无论走哪条后端都必须交付。
- **依据**：文心方向⑤的字面预期是「原生二进制」，若以打包方案冒名顶替会构成对用户的实质误导。区分表述既保住工程灵活性，也守住诚实边界。`subset_gate` 是能力边界的自证机制，缺它则「实验性」变成「不可预期」。
