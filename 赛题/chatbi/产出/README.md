v0.26.0 W145 的验收方式：**不含 LLM、不含 UI**，10 道公开题全部由人手写 `方案.json`，
走 `jk 块 组` / `jk 块 跑` 跑通，源码与结果归档在本目录。规划器在 v0.27.0，所以
「口径层是对的」这件事在本轮必须靠这套手写方案独立证明。

- 执行日期：2026-08-18
- 仓库状态：main / HEAD `4038d37`（工作区有 W130-W144 的未提交改动）
- 块库：制造域 25 块（引擎层 13 + 口径层 12）
- 检索路径：G12（embeddings）当前为红，`jk 块 选` 走 TF-IDF 启发式，**符合预期**；
  本轮不跑 `generate_embeddings.py`
- **本目录未改动任何块文件、评测集、ADR/WBS/AGENTS.md**（硬约束 1）

## 一、怎么复现

本机 `jk` 命令**未安装**（`pip install -e .` 没做过），走模块入口。三条命令：

```powershell
# 仓库根执行，CWD 必须是 g:\jikuai —— 方案里的数据集路径是相对 CWD 的
$env:PYTHONPATH = "g:\jikuai\src"
$env:PYTHONIOENCODING = "utf-8"

# 组：方案 → 极快源码
python -m jikuai 块 组 "赛题\chatbi\产出\Q_PUB_001-方案.json"

# 跑：方案 → 组 → 执行 → 跑响应 JSON
python -m jikuai 块 跑 "赛题\chatbi\产出\Q_PUB_001-方案.json" --json

# 只要源码可以直接落盘再跑
python -m jikuai 块 组 "赛题\chatbi\产出\Q_PUB_001-方案.json" > Q_PUB_001.jk
python -m jikuai Q_PUB_001.jk
```

`<ID>.jk` 就是 `jk 块 组` 的逐字输出，`<ID>-结果.txt` 是 `jk 块 跑 --json` 的
`执行结果` 摘录（退出码 / 占位符检查 / 耗时 / stdout / stderr）。

## 三、多步链路与粘合器自动推参的实际表现

**多步链路是本轮重点验证对象，结论是：链式本身完全跑通，但推参必须人写。**

- 15 份方案共 124 个步骤，最长链路 Q_HID_002 = **17 步**，公开题最长 Q_PUB_007 = 12 步
- `组` / `跑` 退出码：15/15 全为 0
- 源码里出现 `?` 占位或 `需人工填参`：**0 次**
- 但这个 0 **不是**自动推参的功劳——**124/124 个步骤的 `参数` 都是我手写的**，
  自动链式一次都没被真正依赖

### 对照实验：把 `参数` 全部去掉会怎样

拿 Q_PUB_001（最简单的 3 步链）去掉全部 `参数`，用同一批 `共享` 常量，`jk 块 组` 给出：

```jikuai
定义赵果1=读表(赵产量列)。
定义赵果2=截期(赵果1 赵产量列 赵车型维 赵六月末)。
定义赵果3=计产(赵果2 赵产量列 赵车型维)。
```

三行实参**全错**：文件路径槽拿到了 `"actual_quantity"`，`起日` 槽拿到了列表
`【"model_id"】`，`维度列` 槽拿到了字符串。而且——

- **没有一个 `?` 占位**
- **没有一行「类型图未能自动链上」的拒绝理由注释**

跑起来死在第 1 步：`JiKuaiError：表载入：CSV 文件不存在：actual_quantity`（行 15 列 9）。

根因是 ADR-40 §3.1 已经写明的那个代价，在这里第一次咬到人：`共享` 常量在
`glue.TypeGraph.plan` 里一律入池为 `任意`，而 `任意` 在 `type_feeds` 双向放行，
于是**每个字符串常量对每个形参都「类型兼容」**；多候选消解退回「最近产出优先」，
就按池子倒序随便挑了一个。制造域的形参又清一色是 `字符串` / `列表<字符串>`，
`match_slot_name` 的槽名字面匹配对 `赵产量列` ↔ `日期列名` 这种也匹配不上。

**这一条比「跑通了」更值得记**：粘合器在这里既没推对、也没拒绝，是「静默错绑」，
正是 AGENTS.md 第四节警告的那类。W145 的方案能全绿，靠的是人把 124 个实参全写死。

### 手工拆包元组：2 处

`停线汇总`/`延期汇总`/`延期排行`/`班间对比`/`达成率*` 的输出是**元组**，
类型图明确拒绝把 `元组[列表,数]` 喂给 `列表` 形参（这是设计如此）。两处按
AGENTS.md 四·6 用索引显式拆包，语法 `赵果3【0】`：

- `Q_PUB_008` 步骤 4：`定序(赵果3【0】 …)` —— 停线汇总 → 排序
- `Q_HID_005` 步骤 10：`联表(赵果6 赵果9【0】 …)` —— 延期汇总 → 连接

两处都跑通了。但这说明**口径块的元组输出与引擎层的列表输入之间没有官方衔接**，
每次都要调用方自己写索引，规划器要生成这段索引表达式。

## 四、对不上的题：差在哪、根因在哪一方

只有一处实质偏差，牵动两题（Q_PUB_004 与 Q_PUB_007 的 L002 分句）。

**现象**：reference 说「哪条产线单车电耗异常升高 = L002」，而按块库能算出来的
「窗口内单车电耗降序」榜首是 L006（256.505），L002（191.095）排第 4。

**根因：三方都不算错，缺的是一个块。**

- 方案没写错：`截期` + `车耗现` + `定序` 就是「窗口内单车电耗排名」的正确实现，
  两个口径块（现成 191.095 / 重算 191.087）互相校验也一致
- 块没写错：`单车电耗现成` 自报的口径就是「记录等权算术平均」，它没承诺做异常检测
- reference 也没错：「异常升高」是**相对自身基线的升幅**，不是横向水平比较。
  八条产线的能耗强度本来就差一个量级（L001 104.5 ↔ L006 256.5），横向比水平
  必然选出结构上最耗电的那条线，跟「异常」无关

**证据**（Q_PUB_004 方案第 9-10 步已把基线算进归档，无需外部脚本）：

| 产线 | 窗口内（06-10～06-24） | 基线（01-01～06-09） | 升幅 |
| --- | --- | --- | --- |
| **L002** | **191.095** | **151.801** | **+25.9%** |
| L008 | 163.604 | 158.607 | +3.2% |
| L005 | 247.862 | 248.085 | −0.1% |

L002 是唯一一条材料性上升的线，**换成升幅口径后与 reference 完全一致**。

**归责**：**缺口在块库**——没有「同一指标两个时间窗口对比 / 环比 / 基线偏离」的块。
现在的做法是同一个口径块跑两遍不同窗口，然后**人拿两张表逐行相除**。同一个坑在
Q_HID_001（缺陷率 5 月 vs 6 月）、Q_HID_003（中旬 vs 基线）也踩到，共 4 题。
`评测集-chatbi-留出.json` 自己也承认「环比差值由调用方自己比——库里没有环比块」。

Q_PUB_007 的 L002 分句是同一根因的派生：日报只有绝对量口径块，`能耗汇总` 出的
是总电耗，L002 在总电耗上排第 3、看不出异常；要在日报里点出 L002 就得有升幅能力。

**没有把任何数字往期望上凑**：Q_PUB_004 归档的第一张表仍然是「水平降序」的原始结果
（L006 居首），基线表是并列的第三份输出，判读留给人。

## 六、暴露的能力缺口清单（给 v0.27.0 的输入）

按严重度排序。**全部只是报告，本轮未改任何块**。

1. **没有「时间窗口对比 / 环比 / 基线偏离」块**（4 题踩到：Q_PUB_004、Q_PUB_007、
   Q_HID_001、Q_HID_003）。现状是同口径块跑两遍 + 人肉相除。这是唯一一处导致
   公开题与 reference 判读不一致的缺口，优先级最高。所有「是否上升 / 是否异常 /
   是否偏高」类问句都落在这里。
2. **自动推参在制造域是静默错绑，不是「推不出来就占位」**（§三 对照实验）。
   `共享` 常量入池为 `任意` + `任意` 双向放行 ⇒ 每个字符串常量对每个形参都兼容 ⇒
   按「最近产出优先」随便挑，既不报 `?` 也不写拒绝理由。v0.27.0 的规划器**必须
   自己把每一个实参写死**，不能指望 `--自动链式`。若要修粘合器，方向是让 `共享`
   携带声明类型（或至少让「多个 `任意` 候选竞争同一槽」这件事进拒绝理由）。
3. **口径块的元组输出接不上引擎层的列表输入**，每次都要调用方写 `赵果N【0】`
   索引拆包（本轮 2 处）。要么给口径块加「只出汇总表」的姊妹出口，要么让粘合器
   支持声明式拆包，否则规划器得生成索引表达式。
4. **`窗口` 只能切单个闭区间**，表达不了「窗口之外的全部」。做基线对比时我只能取
   01-01～06-09，把 06-25～06-30 那 6 天丢在外面（Q_PUB_004）。需要「补集」或
   「多区间」能力。
5. **绝对量与比率的排名混淆没有块层防护**。`能耗汇总` 出总电耗、`单车电耗*` 出比率，
   两者的排名结论**不同**（L005 总电耗第 1、单车电耗第 2；L002 总电耗第 3、
   升幅第 1）。块描述各自自报了口径，但没有任何东西阻止使用者拿总量榜回答
   「效率异常」的问题。规划器要显式选一条，且在溯源里写明选了哪条。
6. **`延期汇总` / `缺陷汇总` 的结果不能直接排序**（元组 + 按维度键升序）。
   Q_PUB_007 按 customer_id 汇总出 60 行按 ID 升序，C005 是靠人扫出来的，
   没有「按延期天数合计降序取前 N」的现成路径（`延期排行` 是订单级榜、不是分组级榜）。
7. **「6月」这类时间词的锚点列没有单一真源**（Q_PUB_006）。订单表有 order_date /
   planned_delivery_date / actual_delivery_date 三个候选，选哪个直接改变
   「未交付单数」（口径 A 得 0，口径 B 得 9）。本轮两个口径都算了、结论没翻转，
   但这是运气。语义层应当为每个业务词登记**默认时间锚点列**。
8. **`邻期关联` 的一对多会让右表记录被重复计数**（Q_HID_002 步骤 17：邻期窗口内
   L002-焊装 1599，而 6 月 M003 在 L002 焊装的真实缺陷数是 465+97=562）。块描述
   确实写了「输出行数会明显膨胀，绝不是 1 对 1」，但下游 `缺陷汇总` 照样把膨胀后的
   行求和，得到一个**没有业务含义的绝对量**。结构比较仍然有效，绝对值不能用。
   建议：要么给关联结果加去重标记列，要么在 `缺陷汇总` 描述里点名这个坑。

## 七、本轮没有发现的问题（同样值得记档）

- 25 个制造域块**没有一个报出实现 bug**。所有报错都是块按口径主动拒绝
  （对照实验里的「CSV 文件不存在」就是 `表载入` 的正确行为）
- `连接` 的 1:1 行数守恒在真数据上成立：Q_PUB_005 的 L003 子集联表后白/夜班各
  181 行、合计 362 = 筛出的实绩行数；Q_HID_004 全表联表后白/夜班各 1448 行、
  合计 2896 = ADR-40 §4.2 冻结值
- 空值纪律在三处独立复现：延期排行排除 57、Q_HID_005 延期汇总排除 57、
  停线汇总缺测 0（`downtime_minutes` 零空值，与 ADR-40 §4.3 一致）
- 两个单车电耗口径在窗口子集上仍然等值（191.095 vs 191.087，相对差 4e-5），
  与 ADR-40 §5.2 记的「本数据集两口径逐行等值」一致
